第 5 轮好好的，第 40 轮开始胡说。信息全都还在窗口里，模型就是用不好了。

## 一句话

上下文变长会让准确率**非线性下降**，而且这是注意力架构本身的性质——窗口变大不解决它，只把悬崖往后挪。

## 原理

### 有多严重

[Chroma Research](https://research.trychroma.com/context-rot)（Kelly Hong、Anton Troynikov、Jeff Huber，2025 年 7 月）把这个现象命名为 **context rot**，并在 18 个前沿模型上验证了它——**退化在窗口远没坐满时就开始了**。另一组更狠的实测来自 [NoLiMa](https://arxiv.org/abs/2502.05167)（Ali Modarressi 等，慕尼黑大学与 Adobe Research，2025 年 2 月）：**12 个被测模型里有 10 个，在上下文到 32K 时掉到自己短上下文基线的一半以下**。连表现最好的例外之一 GPT-4o 也从近乎满分的 99.3% 掉到 69.7%。

注意「一半以下」这个量级。这不是「稍微差一点」，是**能力腰斩**。

NoLiMa 的设计值得说一句，因为它解释了为什么这个数比常见的「大海捞针」测试难看得多：**它刻意去掉了问题和答案之间的字面重合**。大海捞针那类测试里，问题和目标句往往共享关键词，模型靠字面匹配就能捞出来，于是分数很好看。把字面线索拿掉、逼模型真的做语义关联，长上下文的水分就出来了。

> [!warning] 别拿「支持 100 万 token」当能力承诺
> 标称窗口是**技术上限**，NoLiMa 测的是**有效长度**。两者差一个数量级是常态。选型时该问的不是「窗口多大」，而是「在我的任务上，多长之后开始塌」——后者只能自己测，见 [[04-排行榜怎么读]]。

关键在于它和「窗口装不下」是两件事：

| | 装不下 | context rot |
| --- | --- | --- |
| 现象 | 报错或截断 | **不报错**，只是答得差 |
| 原因 | token 数超上限 | 注意力在长序列上的有效性下降 |
| 解法 | 加大窗口 | **加大窗口没用** |

第二列的「不报错」是它最难缠的地方，见 [[03-漂移监控三条线]]。

### 为什么加大窗口不解决

有个说法叫 MECW——**有效上下文远小于技术上限**，而且这个差距是注意力架构的函数，不只是 token 数的函数。

具体机制有几层：

- **注意力被稀释**。序列越长，权重分布越平，关键信息拿到的权重相对越少
- **位置深处召回差**。这和位置编码的外推问题是同一件事，见 [[07-位置编码与长度外推]]
- **干扰增多**。无关内容越多，模型越容易被带偏
- **多轮里的错误会累积**。前面某轮的错误结论留在历史里，后面基于它继续推

所以窗口从 128k 涨到 100 万，只是把悬崖往后挪一点，坡度没变。

### 四类具体的退化

![[上下文衰减的四类症状.excalidraw.md|700]]

长会话 agent 上表现为这几种，各有各的修法：

| 症状 | 多半是什么问题 | 往哪修 |
| --- | --- | --- |
| 忘了早期定下的规则 | 约束被压缩掉了 | 把约束移出可压缩区，每 N 轮重注入一次，见 [[03-Compaction 与外部记忆文件]] |
| 反复做同一件事 | 没有进度状态 | 外部记忆文件 + [[02-终止条件]] |
| 越答越长、越答越水 | 历史里的长回答成了示范 | 压缩时统一格式 |
| 事实前后矛盾 | 早期的错误结论没被清理 | 定期重新核对，见 [[04-记忆冲突消解]] |

**先分清是哪一类再动手。** 四类的修法完全不同，混着治多半没效果。

### 怎么量它

**成功率随轮数的衰减曲线**是核心工具：

1. 造一批需要多轮完成的任务
2. 记录每一轮之后的任务成功率或关键指标
3. 画出来，找出开始塌的那个点

再补两个更尖锐的测试：

**早期事实召回**——在第 30 轮问一个只在第 3 轮提到过的事实。答不出来说明信息在压缩或衰减中丢了。

**约束保持**——在第 50 轮做一件早期明令禁止的事，看它拦不拦。拦不住就是 governance decay，见 [[03-Compaction 与外部记忆文件]]。

这两个测试要进 golden set，每次改动都跑，见 [[01-Golden set]]。

### 工程上怎么扛

按效果排：

**一、别让它变长。** 最有效的一条。检索少而准、子任务隔离、及时外置，见 [[02-Context engineering：上下文即预算]]。

**二、关键信息放两头。** 序列开头和结尾的召回最好，中间最差。重要约束和当前任务放这两处。

**三、定期重注入。** 每 N 轮把核心约束和任务目标重新贴一遍。几百 token 的成本，换约束不失效。

**四、状态外置。** 进度、待办、已知事实写进外部文件，agent 每轮从文件读，而不是从历史里翻。

**五、该重开就重开。** 超过某个轮数，与其在退化的上下文里挣扎，不如带着摘要开一个新会话。**这是最被低估的一条**——很多系统死撑着不重开，结果后面几十轮全是无效的。

## 动手做

- [ ] 画一条成功率随轮数的衰减曲线，标出开始塌的那个点
- [ ] 做「第 30 轮问第 3 轮的事」测试，记录召回率
- [ ] 做「第 50 轮违反早期约束」测试，看拦不拦得住
- [ ] 把四类症状对照自己系统，判断主要是哪一类
- [ ] 加上定期重注入，重画衰减曲线
- [ ] 设一个「超过 N 轮带摘要重开」的策略，对比效果

## 算学会了

- [ ] 知道 context rot 不报错，只能靠主动测试发现
- [ ] 知道加大窗口不解决这个问题
- [ ] 能分清四类退化症状，对应到不同的修法

## 坑

**以为窗口够大就没事。** 有效表现在远没满的时候就开始衰减。

**只测短会话。** 开发时测三五轮，线上跑四十轮，问题全在后面。

**把退化当成模型能力问题。** 换个更强的模型也一样会衰减，那是架构性质。

**不区分症状类型。** 四类退化的修法完全不同。

**死撑着不重开会话。** 在已经退化的上下文里继续，后面每一轮都是浪费。
