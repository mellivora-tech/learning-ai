同一个模型、同一个任务，一个团队做出来成功率 60%，另一个做出来 92%。差的通常不是提示词。

## 一句话

Harness 是模型周围那一圈脚手架——工具、验证器、重试、环境反馈；它让模型**能自己发现错了**，而这比让它一次做对容易得多。

## 原理

### 两种做法

![[裸 prompt 与 harness.excalidraw.md|700]]

**裸 prompt** 的思路是：把要求写清楚，让模型一次答对。做不好就再改改提示词。

问题在于这条路上没有任何**反馈回路**。模型答完就完了，对不对只有人看得出来，而且错了也不知道错在哪一步。

**Harness** 的思路是：不指望一次对，而是让模型**有办法知道自己对没对**。四个部件：

| 部件 | 干什么 |
| --- | --- |
| **工具** | 让模型能做它算不准的事——查数据、跑代码、调 API |
| **验证器** | 客观判定这次输出行不行——schema 校验、单元测试、业务规则 |
| **重试** | 不行就带着**具体报错**再来一次，见 [[02-修复循环（报错回灌）]] |
| **环境反馈** | 把执行结果送回去，让下一步基于真实状态而非猜测 |

### 那个思维转变

**第一反应从「改改提示词」变成「模型缺什么才能自己发现错误」。**

这是这一节唯一需要记住的事。举个具体的：

> 模型生成的 SQL 老是引用不存在的字段。
>
> **裸 prompt 思路**：在提示词里把表结构写得更详细、加更多例子、强调「只能用列出的字段」。
>
> **harness 思路**：给它一个「查表结构」的工具，再加一个「先 EXPLAIN 一下」的验证步骤。字段不存在时数据库会报错，把报错送回去，它自己就改对了。

第二条路不需要提示词写得多好，而且**对新表、没见过的 schema 一样管用**。这就是泛化能力的来源。

### 验证器是最值钱的那个

四个部件里，验证器的投入产出比最高，因为它把「好不好」从主观变成了客观。

按可得性排：

| 验证器 | 适用 | 强度 |
| --- | --- | --- |
| Schema / 类型校验 | 结构化输出 | 强，且几乎零成本 |
| 单元测试 / 编译 | 代码生成 | 最强 |
| 业务规则检查 | 抽取、计算 | 强，要自己写 |
| 引用校验 | RAG | 中——能查引用的来源是否真实存在 |
| LLM judge | 自由生成 | 弱且贵，见 [[04-Judge 校准]] |

**能用前四种就别用第五种。** 客观验证器又快又便宜又不会自己出错。

一个务实的起步：**先加 schema 校验**。它覆盖面广、实现成本几乎为零，而且立刻能把「格式不对」这类失败从统计里剔除，让你看清真正的问题在哪，见 [[01-结构化输出三档]]。

### 别把 harness 做成无限循环

有反馈回路就有失控风险：

- 重试次数要有上限，通常 2–3 次
- 每次重试要带**具体报错**，不是「格式错了请重试」
- 连续几次没进展就停下来交给人，见 [[02-终止条件]]
- 整体要有预算刹车，见 [[01-五类硬预算]]

**修复三次还不对，第四次多半也不对。** 这时候升级到人比继续烧钱好。

### 怎么证明它有用

这是阶段 2 的里程碑：**同一个任务做两版，用同一批数据测，出一份对比报告**。

要报的不只是成功率，还有：

- 成本（harness 版会多花 token 和工具调用）
- 延迟（多了验证和重试）
- **失败模式的变化**——harness 版剩下的失败是哪一类

第三项最有价值。裸 prompt 版的失败往往五花八门，harness 版剩下的失败会集中在「验证器覆盖不到的那部分」——**那正好告诉你下一个验证器该加在哪**。

## 动手做

- [ ] 挑一个真实任务，做裸 prompt 和 harness 两版
- [ ] 先只加 schema 校验，测一次成功率变化——通常这一步就有明显提升
- [ ] 再加一个客观验证器（测试、业务规则），记录增量
- [ ] 加带报错回灌的重试，上限 3 次，统计一次修复的成功率
- [ ] 用同一批数据测两版，记录成功率、成本、延迟、失败模式分布
- [ ] 分析 harness 版剩下的失败，找出下一个该加的验证器

## 算学会了

- [ ] 遇到效果问题，第一反应是「它缺什么工具才能自查」而不是「改改提示词」
- [ ] 能按可得性给验证器排序，优先用客观的
- [ ] 重试带具体报错，且有次数上限
- [ ] 有一份 harness 版 vs 裸 prompt 版的对比报告，带 eval 数据支撑
- [ ] 会用「剩下的失败集中在哪」来决定下一个验证器

## 坑

**在提示词上死磕。** 提示词的边际收益递减得很快，而且对没见过的输入不泛化。

**先上 LLM judge 当验证器。** 又贵又不可靠，而且它自己也需要被评估。能用客观验证器就别用它。

**重试不带报错。** 「格式错了请重试」几乎没有信息量，模型只能瞎猜，多半再错一次。

**无限重试。** 三次不行就该停，继续只是在烧钱。

**只报成功率。** 成本和延迟都会涨，不报出来就没法判断这笔买卖划不划算。
