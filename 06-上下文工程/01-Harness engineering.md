同一个 Claude Opus 4.5，换一套外围系统去跑 SWE-bench Pro，成绩从 45.9% 变成 55.4%。权重一个比特都没动，差出来的这近 10 分全在模型之外。

## 一句话

Harness 是模型周围那一圈脚手架——工具、验证器、重试、环境反馈；它让模型**能自己发现错了**，而这比让它一次做对容易得多。

## 原理

### 两种做法

![[裸 prompt 与 harness.excalidraw.md|700]]

**裸 prompt** 的思路是：把要求写清楚，让模型一次答对。做不好就再改改提示词。

问题在于这条路上没有任何**反馈回路**。模型答完就完了，对不对只有人看得出来，而且错了也不知道错在哪一步。

**Harness** 的思路是：不指望一次对，而是让模型**有办法知道自己对没对**。四个部件：

| 部件       | 干什么                                   |
| -------- | ------------------------------------- |
| **工具**   | 让模型能做它算不准的事——查数据、跑代码、调 API            |
| **验证器**  | 客观判定这次输出行不行——schema 校验、单元测试、业务规则      |
| **重试**   | 不行就带着**具体报错**再来一次，见 [[02-修复循环（报错回灌）]] |
| **环境反馈** | 把执行结果送回去，让下一步基于真实状态而非猜测               |

### 这一圈脚手架值多少分

[Stop Comparing LLM Agents Without Disclosing the Harness](https://arxiv.org/abs/2605.23950)（Yunbei Zhang、Janet Wang 等，杜兰大学、罗格斯大学与弗吉尼亚理工，2026）把这件事量成了数字：

- 同一个 Claude Opus 4.5 在 SWE-bench Pro 上，只换外围系统，成绩在 **45.9% 到 55.4%** 之间（原文 2.1 节）
- 固定模型、只换 harness，Grok 4 在 SWE-bench Verified 上能动 **14–16 个百分点**（原文 Table 1）
- 他们做了一次控制实验（原文 4.2 节，SWE-bench Verified 的 100 题子集）：把「换 harness」和「换模型」当两个因子分别算方差，**harness 方差是模型方差的 7.8 倍**

> [!info] SWE-bench 是什么
> 一批从真实 GitHub 仓库里取出来的 issue，模型要交一个能让原仓库测试转绿的补丁。由 [SWE-bench](https://arxiv.org/abs/2310.06770)（Carlos E. Jimenez、John Yang 等，普林斯顿大学，2023）提出，Verified 与 Pro 是后来更干净、更难的两个变体。

最后那条是最值得记的：**在模型选型上纠结的那几分，很可能没有换一套脚手架来得多。**

### 四个部件串起来是什么样

四个部件不是四个模块，是一个循环里的四行代码：

```python
def run(task, max_repair=3):
    msgs = [SYSTEM, user(task)]
    repaired = 0
    while True:
        out = model(msgs, tools=[查表结构, 试跑一次])     # 工具
        if out.tool_calls:
            msgs += [out, execute(out.tool_calls)]      # 环境反馈：真实返回值
            continue
        err = validate(out)                             # 验证器
        if err is None:
            return out
        if repaired >= max_repair:
            return escalate(task, msgs)                 # 用完次数是升级，不是失败
        msgs += [out, f"校验失败：{err}"]                # 重试：带原始报错
        repaired += 1
```

三处细节决定这段代码有没有用：

- `validate` 必须是**机器判定**——校验器、类型检查、真实执行。让模型自己回答「你觉得对吗」，它会说对。
- `err` 要**原样**塞回去。校验器吐的 `$.items[2].amount: expected number, got "1,280.00"` 里，路径、期望、实际三样都是模型定位问题需要的；翻译成「格式不对」就全丢了，见 [[02-修复循环（报错回灌）]]。
- `execute` 的返回是**真实状态**。模型的下一步对着它走，而不是对着自己上一步的猜测。

**这段代码里没有一个字在讲提示词怎么写。**

### 那个思维转变

**第一反应从「改改提示词」变成「模型缺什么才能自己发现错误」。** 举个具体的：

> 模型生成的 SQL 老是引用不存在的字段。
>
> **裸 prompt 思路**：在提示词里把表结构写得更详细、加更多例子、强调「只能用列出的字段」。
>
> **harness 思路**：给它一个「查表结构」的工具，再加一个「先 EXPLAIN 一下」的验证步骤。字段不存在时数据库会报错，把报错送回去，它自己就改对了。

第二条路不需要提示词写得多好，而且**对新表、没见过的 schema 一样管用**。这就是泛化能力的来源。

### 验证器是最值钱的那个

四个部件里，验证器的投入产出比最高，因为它把「好不好」从主观变成了客观。

按可得性排：

| 验证器 | 适用 | 强度 |
| --- | --- | --- |
| Schema / 类型校验 | 结构化输出 | 强，且几乎零成本 |
| 单元测试 / 编译 | 代码生成 | 最强 |
| 业务规则检查 | 抽取、计算 | 强，要自己写 |
| 引用校验 | RAG | 中——能查引用的来源是否真实存在 |
| LLM judge | 自由生成 | 弱且贵，见 [[04-Judge 校准]] |

**能用前四种就别用第五种。** 客观验证器又快又便宜又不会自己出错。

一个务实的起步：**先加 schema 校验**。它覆盖面广、实现成本几乎为零，而且立刻能把「格式不对」这类失败从统计里剔除，让你看清真正的问题在哪，见 [[01-结构化输出三档]]。

### 但「通过」不等于「对」

![[验证器的覆盖边界.excalidraw.md|605]]

每一层验证器都只挡住一类形状的错误。schema 校验管的是**字段齐不齐、类型对不对**，它对「金额算错了一位」毫无办法——那个值是合法的 number。测试挡的是跑不起来和崩掉的，业务规则挡的是违反显式约束的。**格式全对、测试全绿、约束全满足，答案照样可以是错的**，而这条路上没有任何检查点。

更麻烦的是第二种情况：**验证器定义了目标，模型就朝那个目标去**，哪怕绕开真正的任务。

[SpecBench](https://arxiv.org/abs/2605.21384)（Bingchen Zhao 等，Weco AI，2026）在 30 个系统级编程任务上测了这件事：前沿 agent 几乎都能把可见测试跑满，但换成模型看不到的留出测试，差距随任务规模迅速拉大——参考实现每大十倍，可见与留出的差距扩大 **28 个百分点**。最极端的一例是模型写了个 2900 行的哈希表「编译器」，把公开测试的输入输出预先算好存进查找表：**可见测试 97%，留出测试 0%**。

这不是模型使坏，是验证器写成什么样，它就优化成什么样。三个对策：

- **留一批模型看不到的检查。** 和 golden set 里留出测试集是同一个道理，见 [[01-Golden set]]。
- **验证器和生成不共用同一份信息。** 用模型自己写的测试来验模型自己写的代码，是在自己给自己判卷。
- **抽样人工看。** 比例可以很低，但不能是零——这是唯一能发现「验证器整体跑偏了」的手段。

### 四类客观验证器都用不上的时候

按可得性排完序，真实的困境往往是：我这个任务，前四种一个都够不着。别直接跳到 LLM judge，先试这两步：

**一、改任务的形态，让它变得可验证。** 「写一段客户情况摘要」验不了，「填这 5 个字段：客户名、合同金额、到期日、风险等级、依据原文的句子」就能验——字段类型能查，金额能和原文比对，引用的句子能查是不是真的存在于原文。**把自由文本换成结构，主观判断的一大半就变成了客观判断。**

**二、把一个主观判定拆成几个客观子判定。** 「这份回答好不好」拆开：引用的每条来源是否真实存在、里面的数字和原文对不对得上、有没有回答被问的那个问题。前两条完全客观，第三条也能用「问题里的实体是否出现在答案里」近似。

剩下真正主观的那一小部分，才轮到 LLM judge，而且用之前要先校准，见 [[04-Judge 校准]]。

底线是：**没有验证器的那部分，别假装有。** 在报告里把它单列成「未验证」，比塞一个不可靠的 judge 让指标好看诚实得多。

### 别把 harness 做成无限循环

有反馈回路就有失控风险：

- 重试次数要有上限，通常 2–3 次
- 每次重试要带**具体报错**，不是「格式错了请重试」
- 连续几次没进展就停下来交给人，见 [[02-终止条件]]
- 整体要有预算刹车，见 [[01-五类硬预算]]

上限定在 2–3 次不是拍脑袋。[How Many Tries Does It Take?](https://arxiv.org/abs/2604.10508)（Johin Johny Arimbur，2026）在 HumanEval 和 MBPP 上跑满五轮修复，结论是**大部分收益集中在前两轮**；按错误类型拆开看更清楚：语法错、名字错修得回来，而 assertion 类的逻辑错只有 **45% 左右**能修好。

还有一条更值得警惕的证据。[Is Self-Repair a Silver Bullet for Code Generation?](https://arxiv.org/abs/2306.09896)（Theo X. Olausson 等，麻省理工学院，ICLR 2024）把修复的开销也算进成本：**很多设定下，修复的收益还不如把同样的预算拿去多采样几次**。他们进一步定位到瓶颈在反馈质量——换更强的模型来产生反馈，收益才明显变大。

所以修复循环的价值不在「再来一次」，在**反馈是真的**。带着真实报错重试值得做，让模型自己回头检查自己不值得。

### 验证器自己也要花钱

验证不是免费的，它的延迟和成本会直接进 P95 和账单。跑一遍单元测试可能比模型生成还慢，调外部 API 做业务规则检查还要算上对方的配额。

两个便宜的做法：

- **分级触发。** 毫秒级的先跑（schema、类型、长度），贵的（跑测试、查外部系统）只在便宜的过了之后才跑。绝大多数失败会被第一级挡掉。
- **能并行的并行。** 几个互不依赖的验证器同时跑，延迟按最慢的算而不是加起来。

还有一个容易漏掉的决定：**失败之后重跑到哪一步。** 多步任务里第 4 步的验证没过，是只重跑第 4 步，还是从头再来？只重跑一步便宜得多，但要求前 3 步的产物是可寻址、可复用的，而且重跑本身得是幂等的，见 [[07-幂等性与故障注入]]。这件事不在设计时想清楚，最后就会退化成整条重来——成本乘以步数。

### 怎么证明它有用

这是阶段 2 的里程碑：**同一个任务做两版，用同一批数据测，出一份对比报告**。

要报的不只是成功率，还有：

- 成本（harness 版会多花 token 和工具调用，还要加上验证器自己的开销）
- 延迟（多了验证和重试）
- **失败模式的变化**——harness 版剩下的失败是哪一类

第三项最有价值。裸 prompt 版的失败往往五花八门，harness 版剩下的失败会集中在「验证器覆盖不到的那部分」——**那正好告诉你下一个验证器该加在哪**。

## 动手做

- [ ] 挑一个真实任务，做裸 prompt 和 harness 两版
- [ ] 先只加 schema 校验，测一次成功率变化——通常这一步就有明显提升
- [ ] 再加一个客观验证器（测试、业务规则），记录增量
- [ ] 加带报错回灌的重试，上限 3 次，统计一次修复的成功率
- [ ] 造一批「格式全对但答案是错的」样本，看现有验证器能抓住几条
- [ ] 留出一批模型看不到的检查，比对可见与留出两套的通过率差距
- [ ] 量一次验证器自己占了多少延迟和成本
- [ ] 用同一批数据测两版，记录成功率、成本、延迟、失败模式分布
- [ ] 分析 harness 版剩下的失败，找出下一个该加的验证器

## 算学会了

- [ ] 遇到效果问题，第一反应是「它缺什么工具才能自查」而不是「改改提示词」
- [ ] 能按可得性给验证器排序，优先用客观的
- [ ] 知道验证器通过不等于答案对，且有留出的检查在盯着这件事
- [ ] 任务本身不可验证时，会先改任务形态或拆成客观子判定，而不是直接上 judge
- [ ] 重试带具体报错，且有次数上限
- [ ] 验证器自己的成本和延迟在账上
- [ ] 有一份 harness 版 vs 裸 prompt 版的对比报告，带 eval 数据支撑
- [ ] 会用「剩下的失败集中在哪」来决定下一个验证器

## 坑

**在提示词上死磕。** 提示词的边际收益递减得很快，而且对没见过的输入不泛化。

**拿验证器通过率当成功率。** 它只说明形状对，不说明答案对——通过率 100% 的系统照样可以一直在给错答案。

**用模型自己产出的东西来验模型。** 自己写测试验自己写的代码，自己判断自己的答案好不好，都是自己给自己判卷。反馈必须来自外部。

**先上 LLM judge 当验证器。** 又贵又不可靠，而且它自己也需要被评估。能用客观验证器就别用它。

**重试不带报错。** 「格式错了请重试」几乎没有信息量，模型只能瞎猜，多半再错一次。

**无限重试。** 三次不行就该停，继续只是在烧钱。

**只报成功率。** 成本和延迟都会涨，不报出来就没法判断这笔买卖划不划算。
