## 交付物

一份对比报告，结论要有 eval 数据支撑，不能是「感觉更好了」。

- 同一个真实任务的两个实现：裸 prompt 版、harness 版
- 同一批数据（至少 50 条，从真实流量抽）上的四项对比：**成功率、单次成本、P95 延迟、失败模式分布**
- harness 每加一个部件（schema 校验 → 客观验证器 → 报错回灌重试）的**增量收益**，一件一件测
- 一条成功率随轮数的衰减曲线，加 compaction 前后各一条
- 一句话结论：**「加了 X，成功率从 A 到 B，代价是成本涨 C%、延迟涨 D%」**

## 做法

1. 挑一个真实任务，先做裸 prompt 版当基线，见 [[01-Harness engineering]]
2. 从线上抽 50 条真实样本并标注，这批同时也是 golden set 的起点，见 [[01-Golden set]]
3. 只加 schema 校验，测一次——通常这一步就有明显提升
4. 加一个客观验证器（测试、业务规则、引用校验），测增量
5. 加带**具体报错**回灌的重试，上限 3 次，统计一次修复成功率
6. 给每一段内容划 token 预算，见 [[02-Context engineering：上下文即预算]]
7. 加 compaction 与外部记忆文件，画衰减曲线，见 [[03-Compaction 与外部记忆文件]]
8. 做两个尖锐测试：第 30 轮问第 3 轮的事、第 50 轮违反早期约束

## 复盘

- 哪个部件带来的增量最大？多数情况下是最便宜的那个（schema 校验），是不是也符合你的观察
- harness 版剩下的失败集中在哪一类？**那就是下一个该加的验证器**
- 成本涨了多少？这笔买卖在你的业务上划不划算
- 约束保持率如果不是 100%，是被压缩掉了还是从来没生效过——前者要改压缩策略，后者要在工具层加硬检查
- 衰减曲线在加了 compaction 之后往后挪了多少轮？够不够覆盖你真实会话的长度
