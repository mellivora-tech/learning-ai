「这两个问题意思差不多，直接返回上次的答案」——听起来很省钱。直到有人问「这个能退款吗」和「这个不能退款吗」，拿到了同一个回答。

## 一句话

语义缓存用相似度判断「问的是不是同一件事」，而**相似不等于等价**——所以真正的工作不是把它做出来，是找出它在哪些场景下绝对不能用。

## 原理

### 它和前缀缓存完全不同

| | 前缀缓存 | 语义缓存 |
| --- | --- | --- |
| 判据 | 前缀**逐 token 完全相同** | 向量相似度超过阈值 |
| 省什么 | prefill 计算 | **整次调用** |
| 会出错吗 | 不会——完全相同就是完全相同 | **会**——相似不等于等价 |

第三行是全部风险的来源。前缀缓存是**无损优化**，语义缓存是**有损的赌注**。

### 假命中是怎么发生的

问题出在 embedding 的相似度不理解语义的**关键差异**，见 [[06-Embedding 与向量空间]]。几类典型的翻车：

| 一对问题 | 相似度 | 实际 |
| --- | --- | --- |
| 「这个能退款吗」/「这个不能退款吗」 | 很高 | 答案相反 |
| 「A 比 B 贵吗」/「B 比 A 贵吗」 | 很高 | 答案相反 |
| 「2024 年的政策」/「2025 年的政策」 | 很高 | 完全不同 |
| 「张三的工资」/「李四的工资」 | 很高 | **越权** |

最后一行最危险：**语义缓存可能变成越权通道**。两个不同用户问结构相同的问题，相似度很高，缓存把 A 的答案给了 B。

### 所以必须做的三件事

**一、cache key 带上隔离维度。** 至少要有 `tenant_id`、`user_id`（涉及个人数据时）、权限范围。这不是优化，是正确性要求，见 [[05-缓存安全与跨租户命中]]。

**二、主动找假命中。** 这是这一节最重要的动作——**不要等线上出事，自己构造语义相近但答案相反的问题对**：

- 加否定词：能/不能、是/不是
- 换主体：张三/李四、A/B
- 换时间：2024/2025、上季度/本季度
- 换数量：一个/多个、全部/部分
- 反转比较：A 比 B / B 比 A

拿这批对子跑一遍，看有多少被判成同一个。**这个数就是你的假命中率**，它比命中率重要得多。

**三、划出禁区。** 有些场景不管阈值调多高都不该用：

| 禁用 | 为什么 |
| --- | --- |
| 涉及个人数据的查询 | 假命中就是数据泄露 |
| 时效性强的信息 | 昨天的答案今天可能就错了 |
| 带否定、比较、数量的问句 | 恰好是 embedding 最不敏感的地方 |
| 有副作用的操作 | 缓存一个「已下单」的回答是灾难 |

**能安全用的通常是：无个人数据、时效性弱、事实性强的问答**——产品说明、政策解释、常见问题这类。

### 阈值怎么定

用假命中率反推，而不是拍一个 0.9：

1. 构造一批「该命中」的对子（真正的同义问法）
2. 构造一批「不该命中」的对子（上面那五类）
3. 扫阈值，画出命中率和假命中率两条曲线
4. **按业务能承受的假命中率定阈值**，而不是按命中率

多数场景下这条线会定得很高（0.95 以上），命中率因此很低——**这时候要诚实地问：省下的这点钱值不值这个风险。**

### 更安全的替代

在下结论之前，先看看这两个是不是更划算：

**前缀缓存**——无损，几乎没有风险，收益也很实在，见 [[04-Prompt caching]]。这个应该先做满。

**精确缓存**——按问题的规范化文本做精确匹配（去空格、统一大小写、去标点）。命中率低于语义缓存，但**没有假命中**。对高频重复问题（FAQ 类）已经够用。

**很多团队上语义缓存是因为没把前面两个做满。** 先做完那两个再评估。

## 坑

**只看命中率不看假命中率。** 命中率好看的配置，假命中率可能高得吓人。

**cache key 不带用户维度。** 直接变成越权通道，而且不报错。

**在时效性内容上用。** 昨天的答案今天可能已经错了，而缓存不知道。

**跳过前缀缓存直接上语义缓存。** 前者无损、后者有损，顺序反了。

**等线上出事才发现假命中。** 这类问题在监控里几乎不可见——用户拿到了一个看起来合理的错误答案。
