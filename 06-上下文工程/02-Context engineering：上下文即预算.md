上下文窗口不是仓库，是预算。每一段塞进去的东西都在挤掉别的东西，而且塞得越满，模型用得越差。

## 一句话

context engineering 要回答的是**「这一刻窗口里该放什么」**——什么该驱逐、什么该压缩、什么该挪到外部存储；答案不是「能塞多少塞多少」。

## 原理

### 窗口里有哪些竞争者

![[上下文预算与衰减.excalidraw.md|700]]

![[上下文的零和分配.excalidraw.md|700]]

一个典型 agent 的窗口里同时住着：系统提示与工具定义、长期记忆、检索到的材料、对话历史、本轮输入，还要给输出留位置。

**它们是零和的。** 多召回 5 篇文档，就得少留几轮对话历史。这个取舍每一轮都在发生，只是多数系统没有显式管理它——直到窗口满了才发现。

### 越长越差，而且不是线性的

这一点是全部工程动机的来源。

Chroma Research 把这个现象叫 **context rot**：随着会话变长，性能**非线性、不可预测**地下降。[NoLiMa](https://arxiv.org/abs/2502.05167)（Modarressi 等，慕尼黑大学与 Adobe Research，2025）实测：12 个被测模型里有 10 个，上下文到 32K 时掉到自己短上下文基线的**一半以下**——连 GPT-4o 都从 99.3% 掉到 69.7%。展开见 [[06-上下文衰减与长轮次退化]]。

> [!warning] 这不是「窗口不够大」的问题
> 信息全都还在窗口里，模型就是用不好。**有效表现会在技术上限之前很久就开始衰减**，根子在注意力架构本身，不是 token 数不够。
> 所以窗口从 128k 涨到 100 万，并不会让这个问题消失——它只是把悬崖往后挪了一点，见 [[07-位置编码与长度外推]]。

推论很直接：**塞得少而准，比塞得多而全，效果更好。** 这和「反正窗口够大，全塞进去」的直觉正好相反。

### 四个可调的杠杆

**一、压缩历史。** 对话历史是最容易膨胀的部分。做法是定期把旧的几轮总结成一段摘要，见 [[03-Compaction 与外部记忆文件]]。

**二、外置。** 不是每一轮都需要的东西挪到外部——文件、向量库、记忆系统，用时再取。这样窗口只放「这一刻真正需要的」，见 [[01-短期与长期记忆分层]]。

**三、按需检索而非全量塞。** 与其把整份文档塞进去，不如检索出相关的几段。这也是为什么检索质量直接决定上下文质量，见 [[06-检索评估两段式]]。

**四、子任务隔离。** 把独立的子任务交给独立的上下文去做，做完只回传结论。这是多 agent 架构最实在的价值——**不是「多个智能体协作」，是「每个子任务有自己干净的窗口」**，见 [[09-多 Agent 编排模式]]。

### 给每一段划预算

把上面几件事落成配置，就是给每一段定一个 token 上限：

```yaml
budget:
  total: 32000
  system_and_tools: 6000      # 静态，放最前，见 05-Prefix caching
  long_term_memory: 2000
  retrieved_docs:   9000      # 超了就减 top-k，不是截断
  history:          8000      # 超了触发 compaction
  current_input:    3000
  reserved_output:  4000
```

**关键在于超预算时的行为要显式定义**，而不是让它自然截断：

- 检索超了 → 减 top-k 或者提高相关度阈值
- 历史超了 → 触发压缩
- 输入超了 → 明确拒绝或者分段处理
- **永远不要静默截断**——那会悄悄丢掉最后一段，而最后一段往往是最重要的

### 顺序也是设计的一部分

同一批内容，摆放顺序会影响两件事：

**缓存命中率。** 静态内容放最前，动态内容放最后，见 [[05-Prefix caching]]。

**模型的注意力。** 序列开头和结尾的位置召回最好，中间最差。所以**把最关键的东西放在开头或结尾**，可有可无的放中间，见 [[01-Transformer 与 attention]] 里 attention sink 那一段。

### 怎么知道自己做得好不好

一个可执行的度量：**画出成功率随轮数的衰减曲线**。

- 横轴是对话轮数或累计 token 数
- 纵轴是任务成功率
- 加上 compaction 和外部记忆之后再画一次

两条曲线之间的差距，就是 context engineering 的收益。**没有这条曲线，你不知道自己的 agent 能撑几轮。**

## 动手做

- [ ] 统计当前系统里各段内容的实际 token 占比，看谁在膨胀
- [ ] 画一次成功率随轮数的衰减曲线，找出开始塌的那个点
- [ ] 给每一段定预算上限，并显式定义超预算时的行为
- [ ] 加上 compaction，重画衰减曲线，对比差距
- [ ] 把检索的 top-k 减半，看成功率掉多少——多数情况下掉得比想象中少
- [ ] 试一次子任务隔离，把一个独立步骤挪到单独的上下文里做

## 算学会了

- [ ] 把上下文当有限预算在分配，而不是「能塞多少塞多少」
- [ ] 知道 context rot 是非线性的，且不靠更大的窗口解决
- [ ] 每一段都有预算上限，超了有显式行为，绝不静默截断
- [ ] 有一条成功率随轮数的衰减曲线
- [ ] 会用顺序同时优化缓存命中和注意力分配

## 坑

**窗口大就全塞进去。** 塞得越满效果越差，而且成本还高。

**静默截断。** 悄悄丢掉的往往是最新、最相关的那一段，而且不报错。

**只在窗口满了才管。** 那时候已经晚了——衰减在远没满的时候就开始了。

**只压缩不外置。** 压缩会丢信息；能挪到外部的东西挪出去，比压缩更保真。

**没有衰减曲线。** 不知道自己的 agent 能撑几轮，就没法判断改进有没有效。
