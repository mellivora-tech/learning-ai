埋点这件事的残酷之处：缺一个字段，就有一类问题你永远查不出来——而且要等到出事那天才发现缺了它。

## 一句话

下面这份清单是从「查不出来的事故」倒推出来的，每一条都对应一类具体的排查场景。

## 原理

### 清单

| 字段 | 打在哪 | 缺了它查不了什么 |
| --- | --- | --- |
| `prompt_version` | 模型调用 | 「上周好好的，这周不行了」——是哪次改的提示词 |
| `tenant_id` | 全链路 | 是所有人都有问题，还是某个租户 |
| `user_id` | 全链路 | 同一个人是不是反复遇到 |
| `feature` / `workflow` | 全链路 | 成本和错误集中在哪个功能上 |
| `model` + 版本 | 模型调用 | provider 悄悄升级模型导致的行为漂移 |
| `cached_read` / `cached_write` | 模型调用 | 缓存命中率为什么塌了 |
| `input_tokens` / `output_tokens` | 模型调用 | 成本归因的基础 |
| `TTFT` / `TPOT` | 模型调用 | 慢在首字还是慢在吐字，见 [[01-Prefill vs Decode]] |
| `finish_reason` | 模型调用 | 是正常结束、被截断、还是触发了过滤 |
| `retry_count` | 全链路 | 有多少成本花在重试上 |
| 检索 `top_k_ids` + `scores` | 检索 | 当时到底召回了什么 |
| `tool_name` + 参数 + 结果 | 工具调用 | 参数错了还是工具本身错了 |
| `error_type` | 出错处 | 错误分类统计 |

### 几个特别容易漏的

**`prompt_version`。** 排查「什么时候开始变差的」时，这是唯一能把行为变化和一次具体改动对上的东西。没有它，你只能靠 git log 猜时间点。

版本号可以是提示词内容的哈希，好处是改了就自动变，不用记得手动加。

**`cached_read` / `cached_write`。** 缓存命中率应该是常规监控项，不是出事才查的东西。一个典型事故：有人在 system prompt 开头加了个时间戳，缓存命中率从 80% 掉到 0，成本翻几倍，而这件事在总成本曲线上要过几天才看得出来，见 [[04-Prompt caching]]。

**`finish_reason`。** 它区分「模型说完了」和「被 `max_tokens` 砍了」。截断的 JSON 解析失败会被记成「模型不听话」，实际是参数配小了——两种问题的修法完全不同，见 [[03-截断处理与 finish_reason]]。

**检索的 `top_k_ids` 和 `scores`。** 只记「召回了 5 篇」没用。事后要复现「当时给模型看的是哪 5 篇、分数多少」，才能判断是没召回还是召回了没用好，见 [[06-检索评估两段式]]。

**`retry_count`。** 重试的成本在 per-token 视图里完全隐形——它就是一次正常的调用。只有把重试次数打出来，才看得见有多少钱花在了反复尝试上，见 [[04-成本归因与每次成功任务成本]]。

### 埋点要在一个地方

字段散落在各处埋，一定会有的地方漏、有的地方名字写错。做法是**把模型调用、检索、工具调用各包一层**，字段在包装层里统一填：

```python
# 不要在每个调用点各写一遍
with llm_span(prompt_version=PV, feature="doc-qa", tenant=t) as sp:
    resp = client.chat(...)
    sp.record(resp)          # token 数、finish_reason、缓存命中一次性填齐
```

这样加一个新字段只改一处，也不会有人忘记填。同时字段名的常量收在这一层，GenAI 约定改了不影响业务代码，见 [[01-Trace 与 Span]]。

### 基数要控制

有些字段会让监控后端的时序数据爆炸——`user_id` 作为**指标标签**是灾难（几百万个不同的值），但作为 **trace 属性**没问题。

区分开：

- **指标标签**只放低基数的：`feature`、`model`、`tenant_id`（租户数可控的话）、`error_type`
- **高基数的**（`user_id`、`request_id`、提示词内容）只进 trace，靠 trace 检索去查

搞混的后果是监控系统先扛不住。

### 怎么验证清单是全的

一个可执行的检验：**列出你最近三个线上问题，逐个问「靠现有字段能不能定位」。**

不能的话，缺的那个字段就是下一个要加的。这比照着别人的清单抄有效得多——每个系统缺的东西不一样。

## 坑

**没有 `prompt_version`。** 「什么时候开始变差的」这个问题会永远查不清。

**不记 `finish_reason`。** 截断会被误诊成模型能力问题，然后花几周调提示词。

**检索只记数量不记 id。** 检索类问题基本失去可查性。

**把 `user_id` 当指标标签。** 时序数据库基数爆炸，监控系统先挂。

**在每个调用点各埋各的。** 一定会漏，而且漏的地方通常正是出事的地方。
