线上出了一个坏答案，用户把截图发给你。五分钟之内，你能不能定位到那一次具体调用，看到它检索了什么、用的哪版提示词、模型返回了什么？

## 一句话

一次请求是一棵树：检索、模型调用、工具执行各是一个节点；把这棵树完整记下来并能按任意维度检索，才谈得上排查。

## 原理

### Trace 和 Span 是什么

**Span** 是一次有始有终的操作，带名字、起止时间、一堆属性。**Trace** 是一次完整请求里所有 span 组成的树。

![[一次请求的 trace 层级.excalidraw.md|700]]

传统后端服务早就这么做了，LLM 应用的特殊之处在于**树更深、每个节点携带的信息更多**：一次对话可能包含多轮模型调用、若干次检索、几个工具执行，而每一步都可能是出问题的地方。

没有这棵树，你能拿到的只有「用户问了什么、系统答了什么」。中间发生的一切都是黑盒——而问题恰恰都在中间。

### 为什么要用 OTel 而不是自己写日志

自己往日志里打 JSON 当然也能跑，但会遇到三件事：

- **字段名各写各的**。这个服务叫 `model`，那个叫 `model_name`，查询时对不上
- **换后端要重写**。从自建 ELK 换到某个托管平台，埋点全得改
- **跨服务串不起来**。请求经过网关、编排层、检索服务，trace id 传不下去就断了

OpenTelemetry 解决的就是这三件事：统一的数据模型、统一的传播机制、后端可插拔。

它的 **GenAI 语义约定**进一步规定了 LLM 相关的字段该叫什么名字——`gen_ai.system`（哪家的模型）、`gen_ai.request.model`、token 计数这些。核心那几个在 2026 年已经算稳定，另外还有 `gen_ai.input.messages`、`gen_ai.output.messages`、`gen_ai.system_instructions` 等。

> [!warning] GenAI 约定至今仍是 pre-stable
> 截至 2026 年 6 月的 v1.42.0，`gen_ai.*` 被挪进了独立的约定仓库，但**整体仍是实验性的，没有 1.0**，字段名在版本之间还可能改。
> 所以：核心字段跟着约定走（换后端和工具时受益），**但别把业务逻辑硬编码在这些字段名上**。中间加一层自己的常量，约定改了只改一处。

### 一棵树上该有哪些节点

| span | 记什么 | 出问题时你会想看 |
| --- | --- | --- |
| 请求根节点 | 租户、用户、feature、总耗时 | 是谁、在用哪个功能 |
| 检索 | 查询、top-k 的**文档 id 与分数** | 到底召回了什么 |
| 重排 | 重排前后的顺序变化 | 重排帮了还是帮倒忙 |
| 模型调用 | 提示词版本、模型、token 数、TTFT、finish_reason | 模型看到了什么、为什么这么答 |
| 工具调用 | 工具名、参数、返回、重试次数 | 参数对不对、是不是重试了 |
| 修复循环 | 第几次、校验器报的什么错 | 有没有在反复自我修复 |

字段的完整清单见 [[02-必打字段清单]]。

### 采样：全量存不起，但不能乱采

trace 数据量很大，尤其是把提示词和输出都存下来的时候。但**均匀采样是错的**——出问题的请求本来就是少数，随机丢掉 99% 之后，需要排查的那次多半不在里面。

务实的策略：

- **错误和慢请求全量留**：`finish_reason` 异常、有重试、延迟超阈值、用户点了踩
- **正常请求按比例采**，用于看趋势
- **尾部采样**：等整个 trace 结束再决定留不留，这样才能按「这次请求出没出问题」来判断

最后一条是关键。头部采样在请求刚开始时就决定，那时候还不知道它会不会出问题。

### 提示词和输出要不要存

存下来排查最方便，但它们通常包含用户数据。取舍：

- **脱敏后存**，或者只存哈希用于比对
- **按租户配置**，敏感租户只存元数据
- **设短保留期**，比如 7 天，够排查就行
- 别忘了这批数据会进日志系统、备份和下游分析，合规范围要覆盖到，见 [[02-审计日志]] 和 [[01-数据驻留]]

### 判据只有一条

**出事之后，你能不能在五分钟内下钻到那一次具体调用？**

模拟一次：随便找一条线上的坏输出，只凭用户给的信息（时间、大致内容），看能不能在你的系统里定位到那次 trace，看到它检索了什么、用了哪版提示词。做不到就说明埋点还差东西。

## 动手做

- [ ] 接入 OTel，给一次完整请求打出根节点、检索、模型调用、工具调用四类 span
- [ ] 按 GenAI 语义约定命名核心字段，但在自己的代码里包一层常量
- [ ] 在检索 span 上记下 top-k 的**文档 id 和分数**，不只是命中数量
- [ ] 配置尾部采样：错误和慢请求全量、正常请求按比例
- [ ] 做一次演练：随便挑一条历史坏输出，计时看多久能定位到那次 trace
- [ ] 定一个提示词与输出的保留期，并确认它在合规范围内

## 算学会了

- [ ] 出事后能在五分钟内下钻到某一次具体调用
- [ ] 知道 GenAI 语义约定仍是 pre-stable，业务代码不硬编码字段名
- [ ] 采样策略是尾部的，错误请求不会被随机丢掉
- [ ] 检索 span 里记了文档 id 和分数，能复现当时召回了什么
- [ ] 清楚提示词与输出的存储范围和保留期

## 坑

**只记入口和出口。** 中间发生的一切才是问题所在，只记两头等于没记。

**均匀采样。** 需要排查的请求恰好是被丢掉的那些。

**检索只记命中数量。** 不记文档 id 和分数的话，事后无法复现「当时召回了什么」，检索类问题基本查不了。

**把字段名硬编码进业务逻辑。** GenAI 约定还在变，改一次就要全量改代码。

**存了提示词却没过合规。** 这批数据里有用户内容，进了日志系统就等于扩散了一份。
