账单上写着这个月花了三万。这个数字没有任何用处——它不告诉你钱花在哪个功能上、哪个租户身上，也不告诉你其中有多少是白花的。

## 一句话

把 per-token 视图换成「每次成功完成任务的成本」，重试、agent 循环、上下文膨胀这些隐形开销才会露出来。

## 原理

### 两种视图，差别在分母

![[两种成本视图.excalidraw.md|700]]

per-token 视图算的是**总花费**。它准确，但它把一次成功和一次失败后重试三遍当成同样的事——都是 token，都计费。

换个分母，问题就浮出来了：

$$
\text{每次成功任务成本} = \frac{\text{总花费}}{\text{成功完成的任务数}}
$$

**分母是「成功」，不是「调用」。** 一个任务失败三次才成功，四次调用的钱都算在这一次成功头上。于是那些隐形开销第一次有了名字。

### 哪些成本在 per-token 视图里隐形

| 隐形开销 | 长什么样 | 怎么现形 |
| --- | --- | --- |
| 重试 | 就是几次正常调用 | 打 `retry_count`，算重试占总花费的比例 |
| 修复循环 | 校验失败后反复让模型改 | 打修复轮次，见 [[02-修复循环（报错回灌）]] |
| Agent 空转 | 反复调工具但没进展 | 打步数，做无进展检测，见 [[02-终止条件]] |
| 上下文膨胀 | 每轮把历史全塞回去 | 看输入 token 随轮次的增长曲线 |
| 缓存失效 | 命中率悄悄归零 | 监控 `cached_read` 占比，见 [[04-Prompt caching]] |
| 用不完的能力 | 用大模型干小模型的活 | 换小一档跑 eval，看掉多少 |

这几项在总账单上就是「token 用得多」，只有换了分母或者按维度拆开才看得见。

### 按四个维度打标

要归因就得有标签。四个维度，各回答一个问题：

- **`feature`**——哪个功能在烧钱？可能某个边缘功能占了三成成本
- **`workflow`**——同一个功能里哪一步最贵？往往是某个 agent 环节
- **`tenant_id`**——哪个客户在亏？定价合不合理靠它判断
- **user journey**——一次完整的用户目标花多少钱？跨多次调用

这些标签要在 trace 上全链路带着走，见 [[02-必打字段清单]]。**打标这件事要在一开始做**，事后从日志里反推基本不可能。

### 一个典型的排查

「这个月成本涨了 40%，但请求数只涨了 10%。」

按维度拆下去：

1. 按 `feature` 拆 → 发现集中在文档问答
2. 看该 feature 的 `cached_read` 占比 → 从 78% 掉到 12%
3. 看 `prompt_version` → 两周前改过
4. 对比两版提示词 → 有人把动态的用户信息挪到了 system prompt 开头

**前缀一变，缓存全废。** 这类问题在总成本曲线上要过很久才看得出异常，但在「按 feature 拆的缓存命中率」这张图上是断崖。

### 成本和质量要一起看

单看成本会推着人往便宜的方向走，然后质量塌了没人知道。所以这两个指标必须成对出现：

| | 单位成本 | 成功率 |
| --- | --- | --- |
| 换小模型 | 降 | 可能降 |
| 加重试 | 升 | 升 |
| 缩短上下文 | 降 | 可能降 |
| 加缓存 | 降 | 不变 |

只有最后一行是纯赚。其余每一行都是取舍，**而「每次成功任务成本」这个指标本身就把两者揉在一起了**——成功率降了，分母变小，单位成本反而会升。这是它比 per-token 好用的另一个原因。

### 定期做一次归零复盘

每个季度问一遍：

- 成本占比最高的三个 feature，各自创造的价值配得上吗
- 重试和修复占总成本多少？降下来的空间在哪
- 有没有哪个租户的单位成本远高于均值？为什么
- 把主力模型换小一档，eval 掉多少？掉得不多的话，就是一直在为用不上的能力付钱，见 [[05-怎么给一个任务挑模型]]

最后一条是最容易发现大额浪费的地方。

## 动手做

- [ ] 在 trace 上打齐四个维度的标签：feature、workflow、tenant、journey
- [ ] 定义清楚什么算「成功完成一次任务」——这一步比想象中难，要和产品对齐
- [ ] 算出当前的每次成功任务成本，作为基线
- [ ] 拆出重试和修复循环占总成本的比例
- [ ] 按 feature 和 tenant 各拆一次，找出单位成本最高的那个
- [ ] 把主力模型换小一档跑 eval，算清楚「多付的钱买到了多少质量」

## 算学会了

- [ ] 报成本时报的是每次成功任务成本，不是每百万 token
- [ ] 能说出重试和修复占了总成本多少
- [ ] 能按 feature、租户拆开定位成本异常
- [ ] 成本和成功率成对看，不会只优化一边
- [ ] 知道自己在为哪些用不上的能力付钱

## 坑

**只看总账单。** 涨了 40% 也不知道涨在哪，只能猜。

**分母用调用数。** 那样重试会被算成「更多产出」，方向就反了。

**事后从日志反推归因。** 没有打标的历史数据基本无法归因，标签要一开始就打。

**只优化成本不看质量。** 换小模型省了钱，成功率掉了，实际单位成本反而升。

**忽略缓存命中率。** 它是最容易悄悄失效、也最容易修复的一项，值得放在日常看板上。
