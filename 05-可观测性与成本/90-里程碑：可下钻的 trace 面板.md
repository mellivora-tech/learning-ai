## 交付物

一个能通过「五分钟演练」的面板。具体是：

- 一条完整请求的 trace 树：根节点 + 检索 + 模型调用 + 工具调用，层级清楚
- [[02-必打字段清单]] 上的字段全部打齐，尤其 `prompt_version`、`cached_read`、`finish_reason`、检索的 `top_k_ids` 与 `scores`
- 尾部采样：错误与慢请求全量留，正常请求按比例
- 三条漂移曲线：输入分布、输出质量代理指标、检索平均分数，且都按 `feature` 和 `tenant_id` 拆开
- 一张成本看板，主指标是**每次成功任务成本**，能按 feature / 租户下钻
- 一次**计时演练**的记录：随便挑一条历史坏输出，从零开始定位到那次 trace，用时多久

最后一项是唯一能证明这个面板真的有用的证据。

## 做法

聚合口径有起步脚本，五个函数留空，填一个过一个：

```bash
python "_练习/05-可下钻的 trace 面板.py"
```

span 用固定的假数据。**练的是口径，因为这几处算错之后面板会一直显示一个好看且错误的数字**，且没有任何东西会提醒你。

| 关 | 要填 | 谁当裁判 |
| --- | --- | --- |
| 1 | `build_tree` | 父 span 不在列表里时，孤儿不能丢——丢了面板会少一整棵子树 |
| 2 | `subtree_cost` | 各子树成本之和必须等于整树，不等就是有 span 算了两次 |
| 3 | `cost_per_success` | 成功率掉到 60% 时，按调用算纹丝不动、按成功任务算必须涨六成 |
| 4 | `should_keep` | 100 条里 5 条错误必须**全部**留下——头部采样就是这样把错误率「优化」掉的 |
| 5 | `check_metric_labels` | `user_id`、`trace_id` 不许进指标维度 |

五关都过之后脚本会打印一棵带成本占比的 span 树，以及三档成功率下两种成本口径的对照。

然后是接真 OTel 的那一半：

1. 接入 OTel，四类 span 先打通，见 [[01-Trace 与 Span]]
2. 把埋点收进包装层，字段统一在那里填，见 [[02-必打字段清单]]
3. `prompt_version` 用提示词内容的哈希，避免忘记更新
4. 配尾部采样，确认错误请求不会被随机丢掉
5. 建三条漂移曲线，全部按 feature 和 tenant 拆，见 [[03-漂移监控三条线]]
6. 定义「成功完成一次任务」，算出每次成功任务成本的基线，见 [[04-成本归因与每次成功任务成本]]
7. 做演练：找一条坏输出，计时定位
8. 做一次注入实验：故意往索引里少灌一批文档，看哪条曲线先动、多久看得出来

## 复盘

- 演练用了多久？超过五分钟的话，卡在哪一步——是找不到那次请求，还是找到了但字段不够
- 缺的字段是哪几个？各自对应哪类查不了的问题
- 三条漂移曲线里，哪条对索引注入实验最敏感？多久才看得出来
- 重试和修复占了多少成本？这部分有多少是可以消除的
- 拆到 feature 和 tenant 之后，有没有发现全局指标掩盖的局部问题
