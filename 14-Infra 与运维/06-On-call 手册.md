凌晨三点被叫醒的人，需要的不是「系统架构文档」，而是一份告诉他「看这个、如果是这样就做那个」的清单。

## 一句话

LLM 系统的 on-call 手册要额外覆盖**质量类故障**——那类问题不报错、不触发传统告警，只是答案变差了。

## 原理

### 两类故障

| | 传统故障 | **质量故障** |
| --- | --- | --- |
| 表现 | 报错、超时、崩溃 | **一切正常，只是答案变差** |
| 发现方式 | 告警 | 用户投诉、漂移监控 |
| 例子 | OOM、下游挂了 | 缓存失效、索引腐化、模型更新 |

**第二列是 LLM 系统特有的**，传统的 on-call 手册完全不覆盖它，见 [[03-漂移监控三条线]]。

### 手册该长什么样

每个条目固定四段：

```markdown
## 症状：P95 TTFT 突然翻倍

**先看这三个**
1. 抢占次数是否上升 → [面板链接]
2. 请求长度分布是否变化 → [面板链接]
3. 有没有超长 prompt 涌入 → [查询语句]

**如果是抢占**
→ 调小 max_num_seqs（见 [配置位置]），观察 5 分钟
→ 仍不缓解则扩容

**如果是长度分布变了**
→ 查是哪个 feature/租户，可能是新功能上线
→ 必要时对该租户单独限流

**升级**
→ 15 分钟未缓解，联系 @xxx
```

**四段：先看什么、按情况怎么做、什么时候升级、找谁。** 不要写背景介绍，凌晨三点没人读。

### 必备的条目

传统那些（服务挂了、延迟高、错误率高）之外，LLM 系统要额外准备：

| 症状 | 先查什么 |
| --- | --- |
| **成本突然上涨** | 缓存命中率、平均 token、重试率，见 [[04-成本归因与每次成功任务成本]] |
| **答案质量下降** | 索引是否完整、模型版本、prompt 版本，见 [[03-漂移监控三条线]] |
| **检索召回变差** | 索引条目数、平均相似度、同步管道，见 [[05-Freshness 与 tombstone 删除传播]] |
| **JSON 解析失败率上涨** | `finish_reason` 分布，见 [[03-截断处理与 finish_reason]] |
| **P95 延迟翻倍** | 抢占次数、请求长度分布，见 [[06-驱逐与内存压力]] |
| **某个租户投诉** | 按租户拆各项指标，见 [[06-多租户隔离]] |
| **上游 provider 异常** | 熔断状态、降级链走到哪一级，见 [[04-降级链]] |

**前两行是最常被叫醒的**，也是传统手册完全没有的。

### 每个条目要有可点击的入口

手册里的「查一下缓存命中率」如果没有链接，值班的人要自己去翻面板、拼查询语句——凌晨三点这一步就足以让人放弃。

**每一条都要有**：面板直链、现成的查询语句、配置文件的具体路径、相关服务的 owner。

### 演练比文档重要

写完的手册不演练，等于没有。做法：

- **新人入职时按手册处理一次模拟故障**——顺便验证手册对新人可读
- **混沌测试时用手册应对**，见 [[05-故障降级与混沌测试]]
- **每次真实故障后更新手册**——这是最重要的一条

**判据：这次故障处理时，手册够用吗？** 不够就补。手册的质量直接反映在「平均恢复时间」上。

### 别只写「怎么修」

好的条目还要说清楚**什么时候不该修**：

- 「这个指标周一早高峰会自然升高，属正常」
- 「这类错误率在 0.5% 以下不用处理」
- 「重试自动会解决，观察 10 分钟再动手」

**误操作造成的故障不比原故障少**。明确「不用管」的边界，能避免值班的人在半夜做出错误的干预。

### 和可观测性的关系

手册的每一条都依赖对应的指标存在。写手册的过程会暴露出监控的缺口——「先查缓存命中率」如果发现根本没这个指标，那就是下一个要补的埋点，见 [[02-必打字段清单]]。

**所以写 on-call 手册是检验可观测性完整度的好方法**，比对着清单打勾有效。

## 动手做

- [ ] 按四段式写出七个必备条目
- [ ] 每条都补上面板直链和现成查询语句
- [ ] 写手册时记下「查不到这个指标」的地方，补埋点
- [ ] 让一个没参与开发的同事按手册处理一次模拟故障
- [ ] 明确写出每类症状的「不用管」边界
- [ ] 混沌测试时用手册应对，记录哪里不够用
- [ ] 定一条规则：每次真实故障后更新手册

## 算学会了

- [ ] 手册覆盖了质量类故障，不只是传统故障
- [ ] 每条都有可点击的入口，凌晨三点能直接用
- [ ] 明确写了「什么时候不用管」
- [ ] 有人按手册演练过，且手册对新人可读
- [ ] 每次故障后会更新手册

## 坑

**只覆盖传统故障。** 质量类问题不报错，是 LLM 系统的主要故障形态。

**写成架构文档。** 凌晨三点没人读背景介绍。

**没有可点击的入口。** 值班的人要自己拼查询语句，等于没写。

**不写「不用管」的边界。** 误操作造成的故障不比原故障少。

**写完不演练。** 真出事时才发现手册对不上实际。
