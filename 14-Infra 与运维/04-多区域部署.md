多区域通常是为了三件事之一：合规、延迟、容灾。这三个目标对架构的要求完全不同，混着做会得到一个都不满足的系统。

## 一句话

先确认你要的是**合规、延迟还是容灾**——合规要求数据不出区，延迟要求就近服务，容灾要求跨区冗余，三者的取舍互相冲突。

## 原理

### 三个动机，三套要求

| 动机 | 核心要求 | 代价 |
| --- | --- | --- |
| **合规** | 数据物理上不出某个区域 | 不能跨区做冗余、缓存也要分区 |
| **延迟** | 就近服务用户 | 每个区都要有完整能力，成本乘以区域数 |
| **容灾** | 一个区挂了另一个能顶 | 冗余容量闲置，或者接受降级 |

**合规和容灾是直接冲突的**：合规要求数据不出区，容灾要求跨区备份。这时候只能在每个区内部做冗余，见 [[01-数据驻留]]。

### GPU 资源的区域差异

和普通服务不同的一点：**GPU 在不同区域的可得性和价格差别很大**。

- 某些型号只在特定区域有
- 同型号的价格可能差几成
- 配额也是按区域给的

**所以「每个区都部署完整能力」在 GPU 场景下比 Web 服务贵得多**，见 [[06-硬件要多少钱]]。务实的做法通常是：

- **主区放完整能力**
- **次区只放延迟敏感的部分**（比如检索），推理仍然回主区
- 或者次区放小模型，复杂请求路由回主区，见 [[04-模型路由与级联]]

### 什么该跟着走，什么不该

多区域时要逐项决定数据放哪：

| 数据 | 跨区吗 |
| --- | --- |
| 模型权重 | **该**——它不是用户数据，各区一份 |
| 向量索引 | **看合规**——数据驻留要求下不能跨 |
| KV cache / 前缀缓存 | **不该跨区**——跨区延迟让缓存失去意义 |
| 用户会话状态 | 尽量粘在一个区，避免跨区读 |
| trace 与日志 | **看合规**，见 [[02-审计日志]] |
| 配置与 prompt 版本 | 该——要保证各区行为一致 |

**最后一条容易被忽略**：各区的 prompt 版本不一致，会导致同一个用户在不同区拿到不同质量的回答，而且极难排查，见 [[02-必打字段清单]]。

### 路由策略

按动机选：

- **合规优先**：按用户归属地强制路由，不允许跨区兜底
- **延迟优先**：就近路由 + 健康检查
- **容灾优先**：主备或多活，失败时切换

**注意跨区兜底和合规可能冲突**。如果某个区挂了，把请求转到另一个区意味着数据出区了——**这个行为必须在合规上被明确允许，否则宁可拒绝服务**。

### 一致性问题

多区域下最难的是保持行为一致：

- **模型版本要对齐**——各区跑不同版本是排查噩梦
- **prompt 和配置要同步**，且变更要原子
- **索引更新要传播到各区**，见 [[05-Freshness 与 tombstone 删除传播]]
- **eval 要在每个区各跑一遍**，见 [[02-回归测试与 CI 门禁]]

**最后一条最容易漏**：CI 只在一个区跑 eval，另一个区的配置漂了没人知道。

### 什么时候不该做多区域

多区域会让所有事情复杂几倍。不做的理由：

- 没有合规强制要求
- 用户集中在一个地理区域
- 流量规模不足以支撑多份容量
- 团队没有多区域运维经验

**默认单区，有明确理由再上多区。** 而最常见的明确理由是合规，不是延迟——对多数 LLM 应用，几十毫秒的网络延迟相对于秒级的推理时间可以忽略。

## 动手做

- [ ] 明确你做多区域是为了合规、延迟还是容灾
- [ ] 逐项决定每类数据跨不跨区，特别是索引和缓存
- [ ] 确认跨区兜底在合规上是否被允许
- [ ] 检查各区的模型版本、prompt 版本、配置是否一致
- [ ] 在每个区各跑一遍 eval，对比结果
- [ ] 算一次多区域的成本增量，看动机值不值这个价

## 算学会了

- [ ] 能说清自己做多区域的动机，且知道三个动机的要求互相冲突
- [ ] 缓存和会话不跨区，索引按合规决定
- [ ] 各区的模型和 prompt 版本严格对齐
- [ ] eval 在每个区都跑
- [ ] 知道对 LLM 应用来说延迟通常不是上多区域的充分理由

## 坑

**动机不明就上多区域。** 三个目标的要求冲突，会得到一个都不满足的系统。

**跨区共享缓存。** 跨区延迟让缓存失去意义，还可能违反数据驻留。

**各区 prompt 版本漂移。** 同一用户不同区拿到不同质量的回答，极难排查。

**eval 只在一个区跑。** 另一个区的配置漂了没人知道。

**跨区兜底不看合规。** 故障切换可能导致数据出区。
