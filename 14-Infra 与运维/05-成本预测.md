「下个季度要多少预算」——这个问题不能靠把当前账单乘个系数来回答，因为 LLM 成本的驱动因子不止流量一个。

## 一句话

成本 = 请求量 × 每次成功任务成本，而**后者会随上下文长度、重试率、缓存命中率变化**——只按请求量外推必然失准。

## 原理

### 分解成可预测的部分

$$
\text{月成本} = \text{请求量} \times \text{每次成功任务成本}
$$

其中后者要拆开，见 [[04-成本归因与每次成功任务成本]]：

$$
\text{每次成功成本} = \frac{(\text{输入 token} \times p_{in} + \text{输出 token} \times p_{out}) \times (1 + \text{重试率})}{\text{成功率}}
$$

**每一个因子都会独立变化**，所以预测要对每个分别建模，而不是把历史总额乘个增长系数。

### 那些会悄悄变的因子

| 因子 | 什么会让它变 |
| --- | --- |
| 平均输入 token | 检索 top-k 调大、上下文预算放宽、用户开始粘贴长文档 |
| 平均输出 token | 换成推理模型（涨几十倍），见 [[04-推理模型的成本与延迟曲线]] |
| **缓存命中率** | 有人改了 prompt 前缀，见 [[04-Prompt caching]] |
| 重试率 | 上游质量下降、schema 变复杂 |
| 成功率 | 模型更新、数据漂移，见 [[03-漂移监控三条线]] |

**缓存命中率那一条最典型**：一行时间戳让命中率从 80% 掉到 0，成本翻几倍，而请求量一点没变。

**所以成本预测的前提是这些因子都在监控里**，见 [[02-必打字段清单]]。

### 自建的成本模型不同

调 API 是按 token 线性计费，自建是**按卡时计费，和用量不成正比**：

| | API | 自建 |
| --- | --- | --- |
| 低负载 | 便宜 | **贵**（卡闲着也花钱） |
| 高负载 | 线性涨 | **边际成本接近零**（直到需要加卡） |
| 预测方法 | 按 token 量 | 按副本数 × 卡时单价 |

自建的预测其实是**容量预测**：需要几个副本、每个副本几张卡，见 [[01-GPU 容量规划]] 和 [[06-硬件要多少钱]]。

**混合部署时要分开建模**，别用一个公式套两种。

### 怎么做预测

一个够用的流程：

1. **拉历史数据**，按月分解出上面那几个因子
2. **识别趋势**：哪些因子在涨、涨多快
3. **叠加计划中的变化**：要上新功能吗、要换模型吗、要加检索量吗
4. **算三个情景**：保守、基准、激进
5. **设告警阈值**——实际超过基准情景 X% 时告警

**第 3 步最容易被跳过**，而它往往是最大的变量。「下季度上推理模型」这一条能让成本涨一个数量级。

### 别忘了非推理成本

预算里容易漏的：

- **embedding 与重排服务**——自建的话也要卡
- **索引存储**——向量库的存储和检索成本
- **训练/微调**——一次性但可能不小，见 [[06-硬件要多少钱]]
- **可观测性**——trace 数据量很大，存储和查询都要钱
- **开发测试环境**

**trace 那一项经常被低估**：如果存了完整的提示词和输出，数据量可能比业务数据还大，见 [[01-Trace 与 Span]]。

### 预算超支的应急顺序

超了怎么办，按见效速度排：

1. **降低缓存失效**——检查是不是有人改坏了 prompt 前缀
2. **收紧上下文预算**——减 top-k、缩短历史，见 [[02-Context engineering：上下文即预算]]
3. **限制输出长度**——输出比输入贵得多，见 [[01-Prefill vs Decode]]
4. **分档路由**——简单请求走小模型，见 [[04-模型路由与级联]]
5. **量化**——自建时，见 [[09-量化]]
6. **降级或限流**——最后手段，见 [[04-降级链]]

**前三条通常能立刻见效且不影响质量**，值得先查。

- [ ] 自建和调 API 分开建模

- [ ] 有一份按见效速度排的应急降本清单

## 坑

**按总账单乘增长系数。** 驱动因子不止流量一个。

**忽略缓存命中率。** 它悄悄归零能让成本翻几倍而请求量不变。

**用一个公式套自建和 API。** 两者的成本结构完全不同。

**漏掉 trace 存储。** 存了完整提示词的话，量可能比业务数据还大。

**不算计划中的变化。** 「下季度上推理模型」能让成本涨一个数量级。
