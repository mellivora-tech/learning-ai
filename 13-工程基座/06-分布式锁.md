两个 worker 同时拿到同一个任务，各自跑了一遍，发了两封邮件。第一反应是加锁——但多数时候有比锁更好的办法。

## 一句话

分布式锁很难做对（过期、续租、脑裂三个坑），所以顺序应该是：**先想能不能靠幂等或乐观并发绕过去，绕不过去再上锁**。

## 原理

### 什么时候真的需要

需要互斥的典型场景：

- 同一个任务被多个 worker 领走
- 同一个用户的记忆被并发写入，见 [[02-记忆写入策略]]
- 定时任务在多个实例上同时触发
- 同一份资源的读改写（余额、库存）

但注意——**上面每一条都有不用锁的解法**，见下面「先试这几招」。

### 锁的三个难点

**一、过期时间难定。** 设短了，任务还没跑完锁就没了，另一个 worker 进来，互斥失效；设长了，持锁进程崩溃后要等很久才能恢复。

**二、续租有竞态。** 为了解决上一条，通常做法是持锁期间定期续租。但续租请求本身可能超时——**这时候你不知道续租成没成功**，见 [[03-超时与背压]] 里那条超时语义。

**三、脑裂。** 进程 A 拿到锁，然后被 GC 暂停了 30 秒（或者网络分区）。锁过期，进程 B 拿到锁开始干活。这时候 A 醒过来，**它以为自己还持有锁**，两个进程同时在改同一份数据。

第三条是最难防的，因为它在应用层完全不可见——A 没有任何理由怀疑自己失去了锁。

标准解法是 **fencing token**：每次发锁附带一个单调递增的编号，写入时带上这个编号，存储层拒绝编号比已见过的更小的写入。A 醒来后带着旧编号去写，会被拒绝。

**但这要求存储层支持这个检查**——多数系统没做，所以脑裂问题在实践中通常是被忽略而不是被解决的。

### 先试这几招

**一、幂等。** 两个 worker 都跑一遍，但因为幂等，结果和跑一遍一样。**这是最省事的方案**，也是 [[07-幂等存储与去重]] 存在的理由。

**二、数据库的原子操作。** 用一条 SQL 完成「领取任务」：

```sql
UPDATE tasks SET status = 'running', worker = :me
WHERE id = :id AND status = 'pending'
```

`WHERE status = 'pending'` 保证只有一个 worker 能改成功，其他的影响行数为 0，直接放弃。**不需要任何外部锁**，而且和状态机天然契合，见 [[02-状态机]]。

**三、乐观并发。** 读的时候带版本号，写的时候检查版本没变。变了就重读重试。适合冲突不频繁的场景。

**四、按键分区。** 让同一个键的任务总是路由到同一个 worker（一致性哈希或者队列分片），从架构上消除并发。**这是最彻底的**——没有并发就不需要互斥。

**大多数「需要分布式锁」的场景，用上面四招之一就够了。**

### 真要用锁

选型上，Redis 的 `SET NX PX` 简单常用但在主从切换时有丢锁风险；etcd 和 ZooKeeper 基于共识协议，正确性更好但更重；数据库的行锁最简单，中小规模下够用且不用引新组件。

不管用哪个，几条必须做：

- **锁要有过期时间**，绝不用永久锁
- **只有持锁者能释放**（释放时校验持有者标识，避免误删别人的锁）
- **锁的粒度尽量小**，锁住一个任务 ID 而不是锁住整张表
- **持锁期间不做慢操作**——尤其别在持锁时调模型，那可能要几十秒

最后一条在 LLM 场景特别重要：**模型调用耗时长且方差大**，持锁调模型意味着锁要设很长的过期时间，前两个难点会同时放大。

正确的做法是：**用锁保护状态转换（毫秒级），不用锁保护整个任务执行（分钟级）。**

## 动手做

- [ ] 找出系统里所有「需要互斥」的地方，逐个判断能不能用幂等或原子更新绕过
- [ ] 用 `UPDATE ... WHERE status = 'pending'` 实现任务领取，验证只有一个 worker 成功
- [ ] 如果确实用了锁，检查有没有过期时间、释放时有没有校验持有者
- [ ] 模拟持锁进程被暂停（发 SIGSTOP），观察锁过期后发生什么
- [ ] 检查有没有在持锁期间调模型——有的话重构成「锁保护状态转换」
- [ ] 给一个关键写操作加 fencing token，验证旧编号的写入被拒绝

## 算学会了

- [ ] 遇到并发问题先想幂等和原子更新，锁是最后手段
- [ ] 能说出锁的三个难点，尤其能解释脑裂为什么难防
- [ ] 会用一条 SQL 的条件更新实现任务领取
- [ ] 用锁时有过期、有持有者校验、粒度小
- [ ] 绝不在持锁期间调模型

## 坑

**在持锁期间调模型。** 锁要设几十秒的过期时间，过期和续租的问题同时放大。

**永久锁。** 持锁进程崩了，那个资源就永远锁死了。

**释放锁不校验持有者。** A 的锁过期后 B 拿到了，A 醒来把 B 的锁删了。

**以为拿到锁就绝对安全。** 脑裂是真实存在的，关键写操作要有 fencing 或者幂等兜底。

**能不用锁的地方也上锁。** 引入了复杂度和单点，收益却是零。
