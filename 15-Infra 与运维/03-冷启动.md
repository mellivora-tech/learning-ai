一个 Web 服务冷启动几百毫秒。一个 LLM 推理实例可能要十几分钟——这个数量级差异改变了整个运维策略。

## 一句话

冷启动的大头是**加载几十 GB 权重**，所以优化方向是让权重离 GPU 更近、体积更小、或者干脆不让用户等它。

## 原理

![[冷启动的时间去哪了.excalidraw.md|700]]

### 时间花在哪

一次冷启动大致分几段：

| 阶段 | 典型耗时 | 能不能优化 |
| --- | --- | --- |
| 调度到节点、拉镜像 | 几十秒到几分钟 | **能**——预拉取、本地缓存 |
| **从存储加载权重** | **几分钟到十几分钟** | **能**——本地 NVMe、更小的模型 |
| 权重上显存、初始化引擎 | 几十秒 | 有限 |
| 编译 / 预热 kernel | 几十秒 | 能——预编译缓存 |
| 健康检查通过、接入流量 | 几秒 | — |

**第二段是绝对大头，而且它可以算出来，不用去查别人的经验值：**

$$
\text{加载耗时} \approx \frac{\text{权重字节数}}{\text{存储读取带宽}}
$$

代两组数进去就明白量级从哪来：

| 模型与精度 | 权重体积 | 对象存储 ≈1 GB/s | 本地 NVMe ≈5 GB/s |
| --- | --- | --- | --- |
| 8B BF16 | 16 GB | 约 16 秒 | 约 3 秒 |
| 70B BF16 | 140 GB | 约 2.3 分钟 | 约 28 秒 |
| 671B BF16 | 约 1.3 TB | 约 22 分钟 | 约 4.5 分钟 |

（带宽是量级示意，取决于你的存储类型、网络和并发读；**代自己实测的带宽进去才算数**。）

十几分钟这个量级不是玄学，是**几百 B 的模型撞上网络存储带宽**的必然结果。同样地，这张表也直接给出了优化方向——分子和分母各有一条路。

### 优化手段

按投入产出比排：

**一、权重放本地 NVMe。** 从对象存储或网络文件系统加载是最慢的路径。把权重预先同步到节点本地盘，能快几倍。代价是每个节点都要存一份。

**二、镜像预拉取。** 推理镜像动辄几个 GB，在节点上预热镜像缓存能省掉几分钟。

**三、模型更小。** 量化到 FP8 权重体积减半，加载时间也大致减半，见 [[09-量化]]。蒸馏出更小的模型收益更大，见 [[07-蒸馏]]。

**四、预编译与缓存。** 引擎的 kernel 编译、图捕获这些可以缓存下来复用。

把这几项叠起来，上面那个公式的分子和分母同时被改善：量化让分子减半，本地 NVMe 让分母涨几倍，两者相乘就是一个数量级。**中等规模的模型确实能压进一分钟以内**——但这需要专门的工程投入，不是配置几个参数就行。

**别照抄任何人的绝对数字，包括上面那张表。** 拿你自己的权重体积和实测存储带宽算一遍，那才是你的起点。

### 让用户不等它

优化之外，另一条路是把冷启动移出关键路径：

| 做法 | 说明 |
| --- | --- |
| **预热池** | 起好但不接流量的实例，需要时秒级接入 |
| **提前扩容** | 按预测而非按当前指标，见 [[02-自动扩缩容]] |
| **保留缓冲容量** | 常驻比实际需要多一点 |
| **队列削峰** | 请求先进队列，容量跟上再处理，见 [[01-异步任务队列]] |

**预热池是效果最直接的**，代价是空闲成本——池子里的实例占着卡但不干活。

池子多大取决于扩容的紧迫程度和你能接受的浪费。**一个务实的起点：能覆盖一次典型扩容步长的量。**

### 什么时候可以接受冷启动

不是所有场景都要优化它：

| 场景 | 能接受吗 |
| --- | --- |
| 交互式产品 | **不能**——用户等不了一分钟 |
| 异步批处理 | 能——反正是异步的，见 [[01-异步任务队列]] |
| 内部工具、低频使用 | 能，但要明确告知，见 [[06-降级 UX]] |
| 开发测试环境 | 能 |

**对能接受的场景，缩容到零能省很多钱**——这笔账怎么算见 [[02-自动扩缩容]]，关键变量是「流量有没有足够长的连续空闲窗口」，不是某个 RPS 阈值。

### 别忘了模型切换也是冷启动

多模型服务的场景下，切换模型 = 卸载旧权重 + 加载新权重，成本和冷启动一样。所以：

- **别频繁切换模型**——按模型分池比动态切换更实际
- **LoRA 适配器是例外**——几十 MB，切换很快，见 [[03-LoRA 与 QLoRA]]

**「一个基座 + 多个适配器」在多任务场景下的价值，很大一部分就在这里**——避免了反复的权重加载。

## 动手做

- [ ] 测一次完整冷启动，按阶段拆解耗时占比
- [ ] 把权重从网络存储改成本地 NVMe，测提升
- [ ] 实施镜像预拉取，测提升
- [ ] 量化后再测一次加载时间，验证和体积成正比
- [ ] 起一个预热池，测「需要时接入」的实际延迟
- [ ] 判断你的场景能不能接受冷启动，能的话算缩容到零省多少

## 算学会了

- [ ] 知道冷启动的大头是加载权重
- [ ] 权重放本地 NVMe、镜像预拉取这两条基础优化做了
- [ ] 有预热池或提前扩容策略
- [ ] 知道自己的场景能不能接受冷启动
- [ ] 知道模型切换等价于冷启动，而 LoRA 适配器不是

## 坑

**权重放网络存储。** 加载是最慢的一段，本地化收益最大。

**等指标到阈值才扩容。** 冷启动十几分钟，来不及。

**在交互式场景缩容到零。** 首个用户等一分钟，基本等于挂了。

**频繁动态切换模型。** 每次都是一次冷启动的代价。

**只优化不做预热池。** 优化到一分钟仍然太久，要把它移出关键路径。
