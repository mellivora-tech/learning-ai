Web 服务的扩缩容是解决过的问题。GPU 推理不是——因为它的冷启动以分钟计，而扩容信号往往来得太晚。

## 一句话

按**队列深度或等待时间**扩容，不按算力利用率；而冷启动的分钟级延迟意味着**必须提前扩**，等指标到阈值就来不及了。

## 原理

### 用什么指标触发

| 指标 | 好用吗 |
| --- | --- |
| 算力利用率 | **不好**——它到顶之前显存就 OOM 了，见 [[01-GPU 容量规划]] |
| 显存利用率 | 可以，但它到 95% 时已经在抢占了 |
| **队列深度** | **好**——领先指标 |
| **等待时间** | **最好**——直接对应用户感受 |
| 抢占次数 | 好——说明已经过载，见 [[06-驱逐与内存压力]] |

**推荐用等待时间当主指标**：队列深度 1000 在快系统里没事、在慢系统里是灾难，而「预计等待超过 X 秒」在任何系统里都说得通，见 [[03-超时与背压]]。

### 冷启动是核心矛盾

> [!warning] 一个新副本可能要十几分钟才能服务
> 起一个 LLM 实例的大头是加载权重，而这一段可以直接算：**权重字节数 ÷ 存储读取带宽**。几百 B 的模型撞上网络存储，光这一步就是十几分钟量级；8B 模型放本地 NVMe 则只要几秒。**先算出你自己的那个数**，见 [[03-冷启动]]。
>
> 经过优化（镜像预拉取、权重放本地 NVMe、缓存管理）能压到一分钟以内，但这需要专门的工程投入。
>
> **十几分钟意味着「等指标到阈值再扩容」必然来不及**——那时候用户已经等了十几分钟。

所以策略只能是：

- **提前扩**——按预测而不是按当前指标，比如按历史同时段流量
- **保留缓冲**——常驻比实际需要多一点的容量
- **预热池**——起好但不接流量的实例，需要时秒级接入
- **缩容要慢**——扩容快、缩容慢，避免抖动导致反复冷启动

### 缩容到零划不划算

serverless 式的「无流量就缩到零」对 GPU 推理常常不成立，但这笔账可以自己算，不用背经验值。缩到零省下的是**空闲时段的卡时费**，付出的是**每次从零启动时那批请求的等待**：

$$
\text{省下的} = \text{空闲时长} \times \text{卡时价}
\qquad
\text{付出的} = \text{冷启动次数} \times \text{冷启动时长} \times \text{受影响请求数} \times \text{每次等待的代价}
$$

**关键在最后那一项**，它决定了整个判断的走向：面向用户的交互式产品里，一次分钟级等待基本等于一次流失，代价高到怎么算都不划算；内部批处理工具里它接近零，于是缩到零几乎白赚。

所以真正的判据不是某个 RPS 数字，而是**两个问题**：

1. **流量有没有足够长的连续空闲窗口？** 空闲窗口短于冷启动时长，缩到零就是纯亏——刚停下就得重启。
2. **首个请求等几分钟，你的场景付得起吗？**

流量密集到副本几乎不会真正空闲下来时，缩到零自然就没意义了。**这个翻转点在哪儿取决于你的冷启动时长和流量形状，代进上面的式子算，别抄别人的 RPS 阈值**——他们的模型大小和存储带宽和你的不一样，见 [[03-冷启动]]。

低频场景（内部工具、离线批处理）可以放心缩到零，但要接受首个请求的分钟级延迟——**产品上必须明确告知**，见 [[06-降级 UX]]。

### 怎么压缩冷启动

按收益排：

| 做法 | 效果 |
| --- | --- |
| **镜像预拉取 / 本地缓存** | 省掉几 GB 的拉取时间 |
| **权重放本地 NVMe 而非网络存储** | 加载快几倍 |
| **预热池** | 把冷启动移出关键路径 |
| 更小的模型 | 加载时间和大小成正比，见 [[07-蒸馏]] |
| 量化 | 权重小一半，加载快一半，见 [[09-量化]] |

**前两条是最基础也最有效的**，而且不需要改架构。

### 缩容要小心正在跑的请求

GPU 推理的请求可能跑几分钟。缩容时直接杀实例会让这些请求全部失败。

正确做法：

1. **先从负载均衡摘掉**，不再接新请求
2. **等现有请求跑完**（设一个最长等待）
3. **超时未完成的转移或转人工**，见 [[03-升级到人与结构化中间状态]]
4. 然后才销毁

**这个优雅退出的窗口要按 P99 请求耗时设**，不是按平均。

### 多副本的路由也要管

扩出来的副本之间怎么分流量，会影响前缀缓存的命中率：

- **轮询**：简单，但同一个租户的请求分散到各副本，前缀缓存全部落空，见 [[05-Prefix caching]]
- **按前缀哈希路由**：同前缀的请求打到同一副本，命中率高
- **按租户路由**：兼顾隔离和命中率，见 [[06-多租户隔离]]

**默认的轮询会显著拉低缓存命中率**，这是扩容后成本不降反升的常见原因。

- [ ] 用等待时间或队列深度触发扩容，不用算力利用率

- [ ] 能说出自己系统的冷启动耗时构成

## 坑

**按算力利用率扩容。** 显存先 OOM，扩容来不及。

**等指标到阈值再扩。** 冷启动十几分钟，用户已经走了。

**缩容直接杀实例。** 正在跑的长请求全部失败。

**扩容后用轮询路由。** 前缀缓存命中率暴跌，成本不降反升。

**盲目追求缩容到零。** 交互式场景里一次分钟级冷启动的代价，通常远超省下的那点空闲卡时费。**先算再缩。**
