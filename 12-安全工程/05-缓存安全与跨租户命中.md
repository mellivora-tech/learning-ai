缓存是按「内容相同」来共享的，而它不知道内容属于谁。这个矛盾会以两种方式咬人：一种是直接给错人，另一种更隐蔽——**通过快慢泄漏信息**。

## 一句话

所有 cache key 必须包含租户与权限维度；而即便这样做了，**前缀缓存的命中与否仍然通过延迟差异泄漏信息**。

## 原理

### 第一类：直接跨租户命中

最直接的问题：cache key 只按内容算，两个租户的相同查询会命中同一份缓存。

涉及三种缓存：

| 缓存 | 风险 |
| --- | --- |
| **前缀缓存**（引擎侧） | 共享 KV cache 块，见 [[05-Prefix caching]] |
| **语义缓存**（应用侧） | 直接返回别人的答案，见 [[05-Semantic caching 与假命中]] |
| 检索结果缓存 | 返回别人有权、自己无权的文档 |

**修法都一样**：cache key 里加 `tenant_id`，涉及个人数据时再加 `user_id` 和权限范围。

```text
key = hash(tenant_id + auth_scope + normalized_content)
```

这不是优化，是正确性要求。**但它只解决了第一类。**

### 第二类：时序侧信道

> [!danger] 即便 key 分开了，快慢仍然泄漏信息
> 前缀缓存的机制是：命中的部分不用重算，所以**命中比不命中快**。这个延迟差异是可观测的，见 [[02-指标体系]] 里的 TTFT。
>
> 攻击者可以据此推断：**某段前缀是不是被别人请求过**。
>
> 有研究展示了更进一步的做法——通过**逐 token 观察命中与否**，增量地重建出另一个用户的请求内容。你猜一个 token，快 → 猜对了，慢 → 猜错了，一个个试出来。

这类攻击的前提是缓存**跨用户共享**。所以防御思路很清楚：

| 做法 | 效果 | 代价 |
| --- | --- | --- |
| **按租户分池** | 彻底消除跨租户共享 | 缓存命中率下降 |
| **按授权组选择性共享** | 只在明确授权的组内共享 | 实现复杂 |
| **时序混淆** | 注入随机延迟，掩盖快慢差异 | 延迟变差，用户体验受损 |
| **监控异常复用** | 发现可疑的共享模式再隔离 | 有研究称这样能保住较高的复用率 |

**高敏场景直接按租户分池。** 简单、彻底、可解释。代价是缓存命中率——但对处理敏感数据的系统，这个代价该付。

### 怎么判断自己需不需要在意

不是所有系统都要防这个：

| 场景 | 需要吗 |
| --- | --- |
| 单租户内部系统 | 不需要 |
| 多租户但内容都是公开的 | 通常不需要 |
| **多租户 + 各自的私有数据** | **需要** |
| 处理个人敏感信息 | **需要** |
| 有对抗性用户（比如开放注册的 SaaS） | **需要** |

判据：**你的用户里有没有动机去探测别人的内容？** 有，就要按租户分池。

### 缓存投毒

第三类风险：攻击者主动往缓存里塞内容，让别人命中。

前缀缓存不容易被投毒（它缓存的是自己请求的前缀），但**语义缓存可以**——攻击者构造一个和常见问题语义相近的查询，让系统缓存一个被污染的答案，后续别人问相似问题时就命中它。

防法：

- **只缓存通过校验的结果**，见 [[06-四层参数校验]]
- **缓存 key 带用户维度**——投毒只能毒自己
- **给缓存条目设短 TTL**，限制污染的持续时间
- **可疑内容不入缓存**——被安全过滤拦过的、置信度低的

### 别忘了监控

几个值得看的：

- **跨租户命中率**——理论上应该是 0，不是 0 就是有 bug
- **缓存命中率的分布**——某个租户命中率异常高，可能在探测
- **TTFT 的方差**——按租户拆开看，异常的快慢模式值得警惕

第一条应该做成**硬性断言**：一旦检测到跨租户命中就告警，见 [[03-漂移监控三条线]]。

## 动手做

- [ ] 审计所有缓存的 key 生成，确认都带了租户维度
- [ ] 做跨租户红队：用租户 A 的身份构造能命中租户 B 缓存的请求
- [ ] 测时序差异：同一段前缀，命中和不命中的 TTFT 差多少
- [ ] 判断你的系统需不需要按租户分池，需要的话实施并测命中率损失
- [ ] 语义缓存做一次投毒测试：能否让别人命中你构造的答案
- [ ] 加跨租户命中的监控告警，设为零容忍

## 算学会了

- [ ] 所有 cache key 都带租户与权限维度
- [ ] 知道前缀缓存存在 TTFT 时序侧信道，且能解释攻击原理
- [ ] 能判断自己的系统需不需要按租户分池
- [ ] 语义缓存做过投毒测试
- [ ] 跨租户命中率有监控且零容忍

## 坑

**cache key 只按内容算。** 直接跨租户泄漏，而且不报错。

**以为分了 key 就安全了。** 时序侧信道不看 key，看快慢。

**在高敏场景为了命中率共享缓存。** 省下的算力抵不上一次泄漏。

**语义缓存不做投毒防护。** 攻击者能主动污染别人会命中的条目。

**不监控跨租户命中。** 这个数应该恒为 0，不监控就发现不了实现 bug。
