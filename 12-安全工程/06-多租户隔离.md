多租户系统里，一个客户的问题必须只是他自己的问题。数据不能串、算力不能被独占、日志不能互相看见。

## 一句话

隔离要覆盖四个面——**数据、算力、缓存、日志**；漏掉任何一个，前面几个做得再好也白搭。

## 原理

### 四个面

| 面 | 怎么隔离 | 漏了会怎样 |
| --- | --- | --- |
| **数据** | 向量库命名空间 + 检索时过滤 | 看到别人的文档，见 [[04-权限过滤时机]] |
| **算力** | per-tenant 限流与配额 | 噪音邻居把别人饿死 |
| **缓存** | cache key 带租户维度 + 按需分池 | 跨租户命中，见 [[05-缓存安全与跨租户命中]] |
| **日志** | 脱敏 + 按租户分区 | 运维或分析链路上泄漏 |

**第四面最容易被忘。** 数据层做得再严，trace 里存了完整的提示词和输出，而 trace 系统对全公司开放——那就等于没隔离，见 [[01-Trace 与 Span]]。

### 数据隔离：命名空间优先

一个租户一个命名空间，而不是靠过滤条件区分。理由在 [[04-权限过滤时机]] 讲过：**命名空间写错是显性失败（查不到东西），过滤条件写漏是静默泄漏**。

租户量很大时（几万个）命名空间可能不现实，这时候退化成「共享索引 + 强制过滤」，但要：

- 过滤条件由框架统一注入，不允许业务代码自己拼
- 加断言：查询结果里出现别的租户 ID 就直接抛异常
- 定期跑跨租户红队测试

### 算力隔离：限什么

不只是 QPS，见 [[07-韧性组件]]：

| 维度 | 为什么 |
| --- | --- |
| QPS / 并发 | 基础 |
| **token 用量** | LLM 特有——超长上下文能用很少的请求吃光算力 |
| **成本** | 直接兜底，见 [[01-五类硬预算]] |
| 队列位置 | 防止一个租户占满队列，见 [[01-异步任务队列]] |
| GPU 时间 | 自建推理时，见 [[06-硬件要多少钱]] |

**token 那一维最容易漏。** 限了 QPS 但没限 token，一个租户用 100k 上下文的请求，几十个并发就能把 KV cache 吃光，触发全局抢占，所有租户的 P99 一起塌，见 [[06-驱逐与内存压力]]。

### 噪音邻居的三个层次

**一、公平调度。** 按租户轮询消费，或者加权公平队列。

**二、硬配额。** 每个租户有上限，超了直接拒绝而不是排队。

**三、物理隔离。** 大客户单独部署实例。成本高，但对某些合规要求是必须的。

多数系统做到第二层就够。**关键是配额要能实时生效**——事后对账发现超了没有意义，那时候别人已经被影响了。

### 日志与可观测性的隔离

trace 里通常存着提示词、检索到的文档、模型输出，见 [[02-必打字段清单]]。这些都是租户数据。

要做的：

- **按租户分区存储**，查询时强制带租户维度
- **敏感字段脱敏**——身份证、手机号、账号这类
- **按租户配置保留期**——有些客户要求更短
- **访问也要审计**——谁看了哪个租户的 trace，见 [[02-审计日志]]

**别忘了下游**：trace 会流进日志系统、数据仓库、告警平台、备份。**隔离要覆盖整条链路**，不只是源头。

### 一个容易忽略的点

**模型本身可能记住租户数据。** 如果你用租户 A 的数据做了微调，那个模型就不该服务租户 B——权重里可能编码了 A 的信息。

同理，用线上数据做训练集时要过隔离审查，见 [[06-用户信号如何变成 eval 与训练数据]]。

### 怎么验证

隔离必须有自动化测试，且接 CI：

- **跨租户检索**：A 的身份能否命中 B 的内容
- **跨租户缓存**：能否命中 B 的缓存
- **配额生效**：A 超配额时 B 是否不受影响
- **日志隔离**：A 的运维账号能否查到 B 的 trace
- **删除彻底性**：删除租户 A 之后，各处是否清干净，见 [[01-数据驻留]]

**这五条 critical 级零容忍**，见 [[03-对抗测试集]]。

## 坑

**只做数据隔离。** 算力、缓存、日志任何一面漏了都等于没隔离。

**只限 QPS 不限 token。** 超长上下文能用很少的请求吃光算力。

**忘了 trace 里的租户数据。** trace 系统全公司可见，等于泄漏。

**配额事后对账。** 发现超了的时候别人已经被影响了。

**用共享索引 + 过滤条件但不做断言。** 过滤写漏就是静默泄漏。
