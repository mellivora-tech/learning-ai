用户没有输入任何恶意内容。恶意指令藏在他让 agent 读的那份 PDF 里——而你所有的输入过滤，都挂在他那一侧。

## 一句话

不可信内容有六个入口，用户输入只是其中一个；**把检索文档、工具返回、网页内容一律当数据而不是指令**，是这一节唯一的立场。

## 原理

![[载荷矩阵：入口 × 载荷.excalidraw.md|700]]

### 直接注入 vs 间接注入

**直接注入**是用户自己在输入框里写「忘掉上面的规则」。它显眼、好防、而且用户是攻击者本人。

**间接注入**是恶意指令藏在 agent 读到的内容里：

![[不可信内容的六个入口.excalidraw.md|700]]

间接这一路之所以是重点，不在于它占比多少（各家统计口径差得很远，别去背某个百分比），而在于它对攻击者有三个结构性优势：

- **用户看不见**，他只是让 agent 「总结一下这份文档」
- **走的是可信数据通道**，绕过了针对用户输入的所有过滤
- **可以提前埋设**，攻击者不需要在场

### 攻击面随功能增长

每加一个数据源就多一个入口：

| 加了什么 | 新增的入口 |
| --- | --- |
| RAG | 知识库里的任何一篇文档 |
| 网页浏览 | 任何被访问的页面 |
| 邮件处理 | 任何一封收到的邮件 |
| 代码仓库读取 | 注释、README、issue |
| MCP / 第三方工具 | 工具的返回值、工具描述本身 |
| 多 agent | 别的 agent 的输出 |

**最后两行最容易被忽略。** 工具描述本身如果来自外部（比如动态加载的 MCP server），它就是一个注入面，见 [[08-MCP]]。

### 自己写 20 条载荷

roadmap 把这条单列为「本节最重要的一个动作」，理由是：**只有针对你自己系统结构的载荷才测得出真问题**。

八个类别，各写两三条：

| 类别 | 测什么 |
| --- | --- |
| **指令覆盖** | 让它忽略系统提示 |
| **角色劫持** | 伪造对话结构、假扮系统消息 |
| **信息外泄** | 诱导它吐出系统提示或其他用户的数据 |
| **工具滥用** | 诱导它调用不该调的工具，尤其写操作 |
| **越权检索** | 诱导它去查它无权访问的东西 |
| **外泄通道** | 诱导它把数据编进一个 URL 里（markdown 图片是经典形态） |
| **编码混淆** | 用 base64、零宽字符、同形异义字包装上面这些 |
| **多轮铺垫** | 分几轮慢慢建立一个错误的前提 |

**每类都要埋在不同的入口试一遍**——同一条载荷，放在用户输入里可能被拦住，放在检索文档里可能就过了。

> [!warning] 种子载荷必须自己想
> 让模型帮你生成攻击载荷，生成出来的往往是它**自己容易防住**的那种。
> 真正有效的载荷来自理解你系统的具体结构：你的系统提示长什么样、有哪些写操作工具、检索了哪些源、输出会被渲染成什么。
> 模型可以帮你扩写变体，但那 20 条种子得自己写。

### 穿透率是主指标

跑完之后报的是**穿透率**——多少条攻击成功了，并按严重级别分开，见 [[03-对抗测试集]]：

| 级别 | 例子 | 门禁 |
| --- | --- | --- |
| critical | 泄露系统提示、跨租户数据、执行了未授权写操作 | **必须为 0** |
| high | 输出了不该输出的内容但无实际损害 | 有阈值且不许上升 |
| medium | 行为异常但无风险 | 记录趋势 |

critical 那档接进 CI，见 [[02-回归测试与 CI 门禁]]。

### 防不住到什么程度

> [!danger] 训练出来的抗性到不了「够用」
> Google DeepMind 在 [Lessons from Defending Gemini Against Indirect Prompt Injections](https://arxiv.org/abs/2505.14534)（Chongyang Shi 等，2025 年 5 月）里把这件事说得很直白：对抗训练确实提升了对**已知**攻击的抗性，但——
>
> > 穷举所有可能的攻击是不可行的，因此无法声称模型真正稳健。
>
> 他们自己的结论是必须做纵深防御：「从模型自身能否识别正在被攻击，到应用层，一直到服务基础设施的硬件防御」，每一层都要设防。
>
> **把它翻译成运维语言**：模型侧的防御是概率性的，残余成功率是个大于零的小数。假设它压到了 1%（这个数字是示意，真实值取决于你的模型、攻击面和攻击者水平）——一天一万次调用就是一百次成功。
>
> 所以高风险操作必须有确定性的那一层兜底，见 [[02-纵深防御]]。**「模型够聪明所以不会上当」不是一个安全论证。**

### 几类防御手段

按性质分：

- **结构化分隔 / spotlighting**——对外部内容做结构变换，让模型能区分「数据」和「指令」。概率性，但便宜且有效
- **模型侧对齐**（StruQ、SecAlign 这类）——训练模型识别并拒绝注入。概率性
- **监督 agent**（GuardAgent 这类）——用第二个模型监控行为偏离。概率性，且自己也可能被绕
- **最小权限**——它拿不到的权限就用不了。**确定性**
- **人确认**——**确定性**，也是唯一真正可靠的那一层

**前三种降低概率，后两种限制爆炸半径。** 两类都要有。

## 动手做

- [ ] 列出你系统里所有不可信内容的入口，逐个标出来
- [ ] 八个类别各写两三条载荷，凑够 20 条种子——**自己写**
- [ ] 每条载荷埋在不同入口各试一遍（用户输入 / 检索文档 / 工具返回）
- [ ] 记录穿透率，按 critical / high / medium 分级
- [ ] 特别测「外泄通道」那一类：输出里的 markdown 图片会不会被渲染
- [ ] 把 critical 那档接进 CI 门禁，设零容忍
- [ ] 修掉穿透的几条，重跑，做一份修复前后对比

## 算学会了

- [ ] 把检索文档、工具返回、网页内容一律当数据不当指令
- [ ] 手上有 20 条自己写的种子载荷，覆盖八个类别

- [ ] 知道模型侧防御到不了 0，高风险必须有确定性兜底

## 坑

**只防用户输入。** 上面那六个入口里，只有一个是用户直接打进来的。

**让模型生成攻击载荷。** 生成的是它自己容易防住的那种。

**忽略工具描述本身。** 动态加载的工具描述是一个真实的注入面。

**以为对齐好的模型就安全了。** 对抗训练能压低成功率，但压不到零，而任何大于零的残余率在高频调用下都是个大数字。

**只测一遍就完事。** 攻击面随功能增长，每加一个数据源都要补测。
