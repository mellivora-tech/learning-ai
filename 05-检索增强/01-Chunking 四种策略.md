「chunk size 设多少」是个问错了的问题。该先问的是：这批文档长什么样，以及我用哪种方式检索。

## 一句话

切法和检索方式**必须一起选**——递归切分配混合检索，语义切分配纯向量；而实测里最朴素的那种反而经常赢。

## 原理

### 四种切法

![[四种切法.excalidraw.md|699]]

| 切法 | 怎么切 | 什么时候用 |
| --- | --- | --- |
| **① 定长 / 递归** | 按 token 数硬切，优先在段落、句子边界断开 | 默认起点 |
| **② 按结构** | 按标题层级、表格、列表边界切 | 文档结构规整时 |
| **③ parent-child** | 小块用来检索，命中后返回它所在的大块 | 需要「检索准 + 上下文全」 |
| **④ late chunking** | 先把整篇过 embedding 模型，再切向量 | 代词和跨段指代多时 |

### 朴素的那个经常赢

一个反直觉但有实测支撑的结论：**递归 512-token 切分在一项 7 种策略的对比里排第一（准确率 69%），而听起来更聪明的「语义切分」只有 54%。** 另一项研究发现 1024 token 附近的忠实度接近峰值。

原因大致是：语义切分依赖模型判断边界，而那个判断本身会出错，错了就把相关内容切散了；定长切分虽然会切断语义，但它**错得均匀且可预测**，配合重叠和重排能补回来。

**所以起点应该是递归切分**，别一上来就上复杂方案。复杂方案要用实测证明它比这个基线好。

### parent-child 解决的是什么

小块检索准（信息密度高、噪声少），大块上下文全（模型能看懂前后文）。parent-child 把两者分开：

- **索引小块**（比如 256 token）用于向量检索
- **返回大块**（比如它所在的那一节）给模型

代价是存储和实现复杂一点，收益是**同时拿到检索精度和上下文完整性**。这是很多生产系统的默认选择。

### late chunking 解决的是指代

普通切分的一个具体损失：

```text
第 3 段：「Qwen3-Embedding 在 MTEB 上排名靠前。」
第 4 段：「它的 0.6B 版本就超过了很多更大的模型。」
        ↑ 单独切出来之后，「它」指谁没人知道
```

**late chunking** 的做法是：先让长上下文 embedding 模型看完整篇、产出每个 token 的向量，**然后再按块聚合**。这样每个块的向量里已经带了全文语境，「它」的指代信息保住了。

实测在**代词和指代较多的文档**上能提升 10–12%。代价是需要长上下文的 embedding 模型，而且整篇一次编码的成本更高。

### contextual retrieval：性价比最高的一招

另一条路是在**切完之后、编码之前**，给每个块补一段上下文说明：

```text
原块：「营收增长了 3%。」
补上下文后：「本段出自 2026 年 Q2 财报中「云业务」一节，
             讨论的是华东区表现。营收增长了 3%。」
```

有研究报告这一招能把**检索失败率降低 49%**，**配合重排能降 67%**。

代价是索引时要给每个块调一次模型生成上下文——一次性成本，但对大语料不便宜。**不过这是索引期成本，不是查询期成本**，通常划算，见 [[04-成本归因与每次成功任务成本]]。

### 切法要和检索方式配对

这一条最容易被忽略：

| 切法 | 配什么检索 |
| --- | --- |
| 递归 / 定长 | **混合检索**（向量 + BM25） |
| 语义切分 | 纯向量 |
| parent-child | 混合检索，小块索引 |
| contextual retrieval | 混合检索 + 重排，收益最大 |

递归切分会切断语义，但 BM25 能靠关键词把它捞回来——**两者互补**。而语义切分本来就是按向量相似度分的边界，配纯向量更自洽，见 [[03-Hybrid search（dense + BM25 + RRF）]]。

**只调切法不调检索，等于只优化了一半。**

### 别忘了 embedding 模型的长度限制

块不能超过 embedding 模型的最大输入长度，超了会被静默截断，见 [[06-Embedding 与向量空间]]。这是选块大小的硬上限。

## 动手做

- [ ] 同一批语料做四版切分，固定其他变量，测 recall@10
- [ ] 先建递归 512 的基线，再让别的方案证明自己比它好
- [ ] 测块大小：256 / 512 / 1024 / 2048，画出 recall 曲线
- [ ] 加 20% 重叠再测一次，看能补回多少被切断的语义
- [ ] 挑一批代词密集的文档，单独测 late chunking 的提升
- [ ] 试一次 contextual retrieval，算清索引期成本和 recall 提升
- [ ] 每种切法分别配纯向量和混合检索各测一次，验证配对效应

## 算学会了

- [ ] 不再问「chunk size 设多少」，而是先看文档结构和检索方式
- [ ] 有递归切分的基线，复杂方案必须证明超过它
- [ ] 知道切法和检索方式要一起选
- [ ] 能说出 parent-child 和 late chunking 各解决什么具体问题
- [ ] 块大小不超过 embedding 模型的输入上限

## 坑

**一上来就用语义切分。** 实测里它输给最朴素的递归切分。

**只调切法不调检索。** 两者配对错了，切法再好也发挥不出来。

**块超过 embedding 模型上限。** 被静默截断，后半段等于不存在。

**不做基线对比。** 换了个复杂方案，说不清到底有没有变好。

**忽略索引期成本。** contextual retrieval 对大语料的索引成本不低，要先算。
