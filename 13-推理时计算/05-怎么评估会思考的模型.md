推理模型在榜单上分数亮眼。但那些分数是在「让它想到饱」的设置下跑出来的，而你线上给的是有限预算。

## 一句话

评估推理模型必须**把预算作为一个维度**——同一个模型在不同思考预算下是两个不同的系统，报分数不带预算等于没报。

## 原理

### 三个额外的维度

普通模型的评估看准确率就够，推理模型要多看三样：

| 维度 | 为什么 |
| --- | --- |
| **思考预算** | 同一模型不同预算，表现差很多 |
| **总 token 量** | 决定成本，见 [[04-推理模型的成本与延迟曲线]] |
| **延迟** | 决定能不能用在交互场景 |

**报「某模型 AIME 提升 20 个点」而不说预算，这个数字没有信息量。**

### 榜单的可比性问题

不同榜单对推理模型的处理规则不一样：

- 有的**允许想到饱**——测的是能力上限
- 有的**限制预算**——测的是给定成本下的表现
- 有的**不区分**，把推理和非推理模型混排

**规则不同，分数不可比**，见 [[04-排行榜怎么读]]。看到推理模型的高分，第一个问题应该是「它花了多少 token」。

### 该怎么自己测

把预算当成扫描维度：

```text
对每个候选模型：
  对每个预算档（关闭 / 低 / 中 / 高）：
    跑 golden set
    记录：准确率、平均总 token、P95 延迟、每次成功成本
```

产出的不是一个分数，而是一条**每个模型的成本-准确率曲线**。然后：

- 划一条成本上限，看谁在这条线下准确率最高
- 划一条延迟上限，同样看
- **两条线都满足的那个点，才是你的选择**

这和推理服务里的帕累托前沿是同一个思路，见 [[10-吞吐-延迟帕累托前沿]]。

### 别只测它擅长的

推理模型在数学和代码上强，但你的任务未必是这两类。要专门测：

| 测什么 | 为什么 |
| --- | --- |
| **简单任务** | 验证过度推理有没有让它变差 |
| **格式遵循** | 思考之后还记得输出格式吗，见 [[01-结构化输出三档]] |
| **工具调用** | 会不会想太久而忘了调工具 |
| **长上下文** | 思考本身也吃上下文预算 |
| **置信度校准** | 过度推理会损害校准，见 [[05-logprobs 与置信度]] |

**第一项经常被跳过**，而它恰恰是决定「要不要全量切换」的关键——如果简单任务上变差了，那就只能做分流而不是全量替换。

### 思考过程要不要评

两种思路：

**只评最终答案。** 简单、客观、和用户实际拿到的一致。**多数场景够用。**

**也评推理过程。** 能发现「答案对但推理错」的情况——那种模型碰巧蒙对了，换个输入就不行。代价是要人工或者用 judge 评过程，成本高，见 [[04-Judge 校准]]。

**建议：日常只评答案，定期抽样评过程。** 后者用来发现「表面成功率虚高」的问题。

### 一个容易漏的失败模式

推理模型有个特有的失败：**想得很好，但最后一步没执行**。

比如它在思考里正确地推导出「应该调用 refund_order 工具」，然后在可见输出里只是描述了一遍这个结论，没真的发起调用。

**只看最终答案的评估抓不到这类问题**，要专门测工具调用的触发率。这和结构化约束抑制工具调用是同一类现象，见 [[01-结构化输出三档]]。

## 动手做

- [ ] 按预算档扫描，为每个候选模型画成本-准确率曲线
- [ ] 划成本上限和延迟上限，找出满足两者的最优点
- [ ] 专门测简单任务，验证过度推理有没有让它变差
- [ ] 测格式遵循和工具调用触发率
- [ ] 抽样评推理过程，找出「答案对但推理错」的比例
- [ ] 对比开关思考时的置信度校准曲线

## 算学会了

- [ ] 报推理模型的分数时一定带预算
- [ ] 产出的是成本-准确率曲线，不是单个分数
- [ ] 专门测过简单任务，知道要不要全量切换
- [ ] 测过工具调用触发率，能发现「想到了但没做」
- [ ] 日常评答案，定期抽样评过程

## 坑

**报分数不带预算。** 同一模型不同预算是两个系统。

**只测它擅长的数学和代码。** 你的任务未必是这两类。

**跳过简单任务的测试。** 那是决定「全量替换还是分流」的关键。

**只评最终答案。** 抓不到「答案对但推理错」和「想到了但没执行」。

**跨榜单比较推理模型。** 各家对预算的处理规则不同。
