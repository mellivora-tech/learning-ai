训练时砸算力提升能力，这条路的成本大家都知道。推理时砸算力也能提升能力——而且这笔钱是按次付的。

## 一句话

同一个模型，在推理时多花算力能换到更高的准确率；但这条曲线**会饱和，甚至会反转**，所以必须实测出自己任务的拐点。

## 原理

### 三种花法

| 做法 | 怎么做 | 特点 |
| --- | --- | --- |
| **想更久** | 单条推理链更长 | 最简单，见 [[01-CoT 与推理链]] |
| **想很多次** | 采样 N 条独立推理，投票或挑最好的 | 可并行，延迟不涨 |
| **搜索** | 树搜索，扩展有希望的分支 | 效果最好，实现最复杂 |

**第二种被低估了。** 生成 N 条候选可以并行发起，延迟基本不变，只有成本线性涨。对延迟敏感但预算宽松的场景，这比「想更久」划算得多。

选出最好那条的方法：

- **自一致性投票**——取多数答案，适合有唯一答案的任务
- **客观校验器**——测试跑通、schema 合规，见 [[01-Harness engineering]]
- **打分模型**——最贵也最不可靠

**有客观校验器的话，第二种花法的性价比很高**——生成 5 条，跑测试挑通过的那条。

### 曲线的形状

![[思考的隐形账单.excalidraw.md|700]]

典型形状是：**陡峭上升 → 收益递减 → 平台期 → 某些任务上反转下降**。

> [!warning] 逆向扩展是真实的
> 有研究专门记录了**增加测试时计算反而让准确率下降**的现象。也有工作质疑「简单地增加测试时计算就能持续提升」这个说法。
>
> 机制大致是：想得越久，越容易在中途引入一个错误的中间结论，然后基于它继续推。**推理链越长，累积出错的机会越多。**
>
> 所以不能默认「多给预算就更好」，**必须画出自己任务的曲线**。

### 怎么找拐点

一个可执行的流程：

1. 固定任务和模型
2. 思考预算按倍数扫：低 / 中 / 高 / 极高
3. 每档记录准确率、成本、P95 延迟
4. 画三条曲线
5. **找准确率提升开始明显放缓的那个点**——那就是拐点
6. 拐点之后的预算是在白花钱

**这条曲线要按任务类型分别画**，因为不同任务的拐点差别很大：简单分类可能在最低档就到顶了，复杂数学可能一直有收益。

### 和训练时扩展的关系

两条路在做同一件事——用算力换能力，但成本结构完全不同：

| | 训练时扩展 | 推理时扩展 |
| --- | --- | --- |
| 谁付钱 | 模型提供方，一次性 | **你，每次调用都付** |
| 效果 | 所有请求都受益 | 只有花了钱的那次受益 |
| 可控性 | 无——模型定型了 | **可以按请求调节** |

**最后一行是推理时扩展的价值所在**：你可以对重要的请求多花钱，对简单的少花，见 [[04-模型路由与级联]]。这个灵活性是训练时扩展给不了的。

### 什么时候值得

| 场景 | 值得吗 |
| --- | --- |
| 有客观校验器（代码、数学、结构化输出） | **非常值得**——生成多条挑对的 |
| 单次决策价值高（医疗、法务、金融） | 值得 |
| 高频低价值请求 | 不值得 |
| 延迟敏感的交互式场景 | 慎用，或者只用可并行的那种 |
| 任务本身简单 | 不值得，可能还有害 |

**判据是「一次答错的代价」**。代价高就值得多花；代价低就该走便宜路径。

## 动手做

- [ ] 挑一个任务，按倍数扫思考预算，画准确率-成本-延迟三条曲线
- [ ] 找出拐点，算出拐点之后每提升 1% 准确率要多花多少钱
- [ ] 按任务类型分别画一次，看拐点差多少
- [ ] 试「生成 N 条 + 客观校验器挑」，和「想更久」对比性价比
- [ ] 找一个逆向扩展的例子——通常在简单任务上能观察到
- [ ] 实现按请求价值分配预算的路由

## 算学会了

- [ ] 知道三种花法，且知道「生成多条」可并行、延迟不涨
- [ ] 画过自己任务的收益曲线，知道拐点在哪
- [ ] 知道逆向扩展存在，不默认多花就更好
- [ ] 用「一次答错的代价」判断值不值得多花
- [ ] 能按请求价值动态分配推理预算

## 坑

**默认给最高预算。** 拐点之后是纯浪费，某些任务上还会变差。

**只试「想更久」。** 「生成多条并行挑」在有校验器时性价比更高。

**不分任务类型画曲线。** 不同任务的拐点差好几倍。

**用打分模型挑候选。** 又贵又不可靠，有客观校验器就别用它。

**忽略延迟。** 想更久会显著拖长响应，交互式场景要慎用。
