「效果不行，微调一下吧」——这句话说出来的时候，八成情况下真正该做的是把检索修好。

## 一句话

判据只有一条：**缺的是知识还是行为**；缺知识走 RAG，缺行为才走微调——而多数人把前者误判成了后者。

## 原理

### 决策

![[四条路线怎么选.excalidraw.md|700]]

四条路线按**迭代成本从低到高**排：

| 路线 | 改什么 | 迭代成本 |
| --- | --- | --- |
| ① 提示词 + few-shot | 行为（弱） | 分钟级 |
| ② RAG | **知识** | 小时级 |
| ③ LoRA 微调 | **行为** | 天级 |
| ④ 蒸馏 | 成本与延迟 | 周级 |

**顺序不能反。** 每往下一级，迭代周期长一个量级，而且不可逆的投入更多。

### 为什么这个判断错得起代价特别大

原因在 [[08-预训练、后训练、对齐]] 里推过：**事实性知识在预训练的十几万亿 token 里长出来，几千条 SFT 样本改不动它**。想让模型知道你们的产品文档，微调是在用最贵的方式做它最不擅长的事——几周的数据和训练花下去，事实还是记不住，原有能力反而退了，见 [[06-灾难性遗忘]]。

而反过来判错的代价小得多：把行为问题误当知识问题去修检索，你会很快发现检索没问题，然后掉头。**两个方向的试错成本不对称，所以默认应该先怀疑是知识问题。**

误判的典型症状：

| 症状 | 真正的问题 | 该做什么 |
| --- | --- | --- |
| 「它不知道我们的产品」 | 知识缺失 | RAG |
| 「它引用了错的文档」 | 检索质量 | 修召回，见 [[06-检索评估两段式]] |
| 「它编造事实」 | 材料不足 + 不肯拒答 | 修检索 + 测拒答率 |
| **「它输出格式老是不对」** | **行为** | 约束解码 → 微调 |
| **「它的语气不符合品牌」** | **行为** | 微调 |
| **「它不按我们的流程走」** | **行为** | harness → 微调 |

**只有加粗那三行才该考虑微调。**

### 微调之前还有几步

即便确认是行为问题，微调也不是第一选择：

1. **提示词写清楚**——尤其是「不要做什么」
2. **few-shot 示范**——三五个例子往往顶得上一次微调
3. **约束解码**——格式问题直接从源头消掉，见 [[01-结构化输出三档]]
4. **harness**——加验证器和修复循环，见 [[01-Harness engineering]]
5. **然后才是微调**

**第 3、4 步经常被跳过。** 格式不对上约束解码，流程不对上 harness，这两样的成本比微调低一个量级。

### 什么时候微调真的值

| 场景 | 为什么微调合适 |
| --- | --- |
| 输出格式极其特殊，约束解码也搞不定 | 行为深度定制 |
| 需要稳定的语气/风格，few-shot 不稳 | 行为一致性 |
| 领域术语的理解偏差 | 这是介于知识和行为之间的灰区 |
| **要把大模型的能力压进小模型** | 蒸馏，见 [[07-蒸馏]] |
| few-shot 例子太长，占掉上下文预算 | 微调能把例子「内化」，省 token |

**最后一条被低估**：如果你的提示词里塞了 20 个 few-shot 例子，每次请求都在为它们付钱。微调之后这部分成本消失，长期算下来可能划算，见 [[04-成本归因与每次成功任务成本]]。

### 混着用才是常态

2026 年的共识做法不是四选一，而是组合：

```text
RAG 供事实  +  微调塑行为  +  harness 兜底
```

比如一个客服 agent：用 RAG 拿到最新的政策条款（知识），用微调保证回复的格式和语气（行为），用 harness 校验输出并在出错时修复。**三者各管一块，互不替代。**

### 决策前先量化

别凭感觉选。做法：

1. **先建基线**——当前方案的 eval 分数，见 [[01-Golden set]]
2. **归类失败**——把失败样本按「知识缺失 / 行为不对 / 检索没召回」分类
3. **看比例**——哪一类占大头，就往哪个方向投入

**第 2 步是关键。** 大多数团队跳过它，直接凭印象决定，然后在错误的方向上花几周。

## 动手做

- [ ] 把当前的失败样本按「知识 / 行为 / 检索」三类归类，统计比例
- [ ] 如果知识类占大头，先测 recall@10——多半是检索的问题
- [ ] 行为类问题先试约束解码和 harness，记录增量
- [ ] 算一次 few-shot 例子占的 token 成本，看内化之后能省多少
- [ ] 只有前面都试过还不行，才启动微调，并且先定好成功判据
- [ ] 设计一个 RAG + 微调 + harness 的组合方案，而不是四选一

## 算学会了

- [ ] 判据是「缺知识还是缺行为」，能当场分类一个具体问题
- [ ] 知道「我们需要微调」这类诉求里，多数其实是检索问题，且能说出两个方向的试错成本为什么不对称
- [ ] 微调之前会先试约束解码和 harness
- [ ] 会算 few-shot 例子的长期 token 成本
- [ ] 默认组合而非四选一

## 坑

**用微调灌事实。** 最贵的一条弯路，而且会把原有能力搞坏。

**跳过失败归类。** 凭印象选方向，在错误的地方花几周。

**跳过约束解码和 harness。** 这两样的成本比微调低一个量级。

**四选一。** RAG 供事实、微调塑行为、harness 兜底，三者互不替代。

**微调前没定成功判据。** 训完不知道算不算成功。
