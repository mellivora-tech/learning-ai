引擎侧的前缀缓存能省多少，取决于你的 prompt 长什么样。这一篇讲的是你这边该怎么摆，才能让那边有得省。

## 一句话

按**变化频率**把 prompt 分层排序：越不变的越靠前——这是一次性的排版工作，收益是长期的 TTFT 和成本下降。

## 原理

### 和前缀缓存的分工

引擎侧的机制（块怎么共享、怎么哈希）见 [[05-Prefix caching]]。这里只关心一件事：**命中的前提是前缀逐 token 完全相同**。

所以你能做的全部工作，就是**让尽可能长的前缀保持稳定**。

### 四层排序

```text
① 系统提示、工具定义、输出格式说明、few-shot 例子
   └ 永远不变，跨所有请求共享

② 租户配置、用户画像、会话级设定
   └ 一个会话内不变，同租户/同用户的请求共享

③ 检索到的文档
   └ 每次请求变，但同一轮内固定

④ 对话历史、本轮用户输入
   └ 一定变
```

**从上到下变得越来越勤，所以就该按这个顺序排。** 第 ① 层通常是最长的（工具定义动辄几千 token），把它保住，收益就拿到大半了。

### 那个最贵的错误

> [!warning] 一行时间戳，命中率归零
> ```
> 系统提示：你是一个客服助手。当前时间：2026-07-31 14:23:07
> ```
> 每个请求的第一个块都不同，**整段缓存全废**。prefill 成本翻几倍，TTFT 明显变差。
>
> 而这件事在总成本曲线上要过几天才看得出异常。只有「按 feature 拆的缓存命中率」那张图上才是断崖，见 [[04-成本归因与每次成功任务成本]]。

同类的还有：随机 ID、请求序号、A/B 实验标记、每次重新排序的工具列表（有些框架的工具顺序不稳定）。

**规则很简单：任何每次请求都会变的东西，必须在末尾。** 时间真的要给，就放在用户输入那一段里。

### 缓存命中率是常规指标

不是出事才查，是天天看。理由：

- 它会悄悄归零（有人改了一行 prompt）
- 归零之后成本上涨要过很久才在总账单上显形
- 而这是所有优化里**最便宜就能修好的一项**

监控做法见 [[02-必打字段清单]]，字段名通常是 `cached_read` / `cached_write` 之类。

### 自建和调 API 的差别

**自建**（vLLM 这类）：引擎自动做前缀匹配，你只要保证前缀稳定就行。省的是自己的算力。

**调 API**：各家规则不同——有的自动生效，有的要显式标记哪一段可缓存，有的有最短长度门槛，有的缓存有 TTL。命中的 token 通常按折扣价计费。

**选型和接入时要专门确认这套规则**，因为它直接影响成本模型，见 [[05-怎么给一个任务挑模型]]。

### 一个容易忽略的收益

除了省钱和降 TTFT，稳定的前缀还有个副作用：**输出更稳定**。

前缀一样意味着模型每次看到的开头完全相同，行为的方差会小一些。这对需要一致性的场景（结构化抽取、分类）有实际帮助，也让 eval 结果更可复现，见 [[02-回归测试与 CI 门禁]]。

## 动手做

- [ ] 把现有 prompt 按四层重排，记录重排前后的缓存命中率
- [ ] 做 A/B：时间戳放开头 vs 放结尾，对比 TTFT 和成本
- [ ] 把缓存命中率加进日常看板，按 feature 拆开
- [ ] review 所有 prompt 模板，找出还有哪几行会破坏前缀
- [ ] 确认工具定义的序列化顺序是稳定的（有些框架不保证）
- [ ] 如果调 API，把该 provider 的缓存规则（触发条件、TTL、计费）记下来

## 算学会了

- [ ] 能一眼指出 prompt 模板里哪一行把命中率打成了 0
- [ ] 按变化频率排序是写 prompt 的默认习惯
- [ ] 缓存命中率在日常看板上，按 feature 拆
- [ ] 知道自己用的 provider 的缓存规则
- [ ] 知道稳定前缀还能降低输出方差

## 坑

**动态内容放在前面。** 时间戳是最经典的一个，随机 ID 和实验标记同理。

**工具列表顺序不稳定。** 有些框架每次序列化的顺序不一样，前缀就断了，而且很难发现。

**只在开发环境验证。** 开发时 prompt 固定，命中率好看；线上有租户变量和实验分流，情况完全不同。

**不监控。** 它会悄悄失效，而成本曲线反应很慢。

**以为「差不多相同」就行。** 差一个空格都不算。
