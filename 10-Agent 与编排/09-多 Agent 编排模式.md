「多个智能体协作」听起来很先进。而按 Anthropic 公布的基准，多 agent 系统烧的 token 大约是普通对话的 15 倍、单 agent 的近 4 倍。

## 一句话

多 agent 的真实价值是**上下文隔离**，不是「协作」；而它的代价是成本翻几倍，所以能用流水线解决的就别上编排。

## 原理

### 三种模式

![[三种多 agent 模式.excalidraw.md|700]]

| 模式 | 怎么组织 | 适合 |
| --- | --- | --- |
| **流水线** | 步骤固定，依次执行 | 流程确定的任务 |
| **supervisor** | 中心协调者动态分派 | 需要动态路由、有序执行、解决冲突 |
| **swarm** | 路由逻辑长在任务里，agent 之间逐个交接 | 各自独立的工作负载 |

### 成本要先摆出来

这是最容易被忽略的一面。Anthropic 在[介绍自己的多 agent 研究系统](https://www.anthropic.com/engineering/multi-agent-research-system)（2025）时给了一组基准倍数：

| 形态 | token 用量（相对普通对话） |
| --- | --- |
| 普通对话 | 1× |
| 单 agent | 约 **4×** |
| 多 agent 系统 | 约 **15×** |

**从单 agent 到多 agent，是又一个近四倍。** 钱花在哪儿很清楚：协调者本身每次路由都是一次模型调用，每个子 agent 都要重新装一遍自己的上下文，结果回传还要再总结一次。

他们给出的判据也很直接：多 agent 只适合**任务价值高到付得起这份开销**的场景，且要求任务能真正并行、信息量超出单个上下文窗口、需要接很多复杂工具。反过来，**需要所有 agent 共享同一份上下文、或 agent 之间依赖很多的领域不适合**——他们点名了编码任务，因为真正可并行的部分比研究类任务少得多。

所以顺序应该是：

1. **先试单 agent**
2. **不行试流水线**（固定步骤，最省）
3. **还不行才上编排**

**多数「需要多 agent」的场景，其实是任务没拆清楚。**

### 真正的价值：上下文隔离

那多 agent 什么时候真的值？答案不是「分工协作」，而是**每个子任务有自己干净的窗口**。

回到 context rot：会话超过一定长度后准确率非线性下降，见 [[06-上下文衰减与长轮次退化]]。而一个复杂任务如果全在一个上下文里做，历史会迅速膨胀。

拆成子 agent 之后：

- 每个子任务从一个**干净的短上下文**开始
- 主上下文只保留子任务的**结论**，不保留过程
- 这直接对抗了衰减，见 [[02-Context engineering：上下文即预算]]

**所以判据是：这个子任务的中间过程，主流程需不需要看见？** 不需要 → 值得隔离出去。需要 → 隔离的意义就小了。

### supervisor 和 swarm 怎么选

| | supervisor | swarm |
| --- | --- | --- |
| 控制 | 中心化 | 分布式 |
| 路由 | 协调者决定 | 任务自带 |
| 冲突解决 | 协调者做 | 难 |
| 可观测性 | **好**——所有决策经过一个点 | 差——决策散落各处 |
| 成本 | 高（多一层协调调用） | 中 |
| 调试 | 相对容易 | 难 |

**工程上 supervisor 通常更实用**，因为可观测和可调试。swarm 的分布式控制在出问题时很难追——你不知道任务是怎么流到那个 agent 手里的。

### 预算必须能传递

多 agent 最常见的失控形态：每个子 agent 各自限 $0.2，但子 agent 的数量是动态的，乘起来等于没有上限。

所以预算必须**沿调用链传递并累加**，见 [[01-五类硬预算]]：

```text
父任务总预算 $0.50
  ├─ 分给子 A：$0.20（实际用了 $0.18）
  ├─ 分给子 B：从剩余的 $0.32 里分
  └─ 剩余额度随时可查
```

同理，步数、时间、工具调用次数也都要累加。

### 可观测性会变难

单 agent 的 trace 是一条线，多 agent 是一棵树。要保证：

- **trace 能跨 agent 串起来**——父子关系明确，见 [[01-Trace 与 Span]]
- **成本能归因到具体的子 agent**——哪个子任务最烧钱，见 [[04-成本归因与每次成功任务成本]]
- **失败能定位到层**——是子 agent 失败了，还是协调者路由错了

**没有这三样，多 agent 系统出问题时基本没法排查。**

### 安全上多了一个面

子 agent 之间传递的内容也是不可信通道——一个被注入的子 agent 可以污染传给其他 agent 的内容，见 [[01-间接提示注入与 20 条攻击载荷]]。

所以 agent 之间最好传**结构化数据而非自由文本**，思路和 dual-LLM 一致，见 [[03-隔离模式（dual-LLM）]]。

## 算学会了

- [ ] 上编排之前先试单 agent 和流水线
- [ ] 能说出 supervisor 与 swarm 的取舍，且知道前者更好调试

## 坑

**默认上多 agent。** 成本翻几倍，而多数场景单 agent 或流水线就够。

**预算不累加。** 子 agent 数量动态，各限一份等于没限。

**用 swarm 做需要调试的系统。** 决策散落各处，出问题追不回来。

**agent 之间传自由文本。** 注入可以在 agent 之间传播。

**trace 串不起来。** 多 agent 出问题时基本没法排查。
