简单请求用大模型是浪费，复杂请求用小模型是灾难。路由就是想同时避开这两件事——但它自己也有成本。

## 一句话

级联路由（小模型先试、校验不过再升级）只在**校验成本远低于重做成本**时成立；否则你付的是两次钱。

## 原理

![[模型级联路由.excalidraw.md|700]]

### 两种路由

**分类路由**——先判断请求类型，直接分派给合适的模型。

优点是只调一次模型。缺点是分类本身可能错，而且分类器要维护。

**级联路由**——小模型先试，校验不通过再升级。

![[级联路由.excalidraw.md|700]]

优点是不需要预判难度，用结果说话。缺点是失败的那次白花了。

### 级联成立的唯一条件

> [!warning] 校验成本必须远低于重做成本
> 级联的期望成本是：
> $$\text{成本} = C_{小} + C_{校验} + (1 - p) \times C_{大}$$
> 其中 $p$ 是小模型的通过率。
>
> 直接用大模型的成本是 $C_{大}$。所以级联划算的条件是：
> $$C_{小} + C_{校验} + (1-p) \times C_{大} < C_{大}$$
>
> **如果校验本身要调一次大模型（比如用 LLM judge 校验），$C_{校验} \approx C_{大}$，这个不等式基本不可能成立。**

所以级联适合的是**校验便宜**的任务：

| 任务 | 校验方式 | 校验成本 | 适合级联 |
| --- | --- | --- | --- |
| 结构化抽取 | schema + 业务规则 | 几乎为零 | **非常适合** |
| 代码生成 | 编译 + 单元测试 | 低 | **非常适合** |
| 数学计算 | 代入验算 | 低 | 适合 |
| 分类 | 置信度阈值，见 [[05-logprobs 与置信度]] | 低 | 适合 |
| 开放式写作 | LLM judge | **高** | **不适合** |

**最后一行是常见的误用。** 用大模型给小模型的作文打分，然后不合格就让大模型重写——不如一开始就让大模型写。

### 用置信度当廉价校验

没有客观校验器时，logprob 是个便宜的替代：小模型输出的平均 token 概率低于阈值就升级，见 [[05-logprobs 与置信度]]。

但要记住它的局限：**模型可以自信地错**，所以这条路只能筛掉「明显在犹豫」的那些。适合当补充，不适合当唯一判据。

### 分类路由的坑

分类路由看着更省（只调一次），但有两个隐藏成本：

**一、分类器要维护。** 业务变了、新增了请求类型，分类器就得更新。而它出错时的失败是静默的——简单请求被派给大模型只是浪费钱，**复杂请求被派给小模型会直接出错**。

**二、难度不总是可预判的。** 「帮我查一下订单」看着简单，但如果订单号是错的、需要多轮澄清，实际很难。**表面复杂度和实际难度经常不一致。**

所以分类路由更适合**类型边界清晰**的场景（比如按功能模块分），不适合按「难度」分。

### 路由本身要能被观测

| 指标 | 说明什么 |
| --- | --- |
| 各档的流量占比 | 路由是否符合预期 |
| **升级率** | 小模型的通过率，直接决定级联划不划算 |
| 各档的准确率 | 小模型档如果准确率也很高，说明可以更激进 |
| **端到端成本对比** | 和全用大模型比，到底省了多少 |

**最后一项必须实测。** 很多级联方案凭直觉觉得省钱，算完发现因为升级率太高，其实更贵了。

### 别忘了延迟

级联的坏情况是「小模型跑一遍 + 校验 + 大模型跑一遍」，延迟接近两倍。

对交互式场景这可能不可接受——**用户不关心你省了多少钱**。所以：

- 交互式场景慎用级联，或者只用超快的小模型当第一档
- 批处理场景放心用，延迟不敏感
- 也可以并行发起，谁先通过用谁（成本换延迟）

### 和降级链的区别

这两个容易混：

| | 触发 | 方向 |
| --- | --- | --- |
| **级联路由** | 主动策略，默认先试便宜的 | 便宜 → 贵 |
| **降级链** | 被动响应，出故障了 | 好 → 差，见 [[04-降级链]] |

级联是为了省钱，降级是为了还能用。**两者可以并存**：级联失败后升级到大模型，大模型也挂了才走降级链。

## 动手做

- [ ] 算一遍级联的期望成本，确认在你的通过率下真的划算
- [ ] 实现级联，统计升级率和端到端成本，和全用大模型对比
- [ ] 测延迟：级联的 P95 比直接用大模型高多少
- [ ] 用置信度阈值做一次廉价校验的级联，对比客观校验器的效果
- [ ] 如果用分类路由：统计「复杂请求被派给小模型」的比例
- [ ] 把小模型档的准确率单独拉出来看，判断能不能更激进

## 算学会了

- [ ] 能写出级联的期望成本公式，并判断自己的场景成不成立
- [ ] 知道用 LLM judge 当校验器的级联基本不划算
- [ ] 分得清级联路由和降级链
- [ ] 会算级联带来的延迟代价
- [ ] 端到端成本是实测的，不是估的

## 坑

**用 LLM judge 当级联的校验器。** 校验成本约等于重做成本，不等式不成立。

**只算成本不算延迟。** 交互式场景下用户体验会明显变差。

**按「难度」做分类路由。** 表面复杂度和实际难度经常不一致。

**不实测端到端成本。** 升级率一高，级联可能比直接用大模型还贵。

**把级联和降级混为一谈。** 一个是省钱策略，一个是故障响应。
