检索挂了，系统照常回答，只是这次是凭模型的记忆编的。用户看不出任何区别——这正是问题所在。

## 一句话

降级的时候要**明说**：告诉用户这次答案的依据变了，并给一条替代路径；悄悄给一个更差的答案，是在消耗信任。

## 原理

### 一条原则

**你从不悄悄给一个更差的答案。**

这句话是这一节的全部。它听起来像产品伦理，其实是工程要求——因为**用户是最后一道校验**。他知道系统在降级，就会自己去核实、会降低依赖、会在关键决策前多问一句。不告诉他，这道校验就没了。

### 三类降级各该怎么说

| 降级 | 怎么说 | 给什么替代路径 |
| --- | --- | --- |
| **检索挂了** | 「本次回答未使用知识库，可能不准确」 | 提供「稍后重试」或搜索入口 |
| **工具挂了** | 「无法自动完成 X，这是手动操作的步骤」 | 给出手动路径或工单入口 |
| **换了小模型** | 「当前处于高负载，回答可能不够详细」 | 提供「用完整模式重试」 |

**第二列比第一列更重要。** 只说「服务降级」而不给替代路径，用户除了干等没别的选择。

### 措辞要具体

对比：

```text
✗ 「服务暂时不可用，请稍后再试」
   —— 用户不知道什么不可用、能不能绕过

✓ 「知识库连接失败，以下回答基于模型的通用知识，
     未经过你们文档的核实。建议核对后使用。
     [重试] [直接搜索文档]」
   —— 知道降了什么、影响是什么、能做什么
```

**说清楚三件事**：降的是什么、对结果的影响、用户能做什么。

### 别过度声明

反过来也有问题：每次轻微降级都弹一个警告，用户会开始无视所有警告——**这时候真正严重的降级也被忽略了**。

分级：

| 严重程度 | 表现 |
| --- | --- |
| 影响正确性（检索挂了、数据源不全） | **必须明确声明**，视觉上要显眼 |
| 影响质量（换小模型、减少了检索量） | 轻量提示，不打断 |
| 影响性能（慢一点） | 通常不用说，除非慢得离谱 |

**只有第一档值得打断用户。**

### 有副作用的操作绝不能静默降级

这是红线。如果 agent 本该执行一个写操作但降级了：

- **必须明确告知没有执行**
- **必须给出手动执行的路径**
- **绝不能返回一个看起来成功的响应**

用户以为退款申请提交了，实际没提交——这类问题的后果远超一个不准确的回答，见 [[06-四层参数校验]]。

### 部分成功比全失败更难说清

降级经常不是全有或全无——八个字段抽出来六个、五份文件处理了三份、退款提交了但通知没发出去。

**这时候最糟的两种做法是：报成功（用户以为全做完了），或者报失败（用户不知道那六个字段其实是好的，全部重来）。**

正确的形态是把已完成的部分交出去，并说清楚缺什么：

```text
✗ 「处理失败，请重试」
✗ 「处理完成」

✓ 「已抽取 6 个字段。金额和开票日期没能识别（手写体），
     已标记为待确认。
     [查看已抽取的 6 项] [手动补这 2 项] [整单重试]」
```

**这和升级到人交出结构化中间状态是同一件事**，只是这次接手的是用户而不是运维，见 [[03-升级到人与结构化中间状态]]。判据也一样：**用户能不能从断点接着做，而不是从零开始。**

有副作用的部分尤其要说清哪些已经生效了——「退款已提交，但通知短信没发出去」和「退款失败」对用户的下一步动作完全不同。

### 恢复了也要说一声

降级说了、恢复不说，用户会一直以为这个功能就是这么差。

- 之前提示「本次回答未使用知识库」，恢复之后要给一个**「现在可以重试」的入口**，而不是等他下次自己碰运气
- 长时间降级恢复后，值得主动提示一次——尤其是那些因为降级而放弃了的用户
- **别默默恢复**：用户上一次拿到的是降级结果，他不知道那一次该不该重做

这一条的成本几乎为零，但它决定了用户对这个功能的长期印象是「偶尔会降级但会恢复」还是「不太行」。恢复机制本身怎么做见 [[04-降级链]]。

### 流式场景里怎么说

流式返回时降级可能发生在中途（工具调用失败了）。这时候不能改状态码，只能在流里发事件，见 [[04-流式与可中断 UX]]。

前端要能处理这类事件并在合适的位置插入提示，而不是等流结束再一次性弹窗——**那时候用户已经读完了那段不可靠的内容**。

### 降级声明也要打点

用户看到降级提示之后做了什么，是有价值的信号：

- **重试率**——高说明用户不接受这个降级
- **放弃率**——高说明降级路径基本没用
- **替代路径的使用率**——低说明那条路径没设计好

这些数据能回答一个关键问题：**这次降级到底算不算「还能用」**。见 [[06-用户信号如何变成 eval 与训练数据]]。

## 动手做

- [ ] 给三类降级各写一版用户可见的文案，包含「降了什么、影响、能做什么」
- [ ] 每类都配一条替代路径，验证那条路径真的可用
- [ ] 按严重程度分级，只让第一档打断用户
- [ ] 检查所有写操作：降级时会不会返回看起来成功的响应
- [ ] 造一个部分成功的场景，确认交出去的是「已完成的部分 + 缺什么」而不是笼统的成功或失败
- [ ] 降级恢复后给一个「现在可以重试」的入口，统计它的点击率
- [ ] 在流式场景中途触发降级，验证提示插在正确位置
- [ ] 统计降级提示后的重试率、放弃率、替代路径使用率

## 算学会了

- [ ] 从不悄悄给更差的答案
- [ ] 降级提示说清了降什么、影响什么、能做什么
- [ ] 按严重程度分级，不过度声明
- [ ] 写操作降级时绝不返回成功响应
- [ ] 用用户行为数据判断降级路径设计得好不好

## 坑

**静默降级。** 用户失去了核实的机会，而这本是最后一道校验。

**只说「服务不可用」。** 不给替代路径，用户只能干等。

**每次降级都弹窗。** 用户学会无视所有提示，严重的那次也被忽略。

**写操作降级返回成功。** 用户以为做了，实际没做，后果远超一个错误回答。

**流式场景等结束才提示。** 用户已经读完那段不可靠内容了。

**部分成功报成笼统的失败。** 已经做对的那部分被扔掉，用户从零重来。

**恢复了不告诉用户。** 他上一次拿的是降级结果，而他不知道那次该不该重做。
