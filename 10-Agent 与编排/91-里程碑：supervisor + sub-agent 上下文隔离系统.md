## 交付物

一个 supervisor 加子 agent 的系统，要能**证明上下文隔离真的带来了收益**——而不只是「跑通了」。

- 一个协调者 + 至少三个子 agent，每个子任务在**独立的上下文**里执行
- 子任务自带输入、成功判据、预算三要素，见 [[12-任务分解策略]]
- 预算沿调用链**传递并累加**，用嵌套场景验证过，见 [[01-五类硬预算]]
- trace 能跨 agent 串成一棵树，成本能归因到每个子 agent
- **两条衰减曲线**：单 agent 版 vs 隔离版的成功率随轮数变化
- **成本对比**：隔离版比单 agent 贵多少，值不值

## 做法

1. 挑一个多步骤的真实任务，先做单 agent 基线版
2. 画依赖图，找出能并行的分支，见 [[12-任务分解策略]]
3. 拆子任务，每个补上输入、成功判据、预算
4. 实现 supervisor（不用 swarm——可观测性差太多），见 [[09-多 Agent 编排模式]]
5. 实现预算传递累加，用嵌套子 agent 验证不会失效
6. 让 trace 跨 agent 串起来，成本归因到子 agent，见 [[01-Trace 与 Span]]
7. 两版各跑长会话，画衰减曲线，见 [[06-上下文衰减与长轮次退化]]
8. 把 agent 之间的传递改成结构化数据，测注入传播

## 复盘

- **成本涨了几倍？** 如果落在四到六倍那个区间，说明和公开的实测一致；远超的话，多半是协调者调用太频繁或者上下文没真隔离
- **衰减曲线往后挪了多少轮？** 这是上下文隔离的直接收益。挪得不多的话，说明子任务的输入里还带着太多历史
- 最烧钱的那个子 agent 是必要的吗？能不能用固定流程替代
- 并行了几个分支？延迟改善和理论值差多少
- 如果把 supervisor 换成人写死的流水线，成功率会掉多少？**掉得不多的话，这套编排就不值得**
