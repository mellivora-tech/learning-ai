下游抖了一下，你的重试逻辑把它彻底压死了。这不是下游的错——是你把一次小故障放大成了雪崩。

## 一句话

熔断器、带抖动的指数退避、per-tenant 限流——三个组件的共同目的是**不把下游的抖动放大成自己的故障**。

## 原理

![[熔断器三态.excalidraw.md|700]]

### 三个组件各管什么

| 组件 | 防什么 |
| --- | --- |
| **熔断器** | 对着已经挂了的下游反复重试 |
| **带抖动的指数退避** | 所有客户端同时重试，形成脉冲 |
| **per-tenant 限流** | 一个租户的异常流量拖垮所有人 |

### 熔断器

三个状态：

![[熔断器三态.svg|660]]

**闭合**：正常放行。
**断开**：直接失败，不再发请求——**给下游喘息的机会**，也让自己快速失败而不是排队等超时。
**半开**：放少量探测请求过去，成功就恢复。

图上四条边的颜色不是装饰，各是一类事：**红实线是故障真的发生了**，橙虚线是**系统自己发起的试探**（可能白试），绿实线是**恢复成功**，红虚线是**试探失败退回去**。**只有橙色那条是自动的**——没有它，断开状态会永远停在那儿，见 [[04-降级链]] 里的回程。

关键参数：

- **失败率阈值**——通常 50% 上下，别用绝对次数（低流量时会误触发）
- **统计窗口**——太短会抖，太长反应慢
- **冷却时间**——太短反复试探，太长恢复慢

> [!warning] LLM 场景下要区分失败类型
> 不是所有失败都该计入熔断：
> - **限流（429）** → 该计入，说明下游过载
> - **超时** → 该计入
> - **内容过滤** → **不该计入**，那是正常业务响应，见 [[03-截断处理与 finish_reason]]
> - **参数错误（400）** → 不该计入，是你的问题不是下游的
>
> 混在一起统计的话，一批格式错误的请求会把好好的下游熔断掉。

### 带抖动的指数退避

重试间隔按指数增长（1s、2s、4s、8s），**并且加随机抖动**：

```python
delay = min(base * 2**attempt, cap) * random.uniform(0.5, 1.5)
```

**抖动那一项不能省。** 没有它的话，同一时刻失败的一批客户端会在同一时刻重试，形成周期性脉冲，下游刚缓过来又被打趴——这叫惊群，而且它会自我维持。

另外要注意：

- **设上限**（cap），别退避到几分钟
- **总重试次数有限**，配合幂等，见 [[07-幂等性与故障注入]]
- **超时后的重试要特别小心**，见 [[03-超时与背压]]

### per-tenant 限流

多租户下必须按租户限流，否则一个大户能吃光所有配额，见 [[06-多租户隔离]]。

维度上通常要限几样：

- **QPS**——请求频率
- **并发数**——同时在跑的任务数
- **token / 成本**——这一条是 LLM 特有的，见 [[01-五类硬预算]]

**最后一条最重要也最容易漏。** 限了 QPS 但没限 token，一个租户用超长上下文一样能吃光你的算力。

### agent 场景的放大效应

普通服务里一次请求打一次下游，agent 里一次任务可能打几十次。所以：

- **重试是叠加的**——框架重试 × 模型重试 × 修复循环，见 [[07-幂等性与故障注入]]
- **熔断要在合适的层级**——熔断整个 provider 还是熔断某个工具，粒度不同影响面差很多
- **限流要看任务而非请求**——一个任务算一份配额，而不是它内部的几十次调用各算一份

**建议按工具/依赖分别设熔断器**，而不是全局一个。某个工具挂了不该影响别的工具。

### 三者要配合

单独看每个都简单，配合起来有几个交互点：

- **熔断断开时不该继续退避重试**——直接走降级链，见 [[04-降级链]]
- **限流拒绝不该计入熔断**——那是你自己限的，不是下游挂了
- **退避期间要占着预算吗**——建议算墙钟时间但不算 token 成本

这几处的处理不一致，会导致「明明熔断了还在重试」或者「限流触发导致误熔断」这类问题。

## 坑

**退避不加抖动。** 惊群效应会让下游反复被打趴。

**所有失败都计入熔断。** 一批参数错误能把好好的下游熔断掉。

**全局一个熔断器。** 一个工具挂了拖累所有工具。

**只限 QPS 不限 token。** 超长上下文的请求一样能吃光算力。

**熔断后还在重试。** 熔断的意义就是快速失败，继续重试等于白熔。
