问 agent「做完了吗」，它说做完了。它经常在没做完的时候这么说，也经常在做完之后继续折腾。

## 一句话

完成必须定义成一次**可观测的状态转换**——记录写进去了、工单关闭了、消息发出且有回执；测不出这个状态，agent 就没有终止条件。

## 原理

![[三种失控三道刹车.excalidraw.md|700]]

### 别问模型

![[终止条件.excalidraw.md|700]]

「模型说自己做完了」不是终止条件，因为：

- 它会在信息不全时草率收工
- 也会在任务其实已经完成后继续「优化」
- 而且它的判断随上下文长度衰减，见 [[06-上下文衰减与长轮次退化]]

**正确的做法是把完成定义成外部世界的可观测变化**：

| 任务 | 完成的定义 |
| --- | --- |
| 抽取发票 | 输出文件里有 N 条记录且通过 schema 校验 |
| 处理工单 | 工单状态变成 closed |
| 发送通知 | 消息发出且收到回执 |
| 修复代码 | 测试跑通 |

**这些都能被程序检测，不需要问模型。** 而且它们天然就是状态机里的一次转换，见 [[02-状态机]]。

如果你的任务**定义不出这样一个状态**，那它可能不适合交给 agent 自主完成——因为没人能判断它什么时候该停。

### 另外两种该停的信号

**无进展检测。** 连续 N 步之后，可观测状态没有任何变化：

- 没有新记录写入
- 没有新文件产生
- 工具调用的返回和上一轮相同
- 上下文里没有新增有效信息

实现上最简单的方式是给「进度」定义一个可比较的指纹（已完成条目数、状态字段的哈希），连续 N 步指纹不变就判定无进展。

**振荡检测。** A → B → A → B 这种来回横跳。典型形态：

- 反复调用同一个工具、拿到同一个错误
- 在两个方案之间反复切换
- 修改 → 校验失败 → 改回去 → 又失败

检测方法是维护最近 K 步的动作指纹，出现重复模式就判定振荡。

> [!warning] 线上的循环长什么样
> **同一个工具调用、同一类报错、成本线一直往上爬，直到有人注意到。**
> 它不报错、不崩溃、指标看起来都正常——只有成本曲线在涨。这就是为什么终止条件必须是主动检测，而不是等异常。

### 三种停法，对应三种后续

| 停的原因 | 后续 |
| --- | --- |
| **完成** | 返回结果 |
| **无进展 / 振荡** | 转人工，带上「卡在哪一步、试过什么」 |
| **预算耗尽** | 转人工，带上完整中间状态，见 [[01-五类硬预算]] |

第二种和第三种都要交出结构化中间状态，见 [[03-升级到人与结构化中间状态]]。**区别在于给人的提示不同**：无进展要说「它反复在做 X 但没效果」，预算耗尽要说「它做到了 Y，还剩 Z」。

### 别把无进展当失败

无进展的原因经常不在 agent：

- **任务本身就无解**——要找的信息根本不存在
- **工具坏了**——一直返回同一个错误
- **权限不够**——它想做的事被拦住了

所以无进展检测触发时，**要把「它在反复尝试什么」记下来**。这份记录往往直接指出真正的问题，见 [[02-必打字段清单]]。

### 和状态机的关系

前面几件事其实都是状态机的语言，见 [[02-状态机]]：

- 完成 = 转到终态
- 无进展 = 状态没变但转换在发生
- 振荡 = 在两个状态之间循环
- 预算耗尽 = 转到「待人工」

**没有显式状态机的 agent，这三种检测都很难做**——因为你没有一个明确的「状态」可以比较。这也是为什么工程基座那一段要排在 agent 之前。

## 算学会了

- [ ] 完成是可观测的状态转换，不问模型
- [ ] 有无进展和振荡两种检测，各自有明确的实现
- [ ] 三种停止对应三种不同的后续处理
- [ ] 无进展触发时会记录「它在反复尝试什么」
- [ ] 知道这三种检测都建立在显式状态机之上

## 坑

**靠模型自述完成。** 它会早停也会晚停，而且判断随上下文衰减。

**只有步数上限没有无进展检测。** agent 会安静地原地打转到步数用完，浪费全部预算。

**振荡检测只看工具名。** 参数不同的同一个工具调用可能是正常推进，要看动作指纹。

**无进展就直接判失败。** 原因可能是任务无解或工具坏了，要把尝试记录交出去。

**没有状态机就想做这些检测。** 没有可比较的状态，无进展和振荡都无从判断。
