约束解码能保证输出一定是合法 JSON。很多人因此以为结构化输出的问题解决了——它只解决了三分之一。

## 一句话

三档手段依次收紧**形式**保证：提示词、JSON mode、约束解码；但没有一档能保证**内容**是对的，所以业务校验永远省不掉。

## 原理

### 三档

![[结构化输出三档.excalidraw.md|678]]

**① 提示词加解析。** 在提示词里描述格式，输出之后自己 parse。失败形态五花八门：前后多了一段解释文字、markdown 代码块包裹、引号不配对、字段缺失、中文引号。

**② JSON mode。** 让模型保证输出是**语法合法**的 JSON。这解决了「能不能 parse」，但没解决「schema 对不对」——字段名拼错、类型不对、嵌套结构错，都还会发生。

**③ 约束解码。** 在采样时把所有会违反 schema 的 token 屏蔽掉，见 [[04-采样参数]]。输出**在形式上一定符合 schema**。自建的话，vLLM 会按情况选 Outlines 或 XGrammar 这类后端来做这件事。

### 关键在于它们各自不保证什么

| | 能 parse | 符合 schema | 内容正确 |
| --- | --- | --- | --- |
| 提示词 + 解析 | 多数时候 | 不保证 | 不保证 |
| JSON mode | **保证** | 不保证 | 不保证 |
| 约束解码 | **保证** | **保证** | **不保证** |

**最后一列永远是空的。** 约束解码保证 `{"amount": 1280.00}` 是合法的、类型是对的，但它不知道这个数字是不是真的从发票上读出来的。

所以约束解码不是银弹，它把失败从「格式错误」转移到了「内容错误」——**后者更难发现，因为它看起来完全正常**。

### 约束是有代价的

两个不那么显然的代价：

**一、可能损害任务本身。** 强行约束生成过程，会影响模型完成任务的能力。直觉上的原因是：模型原本可能想先推理再给结论，约束把它逼进了固定格式，推理的空间没了。

有实证研究发现了更具体的一种——**约束税**：结构化输出约束会**抑制工具调用**。开着严格 schema 约束时，开源模型发起工具调用的倾向明显下降。

对同时需要结构化输出和工具调用的 agent，这是个实打实的坑：**你以为在保证格式，实际上顺手关掉了它调工具的意愿。**

**二、性能开销。** 屏蔽 token 需要在每一步做语法检查，schema 复杂时开销不小。

### schema 的字段名是指令通道

一个很实用的发现：**约束解码下，schema 的字段命名本身在给模型下指令**。

```json
// 差
{"a": "string", "b": "number", "c": "string"}

// 好
{"invoice_number": "string", "total_amount_cny": "number", "issue_date_iso8601": "string"}
```

字段名写清楚，等于在格式约束里顺便把语义要求也说了。这比在提示词里额外描述一遍更有效，因为它就在生成的当下起作用。

**顺带把单位、格式、语言都编进字段名**——`total_amount_cny`、`issue_date_iso8601` 这种写法能省掉一堆后续校验。

### 该怎么选

| 场景 | 建议 |
| --- | --- |
| 调 API 且它支持严格模式 | 直接用，几乎没有理由不用 |
| 自建、schema 固定 | 约束解码 |
| **需要模型先推理再输出** | 让它先自由生成推理过程，**只对最终结构化部分做约束** |
| 同时要工具调用 | 谨慎，先实测约束税有多大 |
| schema 特别复杂 | 拆成多次小请求，见 [[04-降级链]] |

第三行是个常用技巧：把输出分成「思考部分」和「结果部分」，只约束后者。这样既保住了推理能力，又保证了结果可解析。

### 校验永远不能省

不管用哪一档，后面都要接业务校验，见 [[06-四层参数校验]]：

1. **语法**——约束解码已经保证了
2. **语义**——值域、单位、格式是否合理
3. **指称**——引用的 ID 真的存在吗
4. **授权**——当前用户有权这么做吗

**约束解码只覆盖第 1 层。** 后三层是它够不着的地方。

## 动手做

- [ ] 同一个 schema，三档各实现一遍，各跑 200 条真实输入
- [ ] 统计各自的**失败类型分布**，而不只是失败率——看失败是怎么从格式错转移到内容错的
- [ ] 把 schema 字段名从 `a/b/c` 改成语义清晰的名字，测准确率变化
- [ ] 如果系统同时用工具调用：开关约束解码各测一次工具调用触发率，量出你的约束税
- [ ] 试一次「先自由推理，只约束最终结构」的写法，对比全程约束的准确率
- [ ] 测约束解码带来的延迟开销，schema 复杂时尤其明显

## 算学会了

- [ ] 知道约束解码保证形式不保证语义，不会拿它当银弹
- [ ] 知道约束可能损害任务本身，尤其会抑制工具调用
- [ ] 会用有语义的字段名，把单位和格式编进去
- [ ] 会用「只约束最终部分」保住推理空间
- [ ] 三档之后一定还有业务校验

## 坑

**以为约束解码等于正确。** 它只保证形式，内容错误看起来完全正常，更难发现。

**同时用约束解码和工具调用不实测。** 约束税可能让工具调用直接哑火。

**字段名用无意义的缩写。** 白白浪费了一个免费的指令通道。

**全程约束推理型任务。** 模型没有推理空间，准确率会掉。

**只报失败率不看失败类型。** 三档之间真正的差别在失败形态，不在失败率数字。
