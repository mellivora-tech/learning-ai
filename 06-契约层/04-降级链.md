主路径失败之后，系统会做什么？多数系统的答案是「返回一个错误」或者更糟——「悄悄给一个更差的结果」。

## 一句话

降级要**分级、要打点、要能告警**；静默降级比直接失败更危险，因为用户拿到了一个看起来正常的坏答案。

## 原理

### 四级

![[降级链的四级.excalidraw.md|627]]

**① 简化 schema。** 去掉可选字段，只要核心的那几个。输出变短，模型压力变小，成功率通常明显回升。

**② 换更强的模型。** 贵，但更可能一次做对。注意换模型时 prompt 和 schema 要**验证过兼容**，别假设，见 [[05-故障降级与混沌测试]]。

**③ 拆成多次小请求。** 一次抽一个字段。成本高、延迟长，但成功率最高。

**④ 确定性兜底。** 用规则、正则、模板做一个不依赖模型的版本；实在不行就明确返回「无法处理」并转人工。

**顺序是按「代价从低到高」排的**，不是按「效果从好到坏」。

### 静默降级是最危险的

> [!danger] 用户拿到了更差的答案，而没人知道
> 检索挂了，系统不报错，直接让模型凭记忆回答——回答看起来很正常，但它没有依据。
> 换了个小模型，抽取准确率从 95% 掉到 78%——每一条单看都合理，只有汇总才看得出来。
>
> **这类问题不会出现在错误率里。** 它们表现为「质量慢慢变差」，而且要过很久才被发现，见 [[03-漂移监控三条线]]。

所以三条硬要求：

**一、每一级都要打点。** 记录降到了第几级、为什么降。

**二、每一级都要能告警。** 至少第 3、4 级触发时要有人知道。

**三、对用户可见。** 检索挂了就说「本次回答未使用知识库」，别装作正常，见 [[06-降级 UX]]。

### 什么时候不该降级

不是所有失败都该降级：

| 情况 | 该降级吗 |
| --- | --- |
| 模型输出格式错 | 先修复，修不好再降，见 [[02-修复循环（报错回灌）]] |
| 超时 | 降级，但注意超时语义，见 [[03-超时与背压]] |
| 检索无结果 | **不该降级成「凭记忆答」**，该明确说找不到 |
| 触发内容过滤 | **不该降级**，走合规路径 |
| 授权失败 | **绝不降级**，见 [[06-四层参数校验]] |
| 预算耗尽 | 转人工而不是降级，见 [[03-升级到人与结构化中间状态]] |

**后三行是红线。** 降级的边界是「用更差但仍然正确的方式完成」，不是「绕过检查」。

### 降级也要有预算

降级链本身会花钱：换更强的模型贵、拆多次请求更贵。所以：

- 整条链要有**总成本上限**，见 [[01-五类硬预算]]
- 降级触发率要监控——高的话说明主路径有问题，该修主路径而不是靠降级撑着
- 降级成本要单独归因，见 [[04-成本归因与每次成功任务成本]]

**降级触发率超过一成，就该回头看主路径。**

### 怎么测

降级路径最容易腐化——平时不走，出事才走，而出事的时候你不知道它还能不能用。

所以要做混沌测试：随机杀掉检索、工具、主模型，看系统实际走到了哪一级、输出是什么、告警有没有响，见 [[05-故障降级与混沌测试]]。

**没测过的降级路径等于没有。**

## 坑

**静默降级。** 用户拿到看起来正常的坏答案，而且不出现在错误率里。

**检索失败就让模型凭记忆答。** 这是把「找不到」变成了「编一个」，最危险的一种降级。

**降级绕过授权或内容检查。** 降级的边界是「更差但正确」，不是「绕过检查」。

**降级路径从不测试。** 平时不走，出事时发现它自己也坏了。

**用降级掩盖主路径的问题。** 触发率高说明该修主路径。
