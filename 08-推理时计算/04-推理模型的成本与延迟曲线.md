推理模型的标价可能和普通模型差不多。但它一次调用吐的 token 是几十倍，所以实际账单完全不是一回事。

## 一句话

推理模型的**单价**可能不高，但**单次调用的 token 量**高几十倍；比较成本时必须比「每次成功任务多少钱」，不是「每百万 token 多少钱」。

## 原理

### 成本结构完全不同

| | 普通模型 | 推理模型 |
| --- | --- | --- |
| 每次输出 token | 几百 | **一万到三万**（含思考） |
| 单价 | 基准 | 可能相近甚至更低 |
| **单次调用成本** | 基准 | **高几十倍** |
| 延迟 | 秒级 | 十几秒到分钟级 |

**第三行才是你实际付的钱。** 只看单价会得出「推理模型也不贵」的错误结论，见 [[06-硬件要多少钱]]。

正确的比较口径是**每次成功任务成本**，见 [[04-成本归因与每次成功任务成本]]：

$$
\text{每次成功成本} = \frac{\text{单价} \times \text{平均 token 量}}{\text{成功率}}
$$

推理模型的分子高几十倍，分母（成功率）可能高一些——**所以它划不划算，取决于成功率能提升多少**。

### 什么时候真的划算

一个可以直接算的判据：

```text
推理模型划算  ⟺  成功率提升的倍数  >  成本上涨的倍数
```

现实中成本上涨几十倍，而成功率很难提升几十倍——除非**普通模型在这个任务上基本做不对**。

所以典型的划算场景是：

| 场景 | 为什么 |
| --- | --- |
| 普通模型成功率很低（比如 30%） | 提升空间大 |
| 一次答错代价很高 | 重做或人工兜底更贵 |
| 低频、高价值的请求 | 总量小，单次贵得起 |
| 有客观校验器的复杂任务 | 能确认它真的做对了 |

**不划算的场景**：高频简单请求、延迟敏感的交互、普通模型成功率已经 90%+ 的任务。

### 延迟是另一半代价

思考 token 也要一个个生成，所以延迟直接跟着涨，见 [[01-Prefill vs Decode]]。

这对产品形态有硬约束：

- **要求首字 500ms 内**——推理模型基本没戏
- **可以等十几秒**——可以用，但要有明确的进度反馈，见 [[04-流式与可中断 UX]]
- **异步任务**——延迟不敏感，随便用，见 [[01-异步任务队列]]

**推理模型基本把交互式场景排除掉了**，除非你能接受「思考中」的等待界面。

### 简单任务上是纯负担

推理架构在复杂多步任务上更可靠，但**同样的架构在简单问题上是多余开销**——它还是会想一遍，只是想的内容毫无价值。

而且可能更差：过度推理会损害置信度校准，见 [[01-CoT 与推理链]]。

所以路由里必须有分流，见 [[04-模型路由与级联]]：

```text
简单请求 → 普通模型（或关掉思考）
复杂请求 → 推理模型
```

**这个分流的收益通常比任何单点优化都大**，因为它砍掉的是几十倍的成本差。

### 怎么做选型对比

不要只跑一个 benchmark 就下结论，要在自己的任务上量四个数：

| 指标 | 怎么测 |
| --- | --- |
| 成功率 | 用你的 golden set，见 [[01-Golden set]] |
| **平均总 token**（含思考） | 单独统计，别只看可见输出 |
| P95 延迟 | 端到端 |
| **每次成功任务成本** | 前三个算出来的 |

**最后一个才是决策依据。** 见 [[05-怎么给一个任务挑模型]]。

### 一个容易忽略的成本

推理模型的**输出长度方差很大**——同样的输入，有时想两千 token，有时想三万。这带来两个问题：

- **成本难预测**，预算规划要按 P95 而不是均值
- **KV cache 占用波动大**，自建时容量规划更难，见 [[03-KV cache 管理与显存测算]]

所以自建推理模型时，`max_tokens` 要设得比普通模型宽松，而这会进一步压低并发上限。

## 动手做

- [ ] 同一批任务用普通模型和推理模型各跑一次，记四个指标
- [ ] 单独统计思考 token，算出它和可见输出的比值
- [ ] 算两者的「每次成功任务成本」，看推理模型贵几倍
- [ ] 算成功率提升了几倍，和成本倍数比较
- [ ] 统计推理模型输出长度的分布，看方差有多大
- [ ] 实现简单/复杂分流，测总成本下降多少

## 算学会了

- [ ] 比成本时比「每次成功任务成本」，不比单价
- [ ] 能算出「成功率要提升几倍才划算」
- [ ] 知道推理模型基本排除了交互式场景
- [ ] 有简单/复杂的分流路由
- [ ] 预算按 P95 而非均值规划，因为输出长度方差大

## 坑

**只比每百万 token 单价。** 忽略了 token 量差几十倍。

**全量走推理模型。** 简单请求上是几十倍的浪费，还可能更差。

**在交互式场景用。** 十几秒的等待，用户以为系统挂了。

**按均值做预算。** 输出长度方差很大，会经常超支。

**成本估算不含思考 token。** 低估一到两个数量级。
