「让我一步步想」这句话曾经是个提示词技巧。现在它被训进了模型里，变成了一类模型的默认行为——以及账单上的大头。

## 一句话

CoT 的本质是**把推理过程当成中间输出**，让模型有更多步来算；它对多步任务有效，对简单任务是纯粹的浪费。

## 原理

### 为什么有效

模型每一步只能做有限的计算——一次前向的深度是固定的，见 [[01-Transformer 与 attention]]。

需要多步推导的问题，一次前向做不完。而 CoT 把中间结果**写进上下文**，下一步就能基于它继续算。**等于用输出长度换计算深度。**

所以它的适用范围很清楚：**中间结果对最终答案有用的任务**——数学、多步逻辑、代码调试。而分类、抽取这类一步到位的任务，中间过程没有价值。

### 从提示词技巧到模型能力

演进大致三阶段：

| 阶段 | 形态 |
| --- | --- |
| 提示词技巧 | 在 prompt 里写「让我们一步步思考」 |
| few-shot 示范 | 给几个带推理过程的例子 |
| **训进模型里** | 模型自己决定要不要想、想多久 |

第三阶段就是所谓的推理模型。它们通常用可自动校验的奖励训练出来——数学题对不对、代码跑不跑得过，见 [[08-预训练、后训练、对齐]]。

**这个转变的工程后果是：思考过程变成了模型的一部分，你能控制的只有「预算」而不是「怎么想」**，见 [[03-Thinking budget 控制]]。

### 思考过程要不要给用户看

三种做法，各有取舍：

| 做法 | 优点 | 缺点 |
| --- | --- | --- |
| 完全隐藏 | 界面干净 | 用户不知道它在干嘛，长等待很难受 |
| 显示摘要 | 有反馈，可控 | 要额外生成摘要 |
| 完整显示 | 透明、可审查 | 又长又乱，还可能暴露内部提示 |

**多数产品选摘要或者折叠显示。** 但要注意：思考内容可能包含它读到的敏感信息，展示前要过一遍过滤，见 [[02-纵深防御]]。

### 多轮对话里怎么处理

这是个具体的工程坑：**上一轮的思考过程要不要塞回下一轮？**

- **塞回去**：上下文膨胀极快，思考过程往往比答案长几十倍
- **不塞**：模型可能重复推导已经想过的东西

**多数模型的 chat template 已经规定了默认行为**——通常是不回灌，见 [[02-开源权重包里有什么]]。**先读模板再动手**，自己拼多轮时把思考块原样塞回去通常是错的。

### 它不总是有帮助

> [!warning] 想得更久有时反而更差
> 有研究发现了**逆向扩展**现象：在某些任务上，增加测试时计算量反而让准确率下降。
>
> 还有研究指出**过度推理会损害置信度校准**——模型想得越久，越倾向于对错误答案也表现得很自信，见 [[05-logprobs 与置信度]]。
>
> 所以「让它多想想」不是万能药。**要用你自己的 eval 验证，而不是默认它有帮助**，见 [[01-Golden set]]。

### 简单任务上是负担

对分类、抽取、格式转换这类任务，CoT 带来的是：

- **成本上涨几十倍**——见 [[04-推理模型的成本与延迟曲线]]
- **延迟明显变差**——首字之后还要等它想完
- **准确率未必提升**，甚至可能因为过度推理而下降

所以路由策略里应该有一条：**简单任务走非推理模型或关掉思考**，见 [[04-模型路由与级联]]。

## 动手做

- [ ] 同一批任务，开关 CoT 各跑一次，对比准确率、成本、延迟
- [ ] 按任务类型分组看差异——找出哪类任务上 CoT 真的有用
- [ ] 找一个 CoT 反而变差的任务类型（简单分类往往就是）
- [ ] 测多轮对话：思考块回灌与不回灌，看上下文增长和效果差异
- [ ] 读你用的模型的 chat template，确认它对思考块的默认处理
- [ ] 对比开关 CoT 时的置信度校准曲线，验证过度推理的影响

## 算学会了

- [ ] 能解释 CoT 为什么有效——用输出长度换计算深度
- [ ] 知道它对哪类任务无效甚至有害
- [ ] 多轮对话里按 chat template 的规定处理思考块
- [ ] 知道存在逆向扩展现象，不默认「想得多就更好」
- [ ] 路由里对简单任务关掉思考

## 坑

**默认开启 CoT。** 简单任务上成本涨几十倍而准确率未必提升。

**把上一轮的思考块原样塞回去。** 上下文暴涨，而且多数模板本来就不这么设计。

**完整展示思考过程不过滤。** 里面可能有它读到的敏感信息。

**以为想得越久越准。** 逆向扩展是真实存在的。

**不测就上。** CoT 的收益强烈依赖任务类型。
