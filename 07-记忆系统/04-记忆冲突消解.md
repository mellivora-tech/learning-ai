三月存的是「在北京」，七月存的是「在上海」。两条都在存档里，检索都能取到，模型该信哪个？

## 一句话

冲突不是异常，是记忆系统的常态；处理不了冲突的记忆系统，用得越久越不可信。

## 原理

![[冲突还是变更.excalidraw.md|700]]

### 冲突从哪来

| 来源 | 例子 |
| --- | --- |
| **事实变了** | 换城市、换公司、换技术栈 |
| **表述不同** | 「用 PG」和「用 PostgreSQL」 |
| **粒度不同** | 「喜欢简短」和「技术问题要详细」 |
| **模型推断错了** | 上次猜的偏好，这次用户明确否定 |
| **多来源** | 用户自己说的 vs 从工单里抽的 |

第三类最麻烦——它们不是真冲突，是**适用范围不同**，而系统很容易把它们当成互相矛盾。

### 先能检测到

冲突检测的前提是**记忆存成了结构化的键值**，而不是原文，见 [[02-记忆写入策略]]。有了 key 才谈得上「同一个键有两个值」。

三级检测：

1. **键完全相同、值不同** → 明确冲突
2. **键语义相近、值不同** → 可能冲突，要判断
3. **值语义相反** → 明确冲突（「喜欢 X」和「不喜欢 X」）

第二级需要模型判断，成本高一些，可以只在写入时做一次而不是每次检索都做。

### 消解策略

按可靠性排：

**一、时间优先（新的胜出）。** 最简单也最常用。适用于事实型和偏好型——人的情况会变，新的通常对。

**二、来源优先。** 用户明确表述 > 模型推断。这就是为什么写入时必须记置信度。

**三、显式确认。** 拿不准的时候直接问用户：「我记得你之前说在北京，现在是上海吗？」

第三条被严重低估。**一次确认换来的是长期正确的记忆**，而且用户通常不介意被问。

**四、保留两条，标注适用范围。** 针对上面那类「不是真冲突」的情况：

```json
{"key": "回答长度偏好", "value": "简短", "scope": "默认"}
{"key": "回答长度偏好", "value": "详细", "scope": "技术问题"}
```

强行二选一会丢信息。加一个 scope 字段比合并更保真。

### 别默默覆盖

> [!warning] 静默覆盖是最坏的选择
> 检测到冲突直接用新值覆盖旧值，看起来干净，实际上：
> - 覆盖错了没人知道（模型推断的把用户明说的覆盖掉了）
> - 无法回溯——用户问「你怎么知道我在上海」，答不上来
> - 反复横跳：A 会话说在北京、B 会话说在上海，两条记忆互相覆盖，行为变得不可预测
>
> **正确做法是保留历史，只标记哪条是当前有效的。** 存储成本几乎为零，换来的是可回溯和可解释。

### 冲突处理要能被观测

冲突频率本身是个有用的信号：

- **突然升高** → 可能是抽取逻辑出问题了，把不该存的存了
- **集中在某几个键** → 那些键的定义可能有歧义
- **同一用户反复冲突** → 可能是多人共用账号，或者场景切换了

所以要把冲突次数打进指标，见 [[02-必打字段清单]]。这也是 [[03-漂移监控三条线]] 里「输出质量」那条线可以覆盖的一项。

### 和遗忘的关系

有些「冲突」其实是**该过期的没过期**——三天前的工单状态和今天的冲突，正确的处理不是消解，是让旧的自动失效，见 [[05-遗忘与过期机制]]。

**先看能不能靠过期解决，再考虑冲突消解。** 前者是自动的，后者要花判断。

## 动手做

- [ ] 实现三级冲突检测（键相同、键相近、值相反）
- [ ] 加时间和来源两个消解规则，测一批构造的冲突对
- [ ] 把「静默覆盖」改成「保留历史 + 标记当前有效」，验证能回溯
- [ ] 对拿不准的冲突实现一次用户确认流程，统计用户的反应
- [ ] 给「适用范围不同」的那类加 scope 字段，避免误合并
- [ ] 把冲突次数打进指标，跑一周看分布

## 算学会了

- [ ] 知道冲突是常态不是异常
- [ ] 能区分「真冲突」和「适用范围不同」
- [ ] 不静默覆盖，保留历史并标记当前有效
- [ ] 拿不准时会主动向用户确认
- [ ] 会先检查是不是该过期没过期

## 坑

**静默覆盖。** 覆盖错了无人知晓，且无法回溯。

**把「范围不同」当成冲突。** 强行二选一会丢掉有用的细分偏好。

**只按时间不看来源。** 模型上周的推断会把用户上个月的明确表述覆盖掉。

**不监控冲突频率。** 它是抽取逻辑出问题的早期信号。

**该用过期解决的用冲突消解。** 状态类记忆本来就该自己失效。
