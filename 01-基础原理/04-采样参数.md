模型每一步给出的是十几万个候选词各自的分数。从这堆分数里挑一个出来，就是采样参数干的事——而多数人调它们靠玄学。

## 一句话

temperature 改的是分布的**陡峭程度**，top-k / top-p / min-p 改的是**留几个候选**；前者先生效，后者在它之后截断。

## 原理

### 从 logits 到一个字，完整链路

```text
logits [V]  →  ÷ temperature  →  softmax  →  截断（top-k / top-p / min-p）
            →  重新归一化  →  按概率抽一个
```

**顺序很重要。** temperature 在截断之前生效，所以它会改变 top-p 留下多少个候选——两个参数不是正交的，一起调容易互相干扰。

### 四个参数各干什么

![[四种采样参数各砍掉什么.excalidraw.md|700]]

**temperature** —— 把 logits 除以 $T$ 再 softmax。

$T < 1$ 让高分更高、低分更低（分布变尖，输出更保守）；$T > 1$ 拉平（更发散）。$T \to 0$ 时退化成直接取最大值，也就是贪心解码。

**top-k** —— 只保留分数最高的 $k$ 个候选，其余置零。简单粗暴，问题是**它不看分布形状**：分布很尖时（一个候选占 95%）留 50 个纯属浪费，分布很平时留 50 个可能还不够。

**top-p（核采样）** —— 从高到低累加概率，够 $p$ 就停。它自适应分布形状：尖就留得少，平就留得多。实践中用得最多的就是它。

**min-p** —— 只保留概率不低于「最高概率 × 阈值」的候选。比 top-p 更贴合分布形状，在高 temperature 下尤其稳，因为它天然排除掉那些绝对概率极低的长尾。

**重复惩罚**是另一类：`presence_penalty` 惩罚「出现过」，`frequency_penalty` 按出现次数递增惩罚。它们治标不治本——模型开始复读通常说明上下文或提示词有问题，惩罚只是把症状压住，还可能压出别的毛病（该重复的专有名词也被压了）。

### 该怎么调

先看厂商给的默认值。Qwen3-8B 的 `generation_config.json` 里是 `temperature 0.6`、`top_k 20`、`top_p 0.95`——这是官方在他们自己的评测上调过的，见 [[02-开源权重包里有什么]]。**从默认值出发，一次只动一个。**

按任务分：

| 任务          | 大致方向                                                       |
| ----------- | ---------------------------------------------------------- |
| 结构化输出、抽取、分类 | 低 temperature（0–0.3），配约束解码更稳，见 [[01-结构化输出三档]]              |
| 事实问答、RAG    | 中低（0.3–0.7）                                                |
| 写作、头脑风暴     | 高（0.8–1.2）+ top-p 0.9 上下                                   |
| 需要多样候选再排序   | 高 temperature 生成 N 份，再挑，见 [[02-Test-time compute scaling]] |

> [!warning] temperature=0 不等于确定性
> 这是最常见的误解。设成 0 之后仍然可能每次结果不同，原因不在采样：
> - **batch 组成会变**——同一批里有哪些请求会影响浮点归约的顺序，见 [[07-Continuous batching]]
> - **GPU 浮点运算本身不保证跨批次逐位一致**
> - **MoE 模型的专家路由**可能受批次影响
>
> 想要可复现，得固定种子、固定 batch、固定后端版本，而且通常要牺牲吞吐。**做 eval 时如果依赖「跑两次结果一样」，先验证这个假设成不成立**，见 [[02-回归测试与 CI 门禁]]。

### 采样参数属于配置，要版本化

改 temperature 和改提示词一样会改变系统行为，所以它应该：

- 进配置文件而不是散在代码里
- 变更时触发 eval 门禁
- 打进 trace，见 [[02-必打字段清单]]

见过太多次「线上突然变差」最后查出来是有人手改了 temperature 且没记录。

## 动手做

- [ ] 同一个 prompt，temperature 从 0 扫到 1.5，每档跑 10 次，观察输出发散的速度
- [ ] 固定 temperature，对比 top-k=50 和 top-p=0.9 在「分布很尖」和「分布很平」两种输入上的表现差异
- [ ] 设 `temperature=0` 跑 20 次，统计有几次结果完全一致——验证它到底确不确定
- [ ] 打开 logprobs，把某一步的候选分布打印出来，手动算一遍 top-p 会留下几个，见 [[05-logprobs 与置信度]]
- [ ] 在结构化输出任务上对比 temperature 0 和 0.7 的 JSON 合规率
- [ ] 把采样参数挪进配置文件，接进 eval 门禁

## 坑

**同时调好几个参数。** 它们互相影响，一起动之后无法归因是哪个起的作用。

**以为 temperature=0 就可复现。** batch 组成和浮点归约顺序都会让结果变，做 eval 前必须验证。

**用重复惩罚治复读。** 复读通常是上下文或提示词的问题，惩罚会连带压掉该重复的内容。

**照抄别人的参数。** 厂商默认值是在他们的评测上调的，你的任务分布不一样。从默认值出发，用自己的 eval 验证。

**改了不记录。** 采样参数是系统行为的一部分，散在代码里改一次就是一次无声的变更。
