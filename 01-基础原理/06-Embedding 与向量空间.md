「把文本变成向量」这句话底下藏着两件完全不同的事，混在一起会导致一类很难查的错误。

## 一句话

模型内部的 token embedding 是**上下文无关的查表结果**，检索用的句向量是**整段文本压缩成的一个点**；前者是模型的第一层，后者是另一个模型的最后一层。

## 原理

### 两种 embedding，别搞混

| | token embedding | 句向量 / 文档向量 |
| --- | --- | --- |
| 是什么 | 词表里每个 token 对应的一个向量 | 一整段文本对应的一个向量 |
| 从哪来 | 模型的第一层，查表 | 专门的 embedding 模型，取最后一层 |
| 上下文相关吗 | **无关**——「苹果」永远是同一个向量 | 相关——整段话的意思都编进去了 |
| 拿来干什么 | 喂进 Transformer 的输入 | 算相似度、做检索 |

开头那个「苹果」例子里说的「两句话拿到的向量一模一样」，指的就是第一列——那是 attention 之前的状态，见 [[01-Transformer 与 attention]]。经过几十层之后它才变得和上下文有关。

**最常见的错误是拿 token embedding 去做检索。** 那是模型的输入表示，没有为「语义相似」这个目标优化过，效果会明显差于专门的 embedding 模型。

### 向量空间里的「相似」是被训出来的

一个向量空间不会天然知道什么和什么相似。**相似的定义完全来自训练目标。**

检索用的 embedding 模型通常用对比学习训：给它一批「相关的文本对」和「不相关的文本对」，让相关的靠近、不相关的远离。所以：

- 在**问答检索**语料上训的模型，「问题」和「答案」会靠得近
- 在**同义改写**语料上训的，意思相同的句子靠得近
- 这两种「近」不是一回事

这直接导致一个实践后果：**你的任务形态和模型的训练目标不匹配时，相似度分数会失去意义。** 用问答检索模型去做「找重复文档」，或者反过来，效果都会莫名其妙地差。选型方法见 [[02-Embedding 模型选型与评估]]。

### 怎么量相似

**余弦相似度**最常用——只看方向不看长度：

$$
\cos(\mathbf{a}, \mathbf{b}) = \frac{\mathbf{a} \cdot \mathbf{b}}{\|\mathbf{a}\| \|\mathbf{b}\|}
$$

向量**已经归一化**的话，余弦相似度就等于点积，算起来更快。多数向量库默认假设你传进来的是归一化过的向量——**没归一化就传进去，检索结果会莫名其妙，而且不报错**。

### 高维空间的两个反直觉

**一、余弦相似度的绝对值没有意义。** 在高维空间里，随机取两个向量，余弦相似度会集中在 0 附近，而实际模型产出的向量往往挤在一个狭窄的锥形区域里（各向异性），于是**任意两段文本的相似度看起来都挺高**——0.7、0.8 很常见。

所以「相似度 0.85 说明很相关」这句话是没根据的。**该看的是排序和相对差距**：候选之间的分差有没有拉开。一个实用做法是记录 top-1 分数的分布，看它随时间的变化，而不是盯绝对值，见 [[03-漂移监控三条线]]。

**二、维度不是越高越好。** 高维表达力强，但存储和计算成本线性增长，而且收益递减。很多模型支持**降维输出**（比如 Matryoshka 那类训练方式），可以在质量和成本之间取点。

### 几个会咬人的地方

**跨模型的向量不可比。** 不同模型的向量空间毫无关系。换了 embedding 模型，**整个索引必须重建**——这件事常被低估，几亿条文档重新编码是几天的活，见 [[05-Freshness 与 tombstone 删除传播]]。

**同一个模型的不同版本也可能不兼容。** 供应商悄悄升级了 embedding 模型，新老向量混在一个索引里，检索质量会缓慢下滑而且不报错——这正是索引腐化的典型形态，见 [[03-漂移监控三条线]]。

**长文本会被截断。** embedding 模型有自己的最大输入长度，超了就截断，后半段的信息直接丢失。这是 chunking 策略要考虑的第一个约束，见 [[01-Chunking 四种策略]]。

**非对称检索要用对模式。** 有些模型区分「查询」和「文档」两种编码方式，用错了会明显掉点。文档里通常写着要加什么前缀。

## 动手做

- [ ] 拿同一句话，分别取模型的 token embedding 和 embedding 模型的句向量，比较维度和用途
- [ ] 随机抽 1000 对无关文本算余弦相似度，看分布中心在哪——体会绝对值为什么没意义
- [ ] 归一化和不归一化各建一次索引，对比检索结果差异
- [ ] 把一段超过模型最大长度的文本编码，验证后半段信息确实丢了
- [ ] 用同一批查询在两个不同 embedding 模型上检索，确认结果完全不同、向量无法混用
- [ ] 试一次降维输出，看 recall 掉多少、存储省多少

## 算学会了

- [ ] 分得清 token embedding 和句向量，不会拿前者做检索
- [ ] 知道「相似」的定义来自训练目标，会按任务形态选模型
- [ ] 看相似度时看排序和相对差距，不看绝对值
- [ ] 知道换 embedding 模型意味着重建整个索引
- [ ] 记得检查归一化、最大长度、查询/文档前缀这三个细节

## 坑

**拿 token embedding 做检索。** 它是输入表示，不是为相似度优化的。

**把余弦相似度的绝对值当置信度。** 高维空间里任意两段文本看起来都挺像，0.8 不代表相关。

**忘了归一化。** 多数向量库假设输入已归一化，不归一化不报错，只是结果变差。

**换模型不重建索引。** 新旧向量在同一个空间里混着，检索质量缓慢下滑且无告警。

**忽略最大输入长度。** 长文档被静默截断，后半段等于不存在。
