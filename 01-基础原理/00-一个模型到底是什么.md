「模型」这个词至少有三个意思：一张图纸、一堆数字、一个跑着的服务。三个人开会各说各的，能吵一下午。

## 一句话

架构是图纸，权重是零件，推理服务才是那辆能开走的车。
## 原理

### 「模型」这个词的三个所指

你说「我要一辆车」，对方可能给你图纸、给你一堆零件、也可能给你一辆能开走的车。都没错，但显然不是一回事。

**一、架构（architecture），图纸。** 它小得超出多数人预期：几百行模型代码，加一份几十行的配置。拿 Llama 3 8B（Meta，2024 年 4 月）举例——挑它是因为配置干净、文档全，不是因为它最新——架构的核心就是这么几个数字：

```json
{
  "hidden_size": 4096,
  "num_hidden_layers": 32,
  "num_attention_heads": 32,
  "num_key_value_heads": 8,
  "intermediate_size": 14336,
  "vocab_size": 128256
}
```

翻译成人话：每个字用 4096 个数来表示；这套结构重复 32 遍；每遍里注意力分 32 个头，但只留 8 组 KV（省显存用的）；中间那层前馈网络宽到 14336；词表里有 128256 个 token。整个「Llama 3 8B 架构」就是这十几个数字，加一份把它们连起来的代码，`git clone` 一秒钟的事。换个模型、换一代，这些数字会变（尤其上下文窗口这几年翻了好几个数量级），但配置文件就这么长这件事不会变。[[01-Transformer 与 attention]] 整篇讲的就是这份图纸上画了什么。

**二、权重（weights / checkpoint），零件。** 打开 `.safetensors`，里面是一串带名字的张量：

```text
model.embed_tokens.weight               [128256, 4096]
model.layers.0.self_attn.q_proj.weight    [4096, 4096]
model.layers.0.self_attn.k_proj.weight    [1024, 4096]
model.layers.0.mlp.gate_proj.weight      [14336, 4096]
model.layers.0.mlp.down_proj.weight      [4096, 14336]
                     ……中间 31 层，同样一套名字……
model.norm.weight                             [4096]
lm_head.weight                          [128256, 4096]
```

每个形状都能在上面那份配置里对上号：`4096` 是 hidden_size，`14336` 是 intermediate_size，`layers.0` 到 `layers.31` 正好 32 层，`k_proj` 那个 1024 就是 8 组 KV 乘每组 128 维。**架构规定有哪些张量、各是什么形状；权重是往这些形状里填的具体数字。** 一共 80 亿个，FP16 一个数占 2 字节，所以文件 16GB 上下，下载得等一会儿。

这 80 亿个数字，就是 Meta 拿约 130 万 H100·小时烧出来的全部成果。

**三、推理服务（deployment），能开走的车。** 图纸和零件都躺在硬盘上，仍然不能用。得有东西把权重装进显卡、常驻内存、对外开个端口：

```bash
vllm serve meta-llama/Meta-Llama-3-8B-Instruct --max-model-len 8192
curl localhost:8000/v1/chat/completions -d '{"model":"...","messages":[...]}'
```

跑起来之后它占着一张卡的显存，有 QPS，有 P99 延迟，并发高了会排队，上下文开太长会 OOM——变成了一个需要运维的东西，而不是一个文件。

这顺便解释了一个常见的困惑：Llama、Qwen、Mistral 的架构图摆一起，除了几个超参数几乎认不出区别，可实际能力差得很远。因为差别基本全在第二栏——同一张图纸，喂了不同的数据、烧了不同量的算力。**架构决定它能长成什么样，权重决定它实际长成了什么样。**

> [!tip] 一个立刻能用的习惯
> 下次听到「我们要上这个模型」，先问一句是指哪一栏。换架构是研究项目，换权重是一次微调，换部署方式是一个周五下午——三件事的成本差着两个数量级。

### 猜一个 token，到底发生了什么

假设你输入「今天天气」，模型要接下一个字。整件事长这样：

![[猜一个 token 的六步.excalidraw.md|575]]

逐步说：

1. **切词**——「今天天气」变成 token id，比如 `[100, 234, 567]`，见 [[03-Tokenization]]。
2. **查表**——每个 id 查出一个 $d$ 维向量。这时候的「天」还是个通用的「天」，它还不知道自己站在哪句话里，见 [[06-Embedding 与向量空间]]。
3. **过 $N$ 层**——模型的主体就是同一个结构重复 $N$ 遍，每一遍叫一个 block，也直接叫「层」。每层干两件事：先读一遍前面所有的字、把有关的信息取过来，再自己消化一遍。$N$ 随模型规模定，GPT-2 small 是 12 层，Llama 3 8B 是 32 层，70B 是 80 层，再大的更深。
4. **只看最后一个位置**——前面那些位置也算出了结果，推理时全部丢掉。（训练时可不丢，那是全部的监督信号，一次前向能拿 $T$ 份，这笔买卖太划算了。）
5. **映回词表**——lm_head 把那个 $d$ 维向量变成十几万个分数，词表多大就多少个。
6. **挑一个**——把那堆分数变成一个概率分布（这一步叫 softmax），再按 temperature、top-p 之类的参数挑出一个字，见 [[04-采样参数]]。

然后把挑出来的字接到输入末尾，回到第 1 步，再来一遍。

> [!info] 为什么是几十层，不是三层也不是三千层
> 有个很自然的猜测：层数多是为了让信息传得更远——第一层只看得见左右几个字，越往上视野越宽，攒够几十层才终于看全整句话。
> **恰恰不是这样。** 每一层都要「读一遍前面所有字」，第一层就已经全看过了。没有哪一层比另一层看得更远，视野从头到尾都是满的。
> 那多出来的三十层在干什么？**反复加工**。第一层也许只认出「它」指的是前面那只猫；第二层在这个结论之上再推一步，判断这半句是在解释原因；第三层接着推。深度换来的是理解的层次，不是视野的宽度。
> 那为什么不干脆堆一千层？三个理由：每层都得排队走完，层数直接决定吐一个字要等多久；太深了不好训；而且加到一定程度就不怎么涨了。几十层是当前这个规模下试出来的平衡点——[scaling law](https://arxiv.org/abs/2001.08361) 甚至发现，在给定参数总量下，深一点还是宽一点，很大范围内差别不大。所以 32 这个数字没什么神圣性，换成 28 或 36 也照样过日子。

这里有个反直觉但很重要的事实：**模型并没有「打算说什么」这回事。** 它每次只回答一个问题——下一个字最可能是什么。一段通顺的、有逻辑的、看起来像是想好了才说的回答，是这个问题被连续问了两百遍的副产品。

还有个直接影响成本的推论：**每猜一个字，上面六步就要重来一遍。** 你看到的流式输出，是几十上百次循环。所以输出长度比输入长度贵得多，详见 [[01-Prefill vs Decode]]。

### 推理引擎在干什么

图纸有了，零件有了，还差个把它俩跑起来的东西——推理引擎，比如 vLLM、SGLang、TensorRT-LLM、llama.cpp。

一个很自然的念头是：不就是矩阵乘法吗，PyTorch 二十行写完。这话没错，而且真能跑起来。问题是它只能伺候一个人，而且伺候得还不快。推理引擎存在的全部意义，是从「能跑」到「能扛住流量」。

它至少得管这些：

| 它管什么 | 不管的话 | 详见 |
| --- | --- | --- |
| KV cache 的分配与复用 | 每猜一个字都重算整段历史 | [[02-KV cache 为什么存在]] |
| 显存分页 | 碎片吃光显存，明明有空间却 OOM | [[04-PagedAttention 与分页显存]] |
| 批处理调度 | 一次只服务一个人，卡在那儿闲着 | [[07-Continuous batching]] |
| 抢占与驱逐 | 显存一满，整个服务卡死 | [[06-驱逐与内存压力]] |
| 前缀缓存 | 同一段 system prompt 每次重算 | [[05-Prefix caching]] |
| 采样 | 只会挑最高分那个字，回答千篇一律 | [[04-采样参数]] |

归纳成一句：**推理引擎干的活，本质上就两件——别重算，别闲着。** 上面那张表里每一行，展开都是一整套机制。

### 训练引擎在干什么

推理是「拿权重算答案」，训练是「拿答案改权重」，方向反过来。所以它要多背几个包袱：

- **反向传播**——显存里除了权重，还得存前向的激活值和回传的梯度。
- **优化器状态**——用 Adam 的话，每个参数还要额外存两份统计量。
- **分布式切分**——数据并行、张量并行、流水线并行、ZeRO，模型大到一张卡放不下就得切。
- **数据管线与 checkpoint**——训练跑几天几周，中间挂了要能接着跑。

于是有了那个经典的天真估算：「7B 模型，FP16，一个参数 2 字节，14GB 显卡够了吧？」——推理确实差不多，训练可以直接乘以好几倍。**推理的显存主要被权重和 KV cache 吃掉，训练的显存主要被梯度和优化器状态吃掉，两边是完全不同的两本账。** 想省事就上 LoRA，见 [[03-LoRA 与 QLoRA]]；容量规划见 [[01-GPU 容量规划]]。

## 坑

**把「模型」和「推理服务」当成一回事。** 同一份权重换个引擎，能力一个字都不会变，但吞吐和 P99 可能差一个数量级。有人抱怨「这模型好慢」，八成骂错了对象。

**以为架构决定能力。** 架构决定的是上限的形状，不是实际水平。看到一篇新论文改了个模块就断言它更强，通常是把图纸当成了车。

**拿推理的显存账去估训练。** 这是新人最常见的一次性翻车，而且要跑到 OOM 才发现。

**以为模型「知道」自己要说什么。** 它只是在猜下一个字。理解这一点之后，很多现象就不奇怪了：为什么它会一本正经地编、为什么中途能被带跑偏、为什么同一个问题换个问法答案就变了。
