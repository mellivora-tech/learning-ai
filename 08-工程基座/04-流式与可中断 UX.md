用户点了「停止」，前端不再显示了——但后端还在吐字，还在烧钱。这个 bug 很常见，因为它不影响功能，只影响账单。

## 一句话

流式让等待变得可忍受，中断让停止真的省钱；两者都要求**取消信号能一路传到推理引擎**，而不是只在前端断开。

## 原理

### 为什么必须流式

同样是 20 秒出完一段回答：

- **非流式**：20 秒白屏，然后一次性出现
- **流式**：0.5 秒开始出字，边出边读

**用户感知的是首字延迟，不是总时长。** TTFT 决定「它反应快不快」，TPOT 决定「读起来顺不顺」，见 [[02-指标体系]]。

这也是为什么优化 TTFT 的收益经常被低估——它改善的是感知，而感知才是产品体验。

### 流式带来的工程复杂度

流式不是「把返回改成 SSE」这么简单，它把三件事变难了：

**一、错误发生在流中间。** HTTP 200 已经发出去了，头也发完了，吐到一半模型报错或者超时。这时候不能再改状态码，只能在流里发一个错误事件，而**客户端必须处理这种事件**——很多实现漏了这一步，表现是回答莫名其妙截断。

**二、结构化输出和流式冲突。** 要求输出 JSON 时，流到一半的 JSON 是不合法的，没法解析。几种处理：

- 攒够完整的再解析（等于放弃流式）
- 用增量 JSON 解析器（复杂但可行）
- **让模型先流式输出自然语言，结构化部分放最后**（最省事）

**三、token 边界不等于字符边界。** 一个汉字可能被切成多个 token，逐 token 返回会吐出乱码。必须按 UTF-8 边界缓冲再发，见 [[03-Tokenization]]。

### 中断要能真的停下来

用户点停止时，理想的链路是：

```text
前端断开连接
  → 网关检测到客户端断开
  → 应用层收到取消信号
  → 取消上游的模型请求
  → 推理引擎终止该序列并释放 KV cache
```

**现实中这条链最容易断在中间两环。** 常见情况是：前端不再渲染了，后端的 `for chunk in stream` 循环还在跑，模型还在生成，KV cache 还占着，钱还在花。

排查方法很直接：**在生成过程中断开客户端，然后看推理引擎的活跃序列数有没有降下来。** 没降就说明取消没传到。

### 中断之后怎么办

停下来只是第一步，还要决定已经生成的部分怎么处理：

| 场景 | 合理做法 |
| --- | --- |
| 用户主动停止 | 保留已生成部分，标记为「已中断」 |
| 超时中断 | 保留 + 转「待人工」，见 [[03-升级到人与结构化中间状态]] |
| 有副作用的操作跑到一半 | **必须能回滚或标记待清理**——这是最危险的 |
| 多步 agent 中途停 | 保存状态，支持续跑，见 [[05-断点续跑]] |

第三行值得单独强调：**如果 agent 已经调用了写操作工具然后被中断，你需要知道那个操作到底成没成。** 这就绕回了幂等和超时语义，见 [[03-超时与背压]]。

### 长任务的进度反馈

异步长任务没法用流式返回最终结果，但仍然需要给用户反馈。做法是流式返回**进度事件**：

```text
event: step
data: {"step": 3, "total": 8, "desc": "正在检索相关文档"}

event: step
data: {"step": 4, "total": 8, "desc": "调用发票解析工具"}
```

这些事件直接来自状态机的转换，见 [[02-状态机]]。**做了显式状态机之后，进度反馈几乎是免费的**——这是那一节投入的额外回报。

### 别忘了成本归因

中断的请求也花了钱。这部分成本要记在账上，否则「每次成功任务成本」会被低估——因为分子少算了中断掉的那些，见 [[04-成本归因与每次成功任务成本]]。

打点时把 `finish_reason` 记成 `cancelled` 这类值，和正常完成、被截断区分开，见 [[02-必打字段清单]]。

## 动手做

- [ ] 把一个非流式接口改成流式，测 TTFT 的变化和用户感知差异
- [ ] 在流的中间人为触发一个错误，验证客户端能正确处理错误事件
- [ ] 生成过程中断开客户端，观察推理引擎的活跃序列数有没有降下来
- [ ] 中文输出时逐 token 打印，确认有 UTF-8 缓冲，不会吐乱码
- [ ] 让 agent 在调用写操作后被中断，检查那次操作的状态是否可知
- [ ] 把中断请求的成本单独统计出来，看占总成本多少

## 算学会了

- [ ] 知道用户感知的是 TTFT 而非总时长
- [ ] 流中间的错误有专门的事件类型，客户端会处理
- [ ] 取消信号能一路传到推理引擎，验证过序列数会降
- [ ] 中断后已生成的部分有明确的处理策略
- [ ] 中断请求的成本被记在账上

## 坑

**前端停了后端没停。** 最常见的一个，只影响账单所以很难被发现。

**流中间的错误没处理。** 表现是回答莫名其妙截断，用户以为是模型能力问题。

**逐 token 直接输出。** 汉字跨 token 时吐乱码。

**中断时不管副作用。** agent 已经写了数据然后被中断，状态不明。

**中断的成本不计入。** 单位成本被低估，优化方向被误导。
