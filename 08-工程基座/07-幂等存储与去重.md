「同一个请求执行两遍，结果和执行一遍一样」——这句话说起来简单，落到存储层要处理并发、要处理进行中、要定保留期。

## 一句话

幂等的实现是一张「键 → 结果」的表加三种状态；难点不在正常路径，在**两个相同请求同时到达**和**上一次执行到一半崩了**这两种情况。

## 原理

![[幂等键并发.excalidraw.md|700]]

### 和工具层那边的分工

幂等这件事在两个地方出现，管的东西不同：

| | 管什么 |
| --- | --- |
| [[07-幂等性与故障注入]]（契约层） | 工具怎么**声明**自己幂等、键由谁生成、故障注入怎么测 |
| **本篇**（存储层） | 键怎么**存**、并发怎么处理、结果保留多久 |

前者是接口约定，后者是实现。这里只讲后者。

### 一张表 + 三种状态

```sql
CREATE TABLE idempotency (
  key          TEXT PRIMARY KEY,
  status       TEXT NOT NULL,        -- in_progress | completed | failed
  request_hash TEXT NOT NULL,
  response     JSONB,
  created_at   TIMESTAMPTZ NOT NULL,
  expires_at   TIMESTAMPTZ NOT NULL
);
```

处理流程：

1. **插入 key，状态 `in_progress`**——用 `INSERT ... ON CONFLICT DO NOTHING`，插入成功说明我是第一个
2. **插入失败**说明这个键已经存在，去查它的状态：
   - `completed` → **直接返回记录的结果**，不重新执行
   - `in_progress` → 有另一个请求正在处理，返回 409 让调用方稍后重试
   - `failed` → 可以重试（或者按业务决定是否允许）
3. 执行业务逻辑
4. **在同一个事务里**写结果并把状态改成 `completed`

第 4 步的「同一个事务」很关键。业务写入和状态更新分开提交的话，中间崩溃会留下「业务做了但状态还是 in_progress」的不一致。

### `in_progress` 这个状态最容易被忽略

只有 `completed` 和不存在两种状态的实现，会在**两个相同请求同时到达**时同时通过检查，然后都去执行——幂等就失效了。

`in_progress` 就是为这种情况准备的。而它带来一个新问题：**如果持有 `in_progress` 的进程崩了，这个键会永远卡住。**

处理：给 `in_progress` 设一个超时，超时后允许别人接管（更新 `created_at` 并重新执行）。这个超时值要大于业务的最长执行时间——LLM 场景下要留足，一次 agent 任务可能几分钟，见 [[03-超时与背压]]。

### 键怎么生成

**调用方提供**是最好的（HTTP 里通常用 `Idempotency-Key` 头），因为只有调用方知道「这两次请求是不是同一件事」。

自己生成的话，用**业务语义的字段**做哈希：

```text
key = hash(tenant_id + user_id + operation + business_id)
```

> [!warning] 绝不要用时间戳或随机数
> 用这两样生成的键，重试时算出的是新键，等于没有幂等。
> 在断点续跑场景里这条尤其致命——重放时要能算出**和第一次完全相同**的键，所以键必须由工作流 ID 加步骤序号这类确定性输入推出，见 [[05-断点续跑]]。

### 请求指纹要校验

同一个键配了不同的请求体，说明调用方搞错了。这时候应该**返回错误而不是返回上次的结果**——否则会出现「用键 A 提交了订单 X，后来用键 A 提交订单 Y，结果拿到了 X 的回执」。

所以表里存 `request_hash`，命中已有键时先比对指纹，不一致就报 422。

### 保留多久

幂等记录不能永久保留，否则表会无限增长。但也不能太短，否则晚到的重试会被当成新请求。

经验值：**保留期 > 调用方最长的重试窗口**。一般 24 小时到 7 天。过期清理可以用分区表或者定时删除。

**保留期结束后同一个键再来，会被当成新请求执行。** 这一点要在文档里写清楚，避免调用方误解。

### 和其他机制的关系

幂等是好几件事的地基：

- **重试安全**——见 [[01-异步任务队列]]
- **超时后可以放心重试**——见 [[03-超时与背压]]
- **断点续跑**——见 [[05-断点续跑]]
- **多数场景下能替代分布式锁**——见 [[06-分布式锁]]

**先把幂等做扎实，上面这几件事都会变简单。** 反过来，幂等没做好的话，这几件事各自都得处理重复问题，而且处理得零散且不一致。

## 算学会了

- [ ] 幂等表有三种状态，能处理并发同键请求
- [ ] `in_progress` 有超时接管机制
- [ ] 键由业务语义的确定性输入生成，不含时间戳和随机数
- [ ] 会校验请求指纹，键相同体不同时报错
- [ ] 保留期大于调用方的最长重试窗口

## 坑

**只有 completed 和不存在两种状态。** 并发同键请求会同时通过检查，幂等失效。

**`in_progress` 没有超时。** 持有者崩溃后那个键永远卡住。

**用时间戳或随机数生成键。** 重试时算出新键，等于没做。

**不校验请求指纹。** 同一个键提交不同内容，会拿到上一次的结果。

**业务写入和状态更新分两个事务。** 中间崩溃会留下不一致。
