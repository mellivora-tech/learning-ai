一个跑了八分钟、调了十几次模型的 agent 任务，因为一次部署重启从头再来。钱白花了，时间白等了，而这本来是可以避免的。

## 一句话

把每一步的结果记进日志，崩溃后重放时**已完成的步直接读结果不重跑**——而这套机制成立的前提是所有有副作用的步骤都幂等。

## 原理

![[断点续跑：崩在哪一步.excalidraw.md|700]]

### 崩了之后从哪儿接上

![[崩了之后从哪儿接上.excalidraw.md|700]]

理想情况是：前三步的结果从日志里读回来（不重新调模型、不重新检索），只有崩掉的第四步需要重试。

**省下的不只是时间，主要是钱**——前三步里那几次模型调用是这个任务的主要成本。

### 两种机制

| | 日志重放 | 数据库检查点 |
| --- | --- | --- |
| 怎么做 | 记录每一步的输入输出，重启后按日志重放 | 定期把整个状态快照存下来 |
| 恢复方式 | 从头重放，已记录的步返回缓存结果 | 加载最近的快照，从那儿继续 |
| 代价 | 要求代码可确定性重放 | 快照可能很大 |
| 代表 | Temporal、Restate | 自己实现的居多 |

**日志重放是目前 agent 场景的主流。** 它天然记录了完整轨迹，对排查和审计也有用，见 [[02-审计日志]]。

工具上，Temporal 适合需要跑几周甚至几年的超长工作流，但基础设施偏重；Restate 用同样的日志重放机制但轻量得多，更适合边缘或 serverless 部署；Inngest 是另一个常见选项。

**但别急着上框架。** 自己在数据库里存状态机加步骤结果，能覆盖很多场景，见 [[02-状态机]]。框架的价值在超长流程、复杂重试语义、跨服务编排——没到那一步就是过度设计。

### 幂等是前提，不是附加项

> [!warning] 这条不成立，整套机制就是危险的
> 重放的时候，有副作用的步骤会被再执行一次。如果那一步是「扣款」或者「发邮件」，重放就等于扣两次、发两遍。
>
> 所以规则是：**任何写外部状态的操作，必须带一个和工作流状态绑定的幂等键。** 键要能在重放时算出同样的值——用工作流 ID 加步骤序号，而不是用时间戳或随机数，见 [[07-幂等存储与去重]]。

### 确定性要求

日志重放要求代码**可确定性重放**：同样的输入，重放时要走同样的路径。这意味着几类操作要特殊处理：

| 非确定性来源 | 处理 |
| --- | --- |
| 当前时间 | 记录第一次的值，重放时读记录 |
| 随机数 | 同上 |
| 外部 API 调用 | 记录返回值，重放时读缓存 |
| **模型调用** | 同上——温度不为 0 时尤其重要 |

最后一行是 LLM 场景特有的。模型输出天然带随机性，见 [[04-采样参数]]，所以模型调用必须被当成「非确定性副作用」记进日志，重放时用记录的结果，而不是重新调一次。

**否则重放会走上和原来不同的分支**，恢复出来的状态和崩之前对不上。

### 怎么验证它真的能用

这是这一节最实际的一条：**故意在中途杀掉进程，确认恢复后的最终输出和不中断跑完的一致。**

具体做法：

1. 完整跑一遍，记下最终输出
2. 同样的输入再跑一遍，在第 N 步 kill 掉进程
3. 重启，让它恢复
4. 比对两次的最终输出

**上线前必须做这个测试**，而且要在不同的步骤各杀一次。很多断点续跑的实现只在快乐路径上验证过，真崩的时候才发现恢复不了。

### 存什么、存多久

**存**：状态机的当前状态、每一步的输入与输出、幂等键、时间戳。

**别存**：完整的模型输入输出原文（太大），除非有审计需求——那种情况下考虑存到对象存储并在日志里放引用。

**保留期**：任务完成后仍要保留一段时间，用于排查和审计。但要有清理策略，否则日志会无限增长，见 [[05-遗忘与过期机制]] 里同样的思路。

## 动手做

- [ ] 给一个多步任务加上步骤日志，记录每步的输入输出与幂等键
- [ ] 实现重放：重启后已完成的步直接读结果
- [ ] 在第 2、4、6 步各杀一次进程，验证恢复后最终输出一致
- [ ] 把模型调用当成非确定性副作用记进日志，验证重放不会重新调模型
- [ ] 故意让某个写操作的幂等键用时间戳生成，观察重放时会发生什么
- [ ] 算一下断点续跑给一次中断任务省了多少钱

## 算学会了

- [ ] 有一个能中断、能续跑、重启不丢状态的长任务实现
- [ ] 做过「中途 kill 再恢复，输出一致」的验证，且在多个步骤各试过
- [ ] 知道幂等是断点续跑的前提而不是附加项
- [ ] 模型调用被当成非确定性副作用记录，重放时读缓存
- [ ] 幂等键由工作流 ID 和步骤序号推出，不含时间戳或随机数

## 坑

**幂等键用时间戳或随机数生成。** 重放时算出不同的键，等于没有幂等。

**模型调用重放时重新调。** 输出不同，可能走上不同分支，恢复出错误的状态。

**只在快乐路径上验证。** 真崩的时候才发现恢复不了。

**一上来就上重型框架。** 多数场景数据库加状态机就够，框架的复杂度未必值。

**日志无限增长。** 完成的任务日志要有清理策略。
