一次 agent 任务跑三分钟。用同步 HTTP 接，网关会先把连接掐了；用户刷新一下页面，任务白跑。

## 一句话

LLM 任务的耗时天然跨越 HTTP 的舒适区，所以异步不是架构偏好，是**由任务时长决定的必然**——剩下的问题只是队列怎么设计。

## 原理

![[异步任务队列.excalidraw.md|700]]

### 哪些必须异步

| 场景 | 典型耗时 | 怎么接 |
| --- | --- | --- |
| 单轮问答、分类 | 1–5 秒 | 同步 + 流式 |
| 带检索的问答 | 3–15 秒 | 同步 + 流式，但要盯 P99 |
| 多步 agent | 30 秒–几分钟 | **必须异步** |
| 批量处理 | 几分钟–几小时 | **必须异步** |

分界线大致在**30 秒**——多数网关、负载均衡器、浏览器的默认超时都在这个量级附近。超过它，同步接口就是在和基础设施对着干。

### 一个队列至少要有什么

**入队要返回可查询的 ID。** 客户端拿着它轮询或者订阅结果。这个 ID 同时也该是幂等键的一部分，见 [[07-幂等存储与去重]]。

**消费要能重试。** 但重试必须配合幂等，否则一次失败的写操作会被执行两遍。

**要有死信队列。** 重试几次还失败的任务扔进死信，而不是无限重试或者静默丢弃。**死信队列里堆积的东西是最好的 bug 报告来源**——定期看它比看日志有效。

**要有可见的进度。** 长任务跑三分钟，用户看不到任何反馈就会以为挂了。至少要能查到「在第几步」，见 [[02-状态机]]。

### 「恰好一次」是不存在的

这是分布式系统的老结论，但在 LLM 场景里代价特别大（一次调用几毛钱，一次写操作可能是真实的业务动作）：

| 语义 | 现实 |
| --- | --- |
| 最多一次 | 可能丢任务 |
| **至少一次** | **实际能做到的**，可能重复 |
| 恰好一次 | 端到端做不到 |

所以工程上的正解永远是：**至少一次投递 + 消费端幂等**。把「不重复」这件事从传输层挪到业务层，见 [[07-幂等性与故障注入]]。

### 多租户下的公平性

一个大客户提交了一万个任务，把队列占满，其他所有人都在等——这是单队列必然出现的问题。

几种处理：

- **按租户分队列**，轮询消费。简单有效
- **加权公平调度**，按套餐给不同权重
- **per-tenant 限流**，入队时就挡住，见 [[07-韧性组件]]

**最起码要做入队限流。** 不然一个租户的异常流量能拖垮所有人，见 [[06-多租户隔离]]。

### 队列深度是最有用的那个信号

它同时告诉你三件事：

- **容量够不够**——持续增长说明消费能力不足
- **该不该扩容**——这是自动扩缩容最直接的触发信号，见 [[02-自动扩缩容]]
- **该不该拒绝**——超过阈值就开始拒绝新请求，见 [[03-超时与背压]]

所以队列深度和**等待时间**（入队到开始处理）都要打进指标，见 [[02-必打字段清单]]。只看处理耗时会漏掉排队那一段——**用户感受到的是端到端，不是你的处理时间**。

### 选型不必复杂

从简单的开始：

| 量级        | 够用的选择                                        |
| --------- | -------------------------------------------- |
| 单机、任务少    | 数据库表当队列（`SELECT ... FOR UPDATE SKIP LOCKED`） |
| 中等规模      | Redis、RabbitMQ、SQS 这类                        |
| 需要断点续跑与重放 | 持久化执行框架，见 [[05-断点续跑]]                        |

**数据库当队列被低估了。** 它天然有事务、有持久化、好排查，在中小规模下比引入一个新中间件省事得多。

## 动手做

- [ ] 把一个长任务从同步改成异步：入队返回 ID，客户端轮询状态
- [ ] 加重试与死信队列，故意让任务失败，确认最终进了死信
- [ ] 验证重试不会导致重复副作用——这一步必须配合幂等
- [ ] 把队列深度和等待时间打进指标，压测时观察它们怎么变
- [ ] 模拟一个租户提交一万个任务，看其他租户会不会饿死
- [ ] 加入队限流，重跑上面那个测试

## 算学会了

- [ ] 知道 30 秒左右是同步与异步的分界，且能说出原因
- [ ] 默认「至少一次 + 消费端幂等」，不追求恰好一次
- [ ] 有死信队列，并且会定期翻它
- [ ] 队列深度和等待时间都在指标里
- [ ] 多租户场景下做了入队限流或分队列

## 坑

**用同步接口跑长任务。** 网关超时、用户刷新、重试风暴，三件事会同时发生。

**重试但不幂等。** 一次失败的写操作被执行多遍，这是最贵的一类 bug。

**没有死信队列。** 失败的任务要么无限重试烧钱，要么静默消失。

**只监控处理耗时不监控排队时间。** 用户感受的是端到端。

**单队列服务所有租户。** 一个大户能把所有人饿死。
