## 交付物

一个真的能扛住重启和中断的长任务系统，外加三次故障演练的记录。

- 一个至少 5 步、包含**写操作**的长任务（比如：拉文档 → 检索 → 调模型抽取 → 写库 → 发通知）
- 显式状态机，状态持久化，非法转换被拒绝
- 异步队列 + 死信队列 + 三层超时
- 有界队列与背压，压满时明确拒绝而不是崩溃
- 幂等表，三种状态，能处理并发同键
- 断点续跑：崩溃后已完成的步读日志、不重跑
- 流式进度反馈 + 可中断，且中断能一路传到推理引擎

**三次演练的记录**（这才是真正的交付物）：

1. **中途 kill**：在第 2、4 步各杀一次进程，恢复后最终输出与不中断跑完一致
2. **并发同键**：同时发两个相同幂等键的请求，只有一个执行
3. **压满拒绝**：把队列压满，确认返回 429 且系统不崩

## 做法

崩溃安全的那几条不变式有起步脚本，五个函数留空，填一个过一个：

```bash
python "_练习/08-可中断可续跑的长任务.py"
```

不用数据库，存储是内存里的假 KV。**裁判全部是模拟崩溃**——因为这几条不变式的共同特点是：写错了在正常路径上毫无症状，只有「刚好在那一步崩掉」时才暴露。

| 关 | 要填 | 谁当裁判 |
| --- | --- | --- |
| 1 | `can_transition` | 终态转回 running、跳步、未知状态都必须被拒绝 |
| 2 | `idempotent_put` | 同一个 key 写两次，落盘次数必须只有 1，且原值不被覆盖 |
| 3 | `checkpoint` | 重放已完成的步骤必须返回**当初的结果**，不是这次重算的 |
| 4 | `run_task` | 在第 1 步前崩溃后续跑，第 0 步不能重新执行 |
| 5 | `check_replay_safety` | 揪出重放路径上的 `random` / `time.time` / `uuid4` |

五关都过之后，脚本会在**每一个步骤边界各崩一次**并恢复，断言四条路径全部收敛到同一结果。

然后是换成真存储的那一半：


1. 先画状态机，控制在八个状态内，见 [[02-状态机]]
2. 状态持久化到数据库，实现转换表并拒绝非法转换
3. 接异步队列，任务领取用 `UPDATE ... WHERE status='pending'` 而不是分布式锁，见 [[06-分布式锁]]
4. 三层超时（模型调用 / 工具调用 / 整任务）各设一个，见 [[03-超时与背压]]
5. 队列改成有界，实现按等待时间的拒绝策略
6. 实现幂等表，键由「工作流 ID + 步骤序号」推出，见 [[07-幂等存储与去重]]
7. 每步结果记进日志，实现重放，见 [[05-断点续跑]]
8. 加流式进度事件（直接来自状态转换）与取消传播，见 [[04-流式与可中断 UX]]
9. 做三次演练，逐项记录

## 复盘

- 第 4 步（写操作之后）被 kill 那次，有没有产生重复副作用？没有的话，是幂等起了作用还是运气好——**能说清机制才算过**
- 断点续跑省下的钱有多少？如果一次中断任务省不了多少，说明成本集中在别处，这套机制的优先级要重估
- 三层超时的值是从实测 P99 定的，还是拍的
- 客户端断开后，推理引擎的活跃序列数多久降下来？降不下来说明取消没传到底
- 状态机画完之后，有没有发现原来代码里存在的隐式状态——那些通常就是过去 bug 的来源
