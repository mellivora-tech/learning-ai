一张图值多少 token？这个问题的答案决定了多模态应用的成本，而它比文本那边难算得多——因为不同模型的规则完全不同。

## 一句话

图像先被切成 patch 再编码成一串视觉 token，**数量随分辨率增长**；所以控制成本的第一手段是控制送进去的分辨率，而不是压缩提示词。

## 原理

![[图像怎么变成 token.excalidraw.md|700]]

### 图像怎么变成 token

流程大致三步：

1. **缩放**——把图缩到模型期望的尺寸
2. **切 patch**——按固定网格切成小块，比如 14×14 像素一块
3. **编码**——每块过视觉编码器变成一个向量，也就是一个「视觉 token」

这些 token 和文本 token 拼在一起送进语言模型，见 [[01-Transformer 与 attention]]。对模型来说，它们就是序列里的普通位置。

**一个常见配置：图缩到 896×896，编码成 256 个 token。** 但这个数各家差别很大，必须查你用的那个模型的文档。

### 数量随分辨率怎么涨

关键在于**很多模型不是固定 token 数，而是按分辨率动态切块**：

- 图越大，切出来的块越多，token 越多
- 高分辨率模式常常是「先切成若干子图，每张子图各编码一遍，再加一张全局缩略图」
- 所以**分辨率翻倍，token 数可能翻四倍**（面积关系）

> [!warning] 一张高清截图可能比整篇文档还贵
> 用户随手上传的手机照片可能是 4000×3000。如果模型按分辨率动态切块，这一张图的 token 数可能是几千——比你精心压缩的提示词多一个数量级。
>
> **在送进模型之前先缩放**，是多模态应用最有效的降本手段，而且通常不影响效果——多数任务不需要原始分辨率。

### 怎么确定你的模型怎么算

别猜，实测：

1. 送一张图，记下返回的 `usage.prompt_tokens`
2. 只送同样的文本提示词（不带图），再记一次
3. 两者之差就是这张图的 token 数
4. 换不同分辨率重复，画出曲线

**这个曲线画一次，后面所有成本估算都有依据了。** 而且能直接看出模型是固定 token 还是按分辨率动态切。

### 视觉 token 的压缩

2026 年一个明显的方向是把视觉 token 压得更狠。**DeepSeek-OCR 报告在压缩比低于 10 倍时仍能保持约 97% 的 OCR 准确率，最高能压到 20 倍**（数据截至 2026 年 7 月）。

这条路线的意义不只是省钱——它让「用图像承载长文本」变得可行：一页文档渲染成图，视觉 token 可能比它的文本 token 还少。

不过要注意这是**有损**的，压缩比越高丢失越多。对精确抽取的任务要单独验证，见 [[02-OCR pipeline]]。

### 音频

音频的规则更简单一些：通常按**时长**折算。

- 常见量级是每秒几十个 token
- 长音频要分段处理，见 [[01-Chunking 四种策略]]
- 有些接口是先转文字再送模型，那就按文本计费

**同样要实测**：送一段已知时长的音频，看 `usage` 涨了多少。

### 成本上的推论

多模态把 [[04-成本归因与每次成功任务成本]] 那套账变复杂了：

| 做法 | 效果 |
| --- | --- |
| **上传前统一缩放** | 收益最大，通常不影响效果 |
| 按任务选分辨率 | 读大字标题不需要高清，看小字表格需要 |
| **避免多图 + 长上下文叠加** | 视觉 token 也占 KV cache，见 [[03-KV cache 管理与显存测算]] |
| 图片走缓存 | 同一张图反复问，前缀缓存能命中，见 [[04-Prompt caching]] |
| 先便宜路径再回落视觉 | 规整版面先用传统 OCR，只在它置信度低时才升级到视觉模型，见 [[02-OCR pipeline]] |

**第三条容易被忽略**：几千个视觉 token 同样吃显存，多图对话很容易把上下文预算吃光，见 [[02-Context engineering：上下文即预算]]。

## 坑

**假设图像 token 是固定的。** 很多模型按分辨率动态切块，高清图能贵一个数量级。

**直接送用户上传的原图。** 手机照片几千万像素，缩放一下通常不影响效果。

**忘了视觉 token 占上下文预算。** 多图对话很容易把预算吃光。

**照搬别的模型的规则。** 各家的切块方式差别很大，必须实测。

**以为视觉压缩是无损的。** 压缩比越高丢失越多，精确抽取任务要单独验证。
