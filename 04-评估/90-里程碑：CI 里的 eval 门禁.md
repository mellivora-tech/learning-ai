## 交付物

一道**机器执行、不能绕过**的门。具体是：

- 一个从真实流量抽出来、版本化在 git 里的 golden set（100–200 条）
- 一个自己写的对抗集（六类各 10–15 条），critical 级别零容忍
- 一个校准过的 judge，附 Cohen's κ 的实测值
- 一条 CI 流水线：prompt / 模型 / 检索配置变更时自动触发，不过线不许合
- 一份 CI 报告样例，能直接看出**哪几条从对变错了**

外加一次「故意提一个会退步的 PR，被拦住了」的截图——这是唯一能证明门禁真的活着的证据。

## 做法

门禁的**判定逻辑**有起步脚本，五个函数留空，填一个过一个：

```bash
python "_练习/04-CI 里的 eval 门禁.py"
```

不用装东西，也不用调模型——模型输出是固定的假数据。练的是判定逻辑，而**判定逻辑写错比模型差更危险**：一个永远不会红的门禁比没有门禁更糟，因为它让人以为有人在看。

| 关 | 要填 | 谁当裁判 |
| --- | --- | --- |
| 1 | `pass_rate` | 空集必须返回 0，不能返回 1——数据集加载失败是最常见的 CI 故障 |
| 2 | `regressions` | 构造「一好一坏、总分完全不变」的两版，那条坏的必须被抓出来 |
| 3 | `cohens_kappa` | 一个永远说「通过」的 judge：朴素一致率 90%，kappa 必须≈0 |
| 4 | `by_stratum` | 对抗层归零时，总分只掉 25%——分层才看得见 |
| 5 | `gate` | 样本数不足时必须**拦下**而不是放行；且原因要一次报齐 |

五关都过之后脚本会跑一遍完整门禁：一组总分持平、但对抗层塌到 0 的数据，它必须红。

然后是接进真 CI 的那一半：

1. 从线上流量分层抽 100 条，逐条标注，存成 JSONL 进 git，见 [[01-Golden set]]
2. 六类各写 10–15 条对抗载荷，判据用 `must_not` 优先的形式，见 [[03-对抗测试集]]
3. 人工标 100 条，跑 judge，算 κ；低于 0.6 就改提示词重来，见 [[04-Judge 校准]]
4. 跑十次同样的代码，测出分数的自然波动范围
5. 据此分层设阈值：总分宽松、关键子集零容忍、schema 合规率设硬下限
6. 接进 CI，配置成对 prompt/模型/检索配置目录的路径触发
7. 让报告输出退步样本的 input 和两版 output 的 diff
8. 提一个故意退步的 PR，验证真的被拦住
9. 测 PR 档耗时，超过五分钟就拆成快慢两档

## 复盘

- 分数的自然波动有多大？阈值留的余量够不够，会不会天天误报
- judge 的 κ 是多少？低于 0.6 的话，是提示词问题还是这个维度本身定义不清
- 报告能不能让人**不看代码就知道该改哪儿**？做不到就还差一步
- 五分钟跑得完吗？跑不完的话，人迟早会想办法绕
- 下一次线上出 bug 时，回流成 golden set 新样本的路径通不通
