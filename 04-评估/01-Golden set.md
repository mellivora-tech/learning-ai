一百多条真实样本，标好期望结果，存进仓库。这是整个 AI 工程里投入产出比最高的一件事，也是最容易被推迟的一件事。

## 一句话

golden set 不是一次性交付的测试集，是一份**随着线上 bug 持续变厚**的资产——判据不是有没有，是这个月厚了多少。

## 原理

### 为什么它排在最前面

roadmap 把「度量先行」放在阶段 1，理由只有一句：**这步不做完，后面全是盲飞。**

想想没有它的时候你怎么工作：改了一版提示词，跑三个例子，看着好像更好了，上线。过两周有人说效果变差了，你也不知道是哪次改动、变差了多少、哪类输入受影响。**每一次优化都是赌博，而且赌完不知道输赢。**

有了 golden set，同样的改动会得到一个数：从 82% 到 85%，或者从 82% 掉到 79%。仅此而已，但一切都不一样了。

### 从真实流量抽，不要编

![[golden set 的闭环.excalidraw.md|631]]

**这一条是最重要的。** 编出来的样本会不自觉地避开真实数据里那些脏东西——错别字、半截句子、格式怪异的粘贴、意图不明的提问、夹杂表情符号的输入。而模型恰恰是在这些地方分高下。

拿编的样本测，你会得到一个虚高的分数和一个上线就打脸的结论。

抽样的时候刻意保留这几类：

- **高频路径**——占流量大头的那类请求，权重要够
- **已知会翻车的**——线上投诉过的、人工兜底过的
- **边界情况**——超长、超短、空输入、多语言混杂
- **看起来像但不是**——容易被误分类的那些

100–200 条起步就够。**规模不是关键，代表性才是。**

### 标注：够用就行

不需要精确到分数，「这个算对、这个算错」通常就够了。任务不同，标注形态不同：

| 任务形态 | 标注什么 |
| --- | --- |
| 分类、抽取 | 期望的标签或字段值，可以精确比对 |
| 结构化输出 | 期望的 schema，外加关键字段的正确值 |
| 自由生成 | 好/坏二分，或者「必须包含什么、绝不能包含什么」 |
| 检索 | 哪几篇文档是相关的，见 [[06-检索评估两段式]] |

最后一类最难标也最容易拖延。一个务实的做法：先标「绝不能出现的东西」——事实错误、越权信息、格式崩坏。**先能测出「明显错了」，再谈测出「好不好」。**

### 版本化，像对待代码一样

golden set 要进 git，和代码一起走 review。理由：

- 改了期望结果得留痕，不然分数变化会说不清是模型变了还是标准变了
- 谁加的、为什么加，得能查——尤其是从线上 bug 回流的那些
- 分支上的实验要能和主干对比

存成 JSONL 之类的纯文本格式，一行一条，diff 好读：

```jsonl
{"id": "inv-0031", "input": "...", "expect": {"amount": "1280.00"}, "tags": ["发票", "扫描歪"], "added": "2026-03-11", "why": "线上 issue #482 手写金额识别错"}
```

那个 `why` 字段值钱得超出预期——半年后没人记得这条为什么在这儿。

### 让它变厚的那个闭环

**每修一个线上 bug，就补一条进 golden set。** 这一条比前面所有规则加起来都重要。

它把 golden set 从「一次性的测试集」变成「不会重复犯同一个错误的保证」。做到这一点之后，你的系统才真正开始积累。

一个能直接用的判据：**打开 git log，看这个文件最近一个月有没有新增。** 没有的话，要么你的线上零 bug（不可能），要么这个闭环断了。

### 它不只是测试集

攒起来之后你会发现它有别的用处：

- **选模型**时拿它当裁判，见 [[05-怎么给一个任务挑模型]]
- **校准 judge** 时拿它当参照，见 [[04-Judge 校准]]
- **量化后**验证掉了什么，见 [[09-量化]]
- **换 provider** 时验证兼容性

所以攒 golden set 不是给测试环节做的投入，是给后面所有决策做的投入。

## 动手做

- [ ] 从线上流量导出最近一周的请求，按类型分层抽 100 条——**不许编**
- [ ] 逐条标注期望结果，标不动的先标「绝不能出现什么」
- [ ] 存成 JSONL 进 git，每条带上 `tags`、`added`、`why`
- [ ] 拿当前线上版本跑一遍，记下基线分数——这个数以后每次都要对比
- [ ] 翻最近三个线上 bug，各补一条进去，走一遍完整的回流流程
- [ ] 在日历上设一个月后的提醒：检查这个文件有没有变厚

## 算学会了

- [ ] 手上有一个从真实流量抽出来、版本化在 git 里的 golden set
- [ ] 每修一个线上 bug 会条件反射地补一条
- [ ] 能说出这个月它增加了几条，分别为什么加
- [ ] 改任何提示词或模型，第一反应是先跑它
- [ ] 知道它除了测试还能用在选型、judge 校准、量化验证上

## 坑

**用编的样本。** 最常见也最致命。编的样本系统性回避真实脏数据，分数虚高，上线立刻打脸。

**追求规模。** 1000 条编的不如 100 条真的。抽样的代表性远比数量重要。

**标注标准飘。** 同一类样本前后标得不一致，分数变化就没法归因。标注规则要写下来，最好也进 git。

**只在项目初期做一次。** 不回流线上 bug 的 golden set，半年后就和真实分布脱节了，分数好看但没意义。

**放在某个人的本地。** 没进 git 就不算存在——别人跑不了，CI 也接不上，见 [[02-回归测试与 CI 门禁]]。
