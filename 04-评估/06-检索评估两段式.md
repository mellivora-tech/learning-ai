RAG 答错了，是没检索到，还是检索到了但没用好？这两件事的修法完全不同，所以评估必须分成两段。

## 一句话

先测检索段（找没找到），再测生成段（找到了用没用对）——**没检索到的，再强的模型也救不回来**，所以永远先看第一段。

## 原理

### 为什么必须分开

一次 RAG 失败可能来自两处：

- **检索段没给对材料**——相关文档根本没进 top-k
- **生成段没用好材料**——材料在上下文里，但模型忽略了、误读了、或者编了个不在材料里的答案

只测端到端准确率的话，这两种失败混在一个数字里，你不知道该去调 chunk 策略还是调提示词。

**而且优先级是固定的：先修第一段。** 检索没召回，生成段做什么都没用。很多团队在提示词上耗几周，其实 recall@10 只有 0.4。

### 第一段：检索测什么

需要的标注是「对这个查询，哪几篇文档是相关的」。

| 指标 | 回答什么问题 | 什么时候看它 |
| --- | --- | --- |
| **recall@k** | 相关文档有多少进了前 k 名 | **最重要**，先看这个 |
| precision@k | 前 k 名里有多少是相关的 | 上下文预算紧张时看 |
| **nDCG@k** | 相关的排得够不够靠前 | 加了重排之后看它有没有效 |
| MRR | 第一个相关文档排第几 | 只需要一篇正确答案时 |

**先看 recall@k**，因为它是天花板。recall@10 是 0.6，意味着四成的问题从一开始就注定答不对，后面所有优化的上限就是 60%。

一个实用的诊断：**把 k 放大到 50 再测一次 recall**。

- recall@50 也很低 → 问题在**召回本身**：embedding 选型、chunk 策略、要不要加 BM25，见 [[03-Hybrid search（dense + BM25 + RRF）]]
- recall@50 很高但 recall@10 低 → 问题在**排序**：加重排能立竿见影，见 [[04-Rerank（cross-encoder 精排）]]

这个判断只花一次实验，能省掉几周的瞎调。

### 第二段：生成测什么

材料给对了之后，看模型用得怎么样。

**groundedness（有据性）**——回答里的每个事实陈述，能不能在给定的材料里找到依据。这是 RAG 场景幻觉的直接度量。做法通常是把回答拆成一条条陈述，逐条让 judge 判断「材料支持吗」，见 [[04-Judge 校准]]。

**citation precision 与 recall 要分开测**，这是最容易糊弄过去的一处：

| | 定义 | 低了说明 |
| --- | --- | --- |
| citation precision | 引用的那些来源，真的支持对应说法吗 | 在**乱引**——引了但内容对不上 |
| citation recall | 需要引用的说法，都引了吗 | 有**没标注来源的断言**混在里面 |

合成一个「引用准确率」会把这两种毛病搅在一起。乱引和漏引对用户的伤害不同，修法也不同。

**拒答率**——材料里没有答案时，模型有没有老实说不知道。这一项要专门构造样本：**故意问材料里没有的东西**，看它编不编。

很多系统在这项上很难看，因为训练目标就是「要有帮助」，宁可编也不愿意说不知道。而在企业场景里，编一个看着合理的答案比说不知道危险得多。

### 一张能直接用的诊断表

| recall@k | groundedness | 拒答率 | 该修哪儿 |
| --- | --- | --- | --- |
| 低 | — | — | 检索：embedding、chunk、hybrid |
| 高 | 低 | 低 | 生成：模型在编，收紧提示词或换模型 |
| 高 | 高 | 低 | 拒答：材料不足时不肯认输 |
| 高 | 高 | 高 | 检索精度：召回了但不够准，加重排 |

**先定位再动手。** 不看这张表就开始调，多半调在没问题的那一段上。

### 标注怎么攒

检索段的标注最费劲——要人判断哪些文档和查询相关。几个省力的做法：

- **从真实点击或采纳记录反推**，用户复制了哪段、点开了哪篇
- **反向构造**：拿一篇文档让模型生成几个「这篇能回答的问题」，人工筛一遍
- **只标 top-k 里的**，标成「相关/不相关」，比全库标注省几个数量级

第二种最快，但注意它生成的问题会偏「文档友好」——真实用户不那么问。用它起步可以，别只用它。

## 动手做

- [ ] 攒 50 条查询，标出每条的相关文档
- [ ] 算 recall@10，再算 recall@50，用两者的差距判断问题在召回还是排序
- [ ] 加重排跑一次，看 nDCG@10 提升多少、延迟增加多少
- [ ] 构造 20 条「材料里没有答案」的查询，测拒答率
- [ ] 把 citation precision 和 recall 分开算，看是乱引还是漏引
- [ ] 填一遍上面那张诊断表，据此决定下一步调哪儿

## 算学会了

- [ ] 拿到一个 RAG 效果问题，先分清是检索段还是生成段
- [ ] 会用 recall@10 与 recall@50 的差距判断该调召回还是该加重排
- [ ] citation precision 和 recall 分开报，说得出两者低了各意味着什么
- [ ] 有专门测拒答率的样本
- [ ] 知道 recall 是天花板，不会在生成段做超出这个上限的努力

## 坑

**只测端到端准确率。** 两段的失败混在一起，无法定位。

**先调提示词。** 在 recall 只有 0.4 的系统上调提示词，天花板就在那儿，怎么调都上不去。

**把 citation precision 和 recall 合成一个数。** 乱引和漏引是两种病。

**不测拒答。** 材料不足时编答案是 RAG 最危险的失败模式，而它不会出现在准确率指标里。

**用模型生成的查询当唯一标注来源。** 那些查询太「文档友好」，测出来的 recall 虚高。
