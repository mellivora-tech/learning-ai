有了 golden set 却只在想起来的时候手动跑一次，等于没有。它得变成一道机器执行、不能绕过的门。

## 一句话

**任何** prompt、模型、索引、参数的变更都强制跑 eval，不过线不许合——包括那些「只是改了个错别字」的提交。

## 原理

### 为什么必须是强制的

人的判断在这里靠不住。「这次改动很小，应该不用跑吧」——这句话每说一次，就有一次回归溜进主干。

而 LLM 系统对小改动的敏感度远超直觉：

- system prompt 里加一个换行，可能让缓存命中率归零，见 [[04-Prompt caching]]
- 调整一个 few-shot 例子的顺序，某类输入的准确率可能掉几个点
- 模型从 `-0613` 换到 `-1106`，行为可能整体偏移
- 索引重建之后，某些文档的召回位次变了

**这些都不是「小改动」，只是看起来像。** 唯一可靠的办法是不让人来判断，让 CI 来判断。

### 什么变更要触发

| 变更类型 | 例子 |
| --- | --- |
| Prompt | system prompt、few-shot 例子、模板 |
| 模型 | 换模型、换版本、换 provider、改采样参数 |
| 检索 | 换 embedding、改 chunk 策略、重建索引、调 top-k |
| 工具 | 工具描述、schema、新增或删除工具 |
| 参数 | temperature、max_tokens、超时、重试次数 |

一个省事的做法：把这些全部收进一个配置目录，CI 上对该目录做路径匹配触发。**别指望靠 commit message 判断。**

### 门禁怎么设

关键在于**阈值不该是绝对分数，而是相对基线的变化**：

```yaml
gate:
  overall:    { drop_max: 2%  }      # 总分掉超过 2% 拦
  critical:   { drop_max: 0   }      # 关键子集一条都不许掉
  schema:     { min: 99% }           # JSON 合规率硬指标
  adversarial:{ drop_max: 0   }      # 对抗集不许退步
```

**分层设阈值**是这里的核心手法。总分允许小幅波动（LLM 输出有随机性），但关键路径和安全相关的子集必须零容忍。

同时要处理随机性：温度不为 0 时同一输入的结果会变。做法是固定随机种子跑，或者跑多次取多数，或者干脆在 eval 时强制 `temperature=0`——但要清楚这样测的和线上行为有偏差。

### 让它跑得起来

eval 慢会导致人绕过它。几个务实的做法：

- **分层**：PR 上跑 100 条的快集（几分钟），合并到主干跑全量
- **并行**：eval 天然可并行，别串行跑
- **缓存**：没变的那部分不用重跑
- **别用最贵的模型当 judge**：见 [[04-Judge 校准]]

目标是 PR 上的那一档控制在**五分钟以内**。超过这个数，人就开始想办法绕。

### 报告要能看出「哪里退步了」

只报一个总分是不够的。CI 的输出至少要有：

- 总分与基线的差
- **哪几条从对变错了**，附输入和两版输出的 diff
- 分子集的分数变化（按 tag 拆）
- 新增/删除的样本数

最有用的是第二项。「掉了 3%」没法行动，「这 5 条从对变错了，都是发票金额带手写体的」立刻就能定位。

> [!warning] 门禁不是越严越好
> 阈值定得太紧，正常的随机波动会天天拦住合法改动，然后团队会开始用 `skip-eval` 标签绕过——**一旦形成绕过的习惯，门禁就死了**。
> 定阈值时先跑十次同样的代码，看分数的自然波动范围是多少，阈值定在这个范围之外。

### 和线上的关系

CI 门禁挡的是「已知会出错的情况再次出错」。它挡不住新出现的问题——那要靠线上监控，见 [[03-漂移监控三条线]]。

两者的分工：**CI 保证不退步，监控发现新问题，新问题修完回流成 golden set 的新样本。** 这个循环转起来，系统才会越来越稳。

## 动手做

- [ ] 把 golden set 的执行做成一条命令，本地能跑通
- [ ] 接进 CI，配置成 prompt/模型/检索配置目录变更时触发
- [ ] 跑十次同样的代码，记录分数波动范围，据此定阈值
- [ ] 分层设阈值：总分宽松、关键子集零容忍、schema 合规率设硬下限
- [ ] 让 CI 输出「哪几条从对变错了」，附输入和输出 diff
- [ ] 故意提一个会退步的 PR，验证门禁真的能拦住
- [ ] 测一遍 PR 档的耗时，超过五分钟就拆快慢两档

## 算学会了

- [ ] 「只是改了个错别字」也会跑 eval
- [ ] 门禁阈值是基于实测波动定的，不是拍的
- [ ] CI 报告能直接告诉你哪几条退步了，不用自己去比
- [ ] PR 档的 eval 在五分钟内跑完
- [ ] 能说清 CI 门禁和线上监控各挡什么，以及怎么衔接

## 坑

**只在发版前跑一次。** 那时候一堆改动混在一起，退步了也不知道是哪个引起的。要每个 PR 都跑。

**阈值定得太紧。** 随机波动天天误报，团队学会绕过，门禁名存实亡。

**只报总分。** 无法行动的指标等于没有指标。

**eval 太慢。** 超过五分钟人就开始绕。分层是必须的。

**用 temperature=0 测然后以为线上也这样。** 线上采样有随机性，eval 的确定性设置会低估真实方差。至少对关键子集要跑多次。
