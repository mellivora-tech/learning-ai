JSON 解析失败率突然涨了。团队花两周改提示词，最后发现是 `max_tokens` 设小了——输出被砍在半截，剩下的 JSON 自然解析不了。

## 一句话

`finish_reason` 告诉你模型是**说完了**还是**被砍了**；不区分这两种，就会把一个参数问题当成模型能力问题去治。

## 原理

### 它有几种取值

| 值 | 含义 | 该怎么办 |
| --- | --- | --- |
| `stop` | 正常结束，遇到停止符 | 正常处理 |
| `length` | **被 `max_tokens` 砍了** | 加大限额、缩短输入、或分段 |
| `tool_calls` | 模型要调工具 | 走工具执行分支 |
| `content_filter` | 触发了内容过滤 | 走合规路径，不该重试 |
| 其他 provider 特有 | 各家不同 | 查文档 |

**第二行和第一行的处理完全不同**，但如果只看「JSON 能不能解析」，两者都表现为失败。

### 为什么必须单独分类

一个真实形状的排查过程：

```text
现象：JSON 解析失败率从 2% 涨到 11%
↓ 只看解析失败率 → 「模型不听话了」→ 改提示词两周 → 没用
↓ 按 finish_reason 拆开 →
    stop   + 解析失败：2%   ← 真的格式问题
    length + 解析失败：9%   ← 被砍断了
↓ 查最近改动 → 有人给 schema 加了三个字段，输出变长了
↓ 改大 max_tokens → 解决
```

**拆开之后五分钟能定位，不拆开可以查两周。** 这就是为什么 `finish_reason` 必须打进指标并且按值拆分，见 [[02-必打字段清单]]。

### 截断的 JSON 要单独处理

`finish_reason == "length"` 时，输出多半是这样的：

```json
{"invoice_no": "INV-2026-0031", "items": [{"name": "服务费", "amoun
```

处理选项：

**一、直接重试，加大 `max_tokens`。** 最简单。但要注意这次的输入还是原来那些，成本翻倍。

**二、补全后解析。** 用容错的 JSON 解析器把未闭合的括号补上，拿到部分结果。适合「拿到多少算多少」的场景，但**绝不能用在有副作用的操作上**——半截参数触发的写操作是灾难。

**三、拆成多次小请求。** 一次抽三个字段而不是十个。这也是降级链的一级，见 [[04-降级链]]。

**四、改 schema。** 输出太长往往是 schema 设计得太贪心。砍掉可选字段通常立竿见影。

### 怎么给 max_tokens 定值

不要拍一个大数了事——`max_tokens` 会影响引擎的调度和显存预留，见 [[03-KV cache 管理与显存测算]]。

做法：

1. 用真实输入跑一批，统计**输出长度的分布**
2. `max_tokens` 设成 P99 的 1.5 倍左右
3. 监控 `length` 的比例，超过 1% 就说明设小了或者输入变了

**同时监控这个比例的变化趋势**——它悄悄上涨通常意味着输入分布变了或者 schema 变复杂了，见 [[03-漂移监控三条线]]。

### 流式场景更容易漏

流式返回时，`finish_reason` 在最后一个 chunk 里。很多客户端实现只管拼接内容，压根没读这个字段——**表现是回答莫名其妙断掉，而且日志里查不到任何异常**，见 [[04-流式与可中断 UX]]。

检查方法：故意把 `max_tokens` 设成 10，跑一次流式请求，看你的客户端有没有察觉到这是截断。

### 内容过滤要区别对待

`content_filter` 和其他失败在处理上完全不同：

- **不该重试**——同样的输入还会被拦
- **不该走降级链**——换个模型可能一样拦，或者更糟：绕过了合规检查
- **应该走合规路径**——记录、告知用户、必要时转人工，见 [[03-HITL 交互设计]]

把它和普通失败混在一起处理，可能在无意中构造出一条绕过内容安全的路径。

- [ ] 确认 `content_filter` 走的是独立路径，不会被重试或降级

## 算学会了

- [ ] `finish_reason` 在指标里且按值拆分
- [ ] 遇到解析失败率上涨，第一反应是先按 `finish_reason` 拆开看
- [ ] `max_tokens` 是从输出长度分布定的，且监控 `length` 比例
- [ ] 流式客户端能正确识别截断
- [ ] `content_filter` 有独立处理路径，不会被误重试

## 坑

**不区分截断和格式错误。** 会把一个参数问题当模型能力问题治，浪费几周。

**流式客户端不读 `finish_reason`。** 回答断掉而日志无异常，最难查的一类。

**把截断的 JSON 补全后用于写操作。** 半截参数触发的副作用可能不可逆。

**`max_tokens` 设一个很大的数了事。** 影响引擎调度和显存预留，也掩盖了 schema 太贪心的问题。

**`content_filter` 走普通重试。** 浪费成本，还可能构造出绕过合规的路径。
