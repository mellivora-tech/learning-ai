工具描述写成「查询用户信息」五个字，然后抱怨模型乱用工具。它不是不听话，是你没告诉它该怎么用。

## 一句话

工具描述是给模型看的**接口文档**，五段缺一不可：干什么、参数是什么、**错误意味着什么**、**有没有副作用**、什么时候**不要用它**。

## 原理

![[工具合约五段式.excalidraw.md|700]]

### 五段式模板

```yaml
name: refund_order

# ① 干什么 —— 一句话，动词开头，说清楚边界
description: |
  给一笔已支付的订单发起退款。只处理退款，不处理取消、
  改期或部分退货。

# ② 参数 —— 每个参数都要有语义清晰的名字和说明
parameters:
  order_id:
    type: string
    description: 订单号，形如 ORD-2026-000123。必须是已支付状态的订单。
  amount_cny:
    type: number
    description: 退款金额，单位元，最多两位小数。不能超过订单实付金额。
  reason_code:
    type: string
    enum: [quality, wrong_item, late_delivery, other]

# ③ 错误语义 —— 每种错误意味着什么、该怎么办
errors:
  ORDER_NOT_FOUND:    订单号不存在。不要重试，请向用户确认订单号。
  ALREADY_REFUNDED:   已经退过款了。不要重试，告知用户即可。
  AMOUNT_EXCEEDS:     金额超过实付。可以改小金额后重试一次。
  UPSTREAM_TIMEOUT:   支付网关超时，**退款可能已经成功**。不要直接重试，
                      先调 query_refund_status 确认。

# ④ 副作用与幂等 —— 会不会改变外部状态、重复调用安全吗
side_effects: |
  会真实扣减商户余额并给用户打款。**不可逆。**
  幂等：是。相同 order_id 重复调用只会退款一次。

# ⑤ 边界 —— 什么时候不要用它
do_not_use_when: |
  - 用户只是在问「能不能退款」而没有明确要求退 → 先回答，别调
  - 订单还未支付 → 用 cancel_order
  - 只退部分商品 → 用 partial_refund
  - 金额或订单号是你推断出来的而非用户明确给出 → 先确认
```

### 第 ③ 段：错误语义

多数工具描述完全没有这一段，于是模型遇到错误只能瞎猜——最常见的猜法是**再试一次**，而这对写操作是灾难。

错误语义要回答：**这个错误是不是可重试的？** 三类：

| 类别 | 例子 | 模型该怎么办 |
| --- | --- | --- |
| 不可重试 | 订单不存在、已退款 | 停下来，告知用户 |
| 可重试（改参数） | 金额超限 | 改小再试一次 |
| **结果未知** | 上游超时 | **先查状态，不要盲目重试** |

第三类最关键，也最容易被漏掉。它对应的正是超时的语义问题，见 [[03-超时与背压]]。

### 第 ④ 段：副作用与幂等

模型需要知道一次调用会不会改变世界。这直接影响它的行为：

- **只读工具**——放心多调几次，用来验证和确认
- **有副作用且不幂等**——必须谨慎，最好先确认再调
- **有副作用但幂等**——重试是安全的

**这一段还有个工程作用**：它逼你想清楚每个工具的幂等性。写不出来，说明实现上就没想过，见 [[07-幂等性与故障注入]]。

高危操作光靠描述不够，还要在执行前加人工确认，见 [[02-纵深防御]]。

### 第 ⑤ 段：什么时候不要用它

**这一段是区分「工具描述」和「工具合约」的分水岭。**

模型的默认倾向是「有工具就用」。不写边界的话，它会在用户只是随口问问的时候真的发起退款，会在该用另一个工具时用这个。

边界要写得具体，最好带**反例**：

```text
✗ 「仅在合适的时候使用」          —— 等于没说
✓ 「用户只是在问能不能退款而没明确要求 → 先回答，别调」
```

一个实用判据：**看你的工具描述里有没有「不要」两个字。** 一个都没有，说明边界还没写。

### 工具多了要分组

工具超过 20–30 个之后，模型的选择准确率会明显下降。这时候要做分组或者对工具本身做检索，见 [[08-工具数量与工具检索]]。

**在那之前，先把每个工具的合约写扎实**——很多「工具选错」的问题其实是描述写得不清楚，不是工具太多。

### 合约要能被测

工具合约和 prompt 一样属于配置，改了要触发 eval，见 [[02-回归测试与 CI 门禁]]。

针对性的测试：

- **该调不调**：构造明确需要这个工具的场景，看触发率
- **不该调却调**：构造边界场景（用户只是问问），看误触发率
- **参数正确性**：调用了但参数对不对，见 [[06-四层参数校验]]
- **错误处理**：注入各类错误，看模型的反应符不符合 ③ 段的描述

第二项最容易被忽略，而它正是「agent 乱调工具」的直接度量。

## 坑

**只写「干什么」。** 模型不知道边界、不知道错误怎么办、不知道有没有副作用。

**错误码只有名字没有语义。** 模型遇到错误的默认反应是重试，对写操作是灾难。

**没有「结果未知」这一类。** 超时后盲目重试，产生重复副作用。

**参数名用缩写。** 参数名和字段名一样是指令通道，见 [[01-结构化输出三档]]。

**工具一多就想着上检索。** 先把描述写清楚，很多选错是描述的问题。
