agent 调工具超时了。它不知道成没成，于是又调了一次。用户收到两条短信、被扣了两次款——而这一切在日志里看起来都很正常。

## 一句话

在 agent 系统里**重试一定会发生**（模型会重试、框架会重试、用户会重试），所以幂等不是异常处理，是每个写操作的默认要求。

## 原理

### 和存储层那边的分工

| | 管什么 |
| --- | --- |
| **本篇**（契约层） | 工具怎么**声明**幂等、键由谁生成、怎么用故障注入验证 |
| [[07-幂等存储与去重]]（工程基座） | 键怎么**存**、并发同键怎么处理、保留期 |

这里讲接口约定和测试，实现在那边。

### 为什么 agent 场景下重试特别多

普通后端服务里重试是异常路径，agent 里它是常态：

| 重试来源 | 触发原因 |
| --- | --- |
| **模型自己** | 工具返回错误，它决定再试一次 |
| **框架** | 网络抖动、超时自动重试 |
| **修复循环** | 参数不对，改完重来，见 [[02-修复循环（报错回灌）]] |
| **断点续跑** | 崩溃恢复时重放，见 [[05-断点续跑]] |
| **用户** | 觉得没反应，点了两次 |

**五个来源，任何一个都能让同一个写操作被执行两遍。** 所以默认假设必须是「这个调用会被执行多次」，而不是「重试是异常情况」。

### 键由谁生成

三种，各有适用：

**一、调用方（编排层）生成。** 最常见也最推荐。编排层知道「这是同一个业务动作」，能生成稳定的键：

```text
key = hash(workflow_id + step_index + tool_name + canonical(params))
```

注意 `workflow_id + step_index` 这个组合——它保证了**重放时能算出相同的键**，这是断点续跑的前提，见 [[05-断点续跑]]。

**二、模型生成。** 不要这么做。模型不理解「同一个业务动作」的边界，生成的键不稳定。

**三、工具内部推导。** 用业务语义唯一确定，比如「同一个订单同一天只能退一次款」。可靠但只适用于有天然唯一约束的场景。

> [!warning] 键里绝不能有时间戳或随机数
> 用这两样生成的键，每次重试都是新键，幂等等于没做。
> 断点续跑场景下尤其致命——重放时算出的键和第一次不同，那次写操作会被重新执行。

### 工具合约里要声明

每个工具都要在描述里写明幂等性，见 [[05-工具合约五段式模板]]：

```yaml
side_effects: |
  会真实扣减商户余额并给用户打款。不可逆。
  幂等：是。相同 order_id 重复调用只会退款一次。
```

**写不出这一段，说明实现上就没想过。** 这一段的强制要求本身就是个很好的设计检查。

同时，工具的错误码里必须有「结果未知」那一类（典型是上游超时），并明确告诉模型**不要盲目重试，先查状态**。

### 故障注入：怎么验证它真的幂等

声明了不等于做到了。要用故障注入实测，三类：

**一、重复调用。** 同样的参数、同样的键，连续调两次，验证副作用只发生一次。

**二、超时重发。** 让第一次调用超时（但服务端实际执行了），然后重发。**这是最真实也最容易漏的场景**——服务端成功了，客户端不知道。

模拟方法：在工具服务端加一个「执行成功后延迟返回」的开关，让客户端超时。

**三、模型连调两次。** 构造一个让模型误以为第一次失败的场景（比如工具返回一个模糊的错误），看它重试后会不会产生重复副作用。

**第三类是 agent 特有的**，普通后端的幂等测试不会覆盖它。

### 不只是「不重复执行」

完整的幂等语义还包括：**第二次调用要返回和第一次相同的结果**，而不是返回一个「已经执行过了」的错误。

原因是模型会根据返回值决定下一步。返回错误的话，模型可能以为操作失败，去走补偿逻辑——**而那次操作其实是成功的**。

所以正确实现是：命中已有键 → 返回记录的原始结果，见 [[07-幂等存储与去重]]。

### 不可幂等的操作怎么办

有些操作天然难幂等（比如「追加一条评论」）。处理方式：

- **加人工确认**——高危且不可幂等的操作，执行前必须人确认，见 [[02-纵深防御]]
- **拆成两步**——先创建一个带 ID 的草稿，再提交。第二步就幂等了
- **明确标注不可重试**——在工具合约里写死，让模型和框架都不要重试

**别假装它幂等。** 声明和实现不一致比没有声明更危险。

## 动手做

- [ ] 给所有写操作工具补上幂等键，检查生成逻辑里没有时间戳和随机数
- [ ] 在工具合约里补齐幂等性声明和「结果未知」错误码
- [ ] 故障注入一：重复调用两次，验证副作用只发生一次
- [ ] 故障注入二：让服务端执行成功但客户端超时，然后重发
- [ ] 故障注入三：让工具返回模糊错误，观察模型会不会重试并产生重复副作用
- [ ] 验证第二次调用返回的是原始结果而不是「已执行」的错误
- [ ] 找出所有不可幂等的操作，给它们加人工确认或拆成两步

## 算学会了

- [ ] 默认「重试一定会发生」，而不是「重试是异常」
- [ ] 幂等键由编排层生成，含 workflow_id 和步骤序号，不含时间戳
- [ ] 每个工具的合约里声明了幂等性和「结果未知」错误码
- [ ] 做过三类故障注入，尤其是「超时重发」那一类
- [ ] 幂等命中时返回原始结果而非错误

## 坑

**认为重试是异常情况。** 在 agent 里它有五个来源，是常态。

**键里带时间戳或随机数。** 每次重试都是新键，等于没做幂等。

**让模型生成幂等键。** 它不理解「同一个业务动作」的边界。

**幂等命中返回错误。** 模型会以为操作失败，去做补偿——而操作其实成功了。

**只测重复调用不测超时重发。** 后者才是线上真实发生的形态。
