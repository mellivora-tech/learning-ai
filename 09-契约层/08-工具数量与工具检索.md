加一个工具看起来是纯增量——多一个能力，不影响别的。实际上它会让另外三十个工具的选择准确率都下降一点。

## 一句话

工具数量对选择准确率有**负外部性**：每加一个都在稀释其余所有工具；到某个点之后，必须靠分组或检索把候选集缩小。

## 原理

### 为什么会掉

三个机制叠加：

**一、上下文占用。** 每个工具的完整定义要几百 token。三十个工具就是上万 token 常驻在窗口里，挤掉别的东西，见 [[02-Context engineering：上下文即预算]]。

**二、选择空间变大。** 从 5 个里选 1 个和从 50 个里选 1 个，难度不是一个量级。

**三、相似工具互相干扰。** `search_orders`、`query_order`、`get_order_detail` 三个功能重叠的工具放在一起，模型很难稳定地选对。**这一条通常是主因**——不是工具太多，是工具设计得太像。

### 先做减法

上检索之前，先问三个问题：

**能不能合并？** 三个查订单的工具，多半能合成一个带参数的。

**能不能删？** 统计每个工具的实际调用次数，长期为零的删掉。

**描述能不能写清楚？** 很多「选错工具」其实是边界没写明白。每个工具都补上「什么时候不要用它」，见 [[05-工具合约五段式模板]]。

**做完这三步，很多系统的工具数会减少三分之一，准确率明显回升**——而且没有引入任何新机制。

### 到什么规模需要动手

没有绝对数字，但有个可操作的做法：**测出你自己的曲线**。

1. 固定一批任务，从 5 个工具开始
2. 每次加 5 个不相关的工具进去
3. 每档测一次工具选择准确率
4. 画出曲线，找到开始明显下降的那个点

这条曲线是你自己系统的，比任何经验值都可靠。而且**加进去的干扰工具越像，下降越早**——这个实验顺便验证了上面第三条机制。

### 两种缩小候选集的办法

**一、分组 / 命名空间。** 按业务域分组，先让模型选组，再在组内选工具。

优点是确定性强、可解释、好排查。缺点是要人工维护分组，跨组的任务需要两步。

**二、工具检索。** 把工具描述做成向量索引，按当前任务检索出最相关的 N 个塞进上下文。

优点是自动、能扩到几百个工具。缺点是**检索错了模型就完全看不到那个工具**——失败是静默的，而且很难排查。

**推荐组合**：常用的十几个常驻上下文，长尾的走检索。这样高频路径不受检索失败影响。

### 检索工具也要评估

工具检索本质上就是检索，所以同样要测 recall，见 [[06-检索评估两段式]]：

- **工具 recall@k**——该用的工具进候选集了吗
- **端到端选择准确率**——最终选对了吗

两个都要看。recall 高但选择准确率低，说明候选集给对了但模型选错了（描述问题）；recall 低说明检索本身有问题。

**recall 是天花板**——没检索到的工具，模型再聪明也用不上。

### 别忘了另一头

工具多不只影响选择准确率，还影响：

- **攻击面**——每个工具都是一个可能被诱导调用的入口，见 [[01-间接提示注入与 20 条攻击载荷]]
- **权限管理**——工具越多，最小权限原则越难落实，见 [[02-纵深防御]]
- **维护成本**——每个工具的合约都要维护、要测试

所以「加一个工具」的成本要按这几项一起算，而不只是开发那点工作量。

## 动手做

- [ ] 统计每个工具的实际调用次数，删掉长期为零的
- [ ] 找出功能重叠的工具，尝试合并
- [ ] 给每个工具补上「什么时候不要用它」，重测选择准确率
- [ ] 做数量曲线实验：从 5 个开始每次加 5 个，找出准确率开始下降的点
- [ ] 实现分组或检索，对比引入前后的准确率与延迟
- [ ] 单独测工具 recall@k 和端到端选择准确率，区分是检索问题还是描述问题

## 算学会了

- [ ] 能量化「加一个工具」对整体准确率的负外部性
- [ ] 上检索之前先做合并、删除、写清边界三件事
- [ ] 有自己系统的工具数量-准确率曲线
- [ ] 工具检索的 recall 和端到端准确率分开测
- [ ] 算「加一个工具」的成本时会算上攻击面和维护成本

## 坑

**工具一多就直接上检索。** 很多问题是描述不清和功能重叠，先做减法。

**功能重叠的工具不合并。** 相似工具的互相干扰通常是主因。

**只测端到端准确率。** 分不清是检索没召回还是模型选错了。

**全部工具都走检索。** 高频路径会受检索失败影响，而那种失败是静默的。

**只算开发成本。** 攻击面、权限管理、维护成本都在涨。
