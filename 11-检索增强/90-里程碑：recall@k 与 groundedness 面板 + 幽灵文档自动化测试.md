## 交付物

一个能回答「这次答错是检索的锅还是生成的锅」的面板，加一个会主动报警的测试。

- **两段式评估面板**：检索段（recall@10、recall@50、nDCG@10）和生成段（groundedness、citation precision / recall、拒答率）分开展示，见 [[06-检索评估两段式]]
- **一张诊断表**：按 recall / groundedness / 拒答率三个维度定位该修哪一段
- **幽灵文档自动化测试**：CI 里跑一遍，线上定时巡检，失败告警到人，见 [[06-幽灵文档测试]]
- **索引延迟指标**：文档进系统到能被搜到要多久
- **一次完整的优化记录**：从基线开始，每加一样东西记一次增量

## 做法

指标本身有起步脚本，六个函数留空，填一个过一个：

```bash
python "_练习/11-检索评估两段式.py"
```

不用建索引，检索结果是固定的假数据。**练的是指标，因为这些指标算错的方式格外隐蔽**——分母取错、不归一化、把 precision 当 recall，算出来都是个像模像样的小数。

| 关 | 要填 | 谁当裁判 |
| --- | --- | --- |
| 1 | `recall_at_k` | 构造「相关文档数 ≠ k」的用例——用 k 当分母立刻露馅 |
| 2 | `ndcg_at_k` | 同一批文档换个顺序：recall 完全不变，nDCG 必须变 |
| 3 | `rrf` | 两路都排第 2 的文档，必须压过两个「单路第一」 |
| 4 | `diagnose` | 检索和生成都差时，必须**先报检索** |
| 5 | `citation_scores` | 把检索到的全列进引用：recall 满分而 precision 必须塌 |
| 6 | `ghost_probe` | 删掉的文档还能搜到就要报警，删干净了不能误报 |

六关都过之后脚本会打印三种配置的对照面板，其中 recall@50 全程不变而 nDCG 明显上涨——**那正是「衡量重排不能用 recall」的可视化**。

然后是换成自己数据的那一半：

1. 攒 50 条真实查询并标注相关文档，见 [[01-Golden set]]
2. 建基线：递归 512 切分 + 纯向量检索，测 recall@10 和 recall@50
3. **用 recall@10 与 recall@50 的差距判断该修召回还是该加重排**，见 [[06-检索评估两段式]]
4. 加 BM25 走 RRF 融合，测增量，见 [[03-Hybrid search（dense + BM25 + RRF）]]
5. 加 cross-encoder 重排，用 nDCG@10 测增量（不是 recall@50），见 [[04-Rerank（cross-encoder 精排）]]
6. 构造 20 条「材料里没有答案」的查询，测拒答率
7. 分开测 citation precision 与 recall
8. 实现幽灵文档测试的三步，覆盖向量与 BM25 两条路径
9. 接 CI 与线上巡检

## 复盘

- **recall@10 和 recall@50 的差距说明了什么？** 差距大就该加重排，两个都低就该修召回——这个判断只需要一次实验
- 混合检索和重排，哪个的增量更大？和「先做混合再做重排」这个建议顺序符不符
- 拒答率如果很低，模型是在材料不足时编答案吗——这是 RAG 最危险的失败模式
- citation precision 和 recall 哪个更低？前者低是乱引，后者低是有没标来源的断言，两者修法不同
- 幽灵文档测试第一次跑就通过了吗？没通过的话，断在哪一环
