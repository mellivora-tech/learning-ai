换更好的 embedding 模型能提两个点，加一个重排器能提十个点。而后者的实现成本低得多。

## 一句话

重排器把查询和文档**放在一起**过一遍模型，所以判断得比向量准得多；代价是只能用于精排少量候选，但那正好够用。

## 原理

### 和向量检索的本质区别

| | 怎么算相关度 | 代价 |
| --- | --- | --- |
| **向量检索（bi-encoder）** | 查询和文档**分别**编码成向量，再算距离 | 文档可以预先编码，查询时只做向量搜索，**很快** |
| **重排（cross-encoder）** | 查询和文档**拼在一起**送进模型，直接输出相关度分数 | 每一对都要过一次模型，**很慢** |

关键在第一列。bi-encoder 编码文档的时候**还不知道查询是什么**，所以它只能产出一个「通用的」表示。cross-encoder 能看到两者的交互——哪个词对应哪个词、条件满不满足、否定词在不在。

这就是它准得多的原因，也是它慢得多的原因。

### 所以是两段式

```text
召回：混合检索取 top-50~200   ← 快，宽
  ↓
精排：cross-encoder 重排取 top-5~10   ← 慢，准
  ↓
给模型
```

**召回求全，精排求准。** 召回阶段宁可多要一些（recall 是天花板，见 [[06-检索评估两段式]]），精排阶段负责把真正相关的挑到前面。

### 收益通常比换 embedding 大

一个反复被验证的经验：**加重排的收益，通常大于换一个更好的 embedding 模型**。

原因有两层：

- **上限不同**——embedding 模型之间的差距在收敛，而 bi-encoder 和 cross-encoder 之间是结构性差距
- **成本不同**——换 embedding 要重建整个索引，加重排只是在查询链路上加一步，见 [[02-Embedding 模型选型与评估]]

所以优化顺序建议是：**先上混合检索，再加重排，最后才考虑换 embedding 模型。**

有研究报告，contextual retrieval 单独用能把检索失败率降 49%，**配上重排能到 67%**——重排的边际贡献很实在，见 [[01-Chunking 四种策略]]。

### 代价是延迟

重排 50 个候选意味着 50 次前向。这部分延迟直接加在 TTFT 上，见 [[02-指标体系]]。

控制手段：

- **减少候选数**——重排 top-50 而不是 top-200，收益递减得很快
- **用小的重排模型**——重排任务比生成简单，小模型够用
- **批量推理**——50 个候选一批发，别一个个来
- **加缓存**——高频查询的重排结果可以缓存

**先测出「候选数 vs nDCG 提升」的曲线**，找到收益拐点，通常在 30–50 之间。

### 怎么衡量它有没有用

重排改变的是**排序**，所以要看排序质量指标，而不是 recall：

| 指标 | 重排会改变吗 |
| --- | --- |
| recall@50 | **不会**——重排不引入新文档 |
| recall@5 | 会——相关文档被提到前面了 |
| **nDCG@10** | 会，最直接 |
| MRR | 会 |

**只看 recall@50 会得出「重排没用」的错误结论**，因为它按定义就不变。要看 nDCG@10 或者 recall@5。

### 一个容易被忽略的用法

重排器不只能排文档，还能**排别的候选**：

- 排工具——工具太多时用它挑候选，见 [[08-工具数量与工具检索]]
- 排记忆——记忆检索求准，重排很合适，见 [[03-记忆检索与召回]]
- 排模型生成的多个候选答案

**任何「先粗召回再精挑」的场景都能用**。

### 什么时候不值得

- **候选本来就少**（top-5 就是全部）——没有可排的
- **延迟极敏感**——重排那几十毫秒不能接受
- **召回本身就很差**——recall@50 只有 0.4 的话，重排也救不回来。**先修召回**

最后一条最重要：**重排是在召回的结果里挑，它不会凭空变出没召回的文档。**

## 坑

**用 recall@50 评估重排。** 它按定义不变，会得出「重排没用」的结论。

**重排一两百个候选。** 收益递减，延迟白涨。

**召回很差就想靠重排补。** 重排只在召回结果里挑，没召回的永远出不来。

**用大模型做重排。** 重排任务比生成简单，专用的小重排模型性价比高得多。

**先换 embedding 再考虑重排。** 顺序反了，前者贵得多、收益还小。
