文档从源系统删了，主库删了，向量索引里还在。检索照常召回它，模型照常引用它——整个过程没有一个报错。

## 一句话

索引和源数据之间的**不一致不会报错**，只会让答案慢慢变错；所以删除必须显式传播，而且要有自动化测试来证明它传到了。

## 原理

![[幽灵文档怎么产生的.excalidraw.md|700]]

### 三种不一致

| | 现象 | 危害 |
| --- | --- | --- |
| **删除没传播** | 已删的文档还能被检索到（幽灵文档） | 引用作废信息，可能涉及合规 |
| **更新没传播** | 检索到的是旧版本 | 答案基于过期内容 |
| **新增没进索引** | 新文档检索不到 | 用户以为系统不知道 |

**第一种最危险**，因为它可能返回已经被明确要求删除的内容——比如用户注销后本该清掉的数据，见 [[05-遗忘与过期机制]]。

### 为什么容易漏

RAG 系统的数据链路通常是这样：

```text
源系统 → 抽取 → 切分 → 编码 → 向量索引
                              ↘ 元数据库
```

**删除要沿着这条链一路传下去**，而每一环都可能断：

- 源系统的删除是软删还是硬删？软删的话下游怎么知道
- 抽取管道是全量重跑还是增量？增量的话删除事件从哪来
- 一篇文档切成了 12 个块，删的时候 12 个都删了吗
- 向量索引支持删除吗？有些索引结构删除代价很高，实现上做成了「标记」

**最后一条是个真实的坑**：某些向量索引的删除是逻辑标记，重建索引之前实际还在。查询时如果没过滤标记，照样会被召回。

### tombstone：显式的删除标记

做法是给每条记录加一个删除标记（tombstone），并让它沿着链路传播：

```json
{
  "doc_id": "doc-77",
  "op": "delete",
  "at": "2026-07-31T10:00:00Z",
  "reason": "source_deleted",
  "chunk_ids": ["doc-77:0", "doc-77:1", "…", "doc-77:11"]
}
```

要点：

- **记录 chunk 级的 ID**，删的时候一个不漏
- **检索时过滤 tombstone**，别只依赖索引的物理删除
- **删除事件要持久化**，重建索引时才知道哪些不该重新灌进去
- **合规删除要真删**，不能只留标记，见 [[01-数据驻留]]

最后一条要和前面区分开：**过期和淘汰可以软删，用户主动要求的删除必须硬删**——包括向量索引、备份和日志。

### 新鲜度也要管

除了删除，还有「多新才算新」：

| 场景 | 可接受的延迟 |
| --- | --- |
| 政策、规章 | 分钟级——改了就得立刻生效 |
| 产品文档 | 小时级 |
| 历史归档 | 天级 |

**先定义清楚每类内容的新鲜度要求**，再设计同步频率。全部走同一个批量同步周期，要么对时效内容太慢，要么对归档内容太浪费。

实现上通常是：**高时效走事件驱动（源系统变更立刻推），低时效走定时批量。**

### 这类问题只能靠主动测试发现

> [!warning] 它永远不会报错
> 幽灵文档不会抛异常、不会进错误日志、不会触发告警。它只是让某些答案变错，而这些答案看起来完全正常。
>
> **所以必须有一个自动化测试主动去找它**，见 [[06-幽灵文档测试]]。

同时在监控侧加一条：**索引条目数与源系统条目数的差值**。持续偏离说明同步在漏，见 [[03-漂移监控三条线]]。

### 重建索引时的陷阱

全量重建看着是个万能修复手段，但它有自己的坑：

- **重建期间的双写**——新数据往哪写
- **切换的原子性**——不能出现一半新一半旧
- **删除记录要保留**——不然重建时又把删掉的灌回去了

**最后一条最容易踩。** 重建通常是从源系统全量拉，如果源系统那边是软删而管道没过滤，删掉的文档就复活了。

- [ ] 确认向量索引的删除是物理删还是逻辑标记，检索时有没有过滤

- [ ] 监控「索引条目数 vs 源系统条目数」的差值
- [ ] 做一次全量重建，验证已删除的文档不会复活

## 算学会了

- [ ] 知道索引与源数据的不一致不会报错
- [ ] 删除是 chunk 级传播的，一篇文档的所有块都会被删
- [ ] 清楚自己用的向量索引删除是物理还是逻辑
- [ ] 按内容类型分别定义了新鲜度要求
- [ ] 有条目数差值的监控，且做过重建验证

## 坑

**只删主库不删索引。** 幽灵文档就是这么来的。

**删了文档但漏了它的部分块。** 一篇文档十几个块，漏一个就还能被召回。

**依赖索引的物理删除。** 有些索引的删除是逻辑标记，查询不过滤照样召回。

**全部内容用同一个同步周期。** 时效内容太慢，归档内容太浪费。

**重建索引时把删掉的灌回去。** 源系统软删而管道没过滤，删除全部失效。
