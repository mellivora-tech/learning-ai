换 embedding 模型意味着重建整个索引。这件事的代价大到值得在一开始就选对——而选对的方法不是看排行榜。

## 一句话

先用榜单收窄，再拿**自己的查询和语料**测 recall；换模型的迁移成本很高，所以选型阶段多花的时间都是值的。

## 原理

### 榜单只能用来收窄

MTEB 是 embedding 模型最常被引用的评测，覆盖分类、聚类、重排序、检索、语义相似度等多个维度。截至 2026 年，开源模型在上面已经追平甚至超过主流闭源 API。

但它和所有榜单一样，只能用来缩小候选，见 [[04-排行榜怎么读]]：

- **它测的任务分布不是你的。** MTEB 的检索子任务用的是通用语料，你的可能是发票、工单、法条
- **平均分掩盖了维度差异。** 你只关心检索，那就该看检索子项而不是总分
- **语言覆盖差异大。** 中文任务上的排名和多语言总分排名经常不一样

### 中文场景的两个主力

截至 2026 年，中文语料上常见的开源选择是这两支：

| | 特点 | 适合 |
| --- | --- | --- |
| **Qwen3-Embedding** | MTEB 多语言榜领先，8B 版本得分约 70.6；同时具备一定语言理解能力 | 「多面手」，通用场景 |
| **BGE-M3** | 单个模型同时支持稠密、稀疏、多向量三种检索 | 「专业工具」，检索任务优化得更专 |

有个值得注意的观察：**Qwen3-Embedding 的 0.6B 版本在多个任务上就超过了 BGE-M3**——参数量不是决定性因素。这直接影响选型策略：**先试小的**，小的够用就别上大的，见 [[05-怎么给一个任务挑模型]]。

BGE-M3 那个「一个模型出三种向量」的特性值得单独提：它可以在一次编码里同时产出稠密向量和稀疏向量，等于把混合检索的两条路合并了，见 [[03-Hybrid search（dense + BM25 + RRF）]]。

### 怎么用自己的数据测

榜单收窄到三五个之后，用自己的数据定夺：

1. **攒 50 条真实查询**，从线上流量抽，不要编，见 [[01-Golden set]]
2. **标出每条的相关文档**——最费劲的一步，省力做法见 [[06-检索评估两段式]]
3. **同一套切分、同一套检索配置**，只换 embedding 模型
4. **比 recall@10 和 recall@50**——前者是实际效果，后者是召回天花板

**关键是控制变量。** 换模型的同时换了切分策略，测出来的差异归因不了。

### 几个必须查清的参数

选型时容易漏掉的技术细节：

| 项 | 为什么重要 |
| --- | --- |
| **最大输入长度** | 决定块大小的上限，超了静默截断 |
| **向量维度** | 影响存储和检索成本，有些模型支持降维输出 |
| **是否区分查询/文档** | 非对称模型用错模式会明显掉点 |
| **是否需要指令前缀** | 有些模型要求查询前加特定前缀 |
| **归一化** | 多数向量库假设输入已归一化，见 [[06-Embedding 与向量空间]] |

**第三、四项最容易踩。** 模型卡里通常写着「查询要加 `query: ` 前缀」之类的要求，漏了会让 recall 掉几个点，而且很难察觉——因为结果看起来还是「有点相关」。

### 迁移成本要一开始就算清

换 embedding 模型意味着：

- **整个索引要重建**——几亿条文档重新编码是几天的活
- **新旧向量不能混**——混在一起检索质量会缓慢下滑且不报错，见 [[03-漂移监控三条线]]
- **需要双写或停机窗口**——生产系统还得设计迁移方案

所以选型阶段多花一周，比上线半年后被迫迁移划算得多。

**同理，要盯住供应商的模型版本。** 闭源 embedding API 悄悄升级模型的话，新老向量就不兼容了——这是最隐蔽的一类索引腐化。

### 降维是个被低估的选项

有些模型支持在训练时就让向量的前 N 维单独可用（Matryoshka 那类做法），于是可以按需截断：

- 1024 维存储和检索都贵
- 截到 256 维，存储省四倍，recall 可能只掉一两个点

**对大规模语料，这个取舍值得实测**，见 [[06-Embedding 与向量空间]]。

## 坑

**只看 MTEB 总分。** 你只做检索，该看检索子项。

**换模型时同时换了切分策略。** 差异归因不了。

**漏掉查询前缀或非对称模式。** recall 掉几个点，而且结果看起来还是「有点相关」，很难察觉。

**新旧向量混在一个索引里。** 检索质量缓慢下滑且不报错。

**不算迁移成本。** 上线半年后被迫换模型，几亿条文档重编码。
