用户搜「ERR-4092」，向量检索一条都没召回。不是模型不好——是这类查询本来就不该交给向量。

## 一句话

向量懂语义、关键词懂精确匹配，两者的失败场景**互不重叠**；所以混合检索应该是**基线**，不是优化项。

## 原理

### 各自擅长什么

![[向量与关键词各擅长什么.excalidraw.md|700]]

| | 强在哪 | 弱在哪 |
| --- | --- | --- |
| **向量（dense）** | 同义、改写、跨语言。「怎么退货」能召回「退换货流程」 | **专有名词、型号、错误码、人名** |
| **关键词（BM25）** | 精确匹配。「ERR-4092」直接命中 | 换个说法就完全召不回 |

**第二行右列是最容易被低估的。** embedding 对精确 token 不敏感，见 [[06-Embedding 与向量空间]]——`ERR-4092` 和 `ERR-4093` 在向量空间里几乎一样近。

而企业场景里的查询恰恰充满这类东西：订单号、SKU、错误码、内部系统名、人名、法条编号。**纯向量方案在这些查询上的 recall 可能低得吓人，而通用评测测不出来**。

### RRF：不用调权重的融合

两路召回之后要合成一个排序。最省事的办法是 **RRF（倒数排名融合）**：

$$
\text{score}(d) = \sum_{r \in \text{检索器}} \frac{1}{k + \text{rank}_r(d)}
$$

$k$ 通常取 60。**它只用排名，不用分数。**

这一点很关键：向量的余弦相似度和 BM25 的分数**根本不可比**——量纲不同、分布不同、绝对值都没有语义，见 [[06-Embedding 与向量空间]]。想加权融合就得先做分数归一化，而归一化的方式又会引入新的调参。

RRF 绕过了这一整套：**不需要调权重、不需要归一化、不需要校准**。对多数场景它就够了。

想加权的话可以给不同检索器不同的 $k$ 或者乘一个系数，但**先用无参数版本建基线**。

### 什么时候纯向量就够

不是所有场景都需要混合：

| 场景 | 建议 |
| --- | --- |
| 语料里专名密集（工单、代码、文档） | **必须混合** |
| 纯自然语言问答、语料是叙述性文本 | 纯向量可能够 |
| 多语言检索 | 向量为主，BM25 帮助有限 |
| 用户查询里常带 ID、编号 | **必须混合** |

**判据很简单：把你真实查询里带专名或编号的那部分单独拉出来，测纯向量的 recall。** 明显低于整体就说明需要混合。

### 稀疏向量：第三条路

BM25 之外还有一类「学习出来的稀疏表示」（把文本映射到词表维度的稀疏向量，但权重是模型学的）。它介于 BM25 和 dense 之间：既有精确匹配能力，又有一定的语义泛化。

BGE-M3 那类模型可以**在一次编码里同时产出稠密和稀疏向量**，等于把混合检索的两条路合并了，工程上省事不少，见 [[02-Embedding 模型选型与评估]]。

### 和切分策略要配对

递归切分会切断语义，但 BM25 能靠关键词把它捞回来——**所以递归切分配混合检索是自洽的组合**。语义切分本来就是按向量相似度分的边界，配纯向量更一致，见 [[01-Chunking 四种策略]]。

**换切法要重测混合检索的收益**，两者不是独立的。

### 工程上要注意的

**两路要并行发起。** 串行的话延迟直接翻倍。

**各自的 top-k 可以不同。** 通常 BM25 取多一点（它便宜），向量取少一点。

**融合之后再重排。** RRF 给的是粗排结果，精排交给 cross-encoder，见 [[04-Rerank（cross-encoder 精排）]]。

**要分别监控两路的召回贡献。** 如果 BM25 那一路长期没有独立贡献（它召回的都被向量也召回了），那它就是纯开销，可以考虑去掉。反过来贡献很大，说明语料里专名很多，值得再往这个方向优化。

## 动手做

- [ ] 建纯向量基线，测 recall@10
- [ ] 加 BM25 走 RRF 融合，再测一次，看提升多少
- [ ] 把查询按「含不含专名/编号」分成两组，分别测两种方案的 recall
- [ ] 统计 BM25 的独立贡献：它召回但向量没召回的比例
- [ ] 试一次加权融合，对比无参数 RRF——多数情况下差别不大
- [ ] 确认两路是并行发起的，测延迟开销

## 算学会了

- [ ] 把混合检索当基线而不是优化项
- [ ] 能解释为什么 RRF 不需要分数归一化
- [ ] 会用「含专名的查询单独测 recall」判断是否需要混合
- [ ] 知道切分策略和检索方式要配对
- [ ] 监控 BM25 的独立贡献，判断它值不值这个开销

## 坑

**纯向量方案上线。** 专名、编号、错误码类查询的 recall 可能低得吓人，而通用评测测不出来。

**加权融合前不做归一化。** 两边的分数量纲不同，直接加是错的。

**串行发起两路检索。** 延迟翻倍。

**融合完就直接给模型。** RRF 是粗排，还该过一遍重排。

**换了切法不重测混合检索的收益。** 两者是配对的。
