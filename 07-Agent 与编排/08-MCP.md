每接一个新工具就写一遍适配代码，换个 agent 框架又得重写一遍。MCP 想解决的就是这个 N×M 问题。

## 一句话

MCP 是模型与外部能力之间的标准接口；**2026-07-28 的版本把它从有状态协议改成了无状态的请求/响应协议**，这是它发布以来最大的一次改动。

## 原理

### 它解决什么

没有标准协议时，接入 M 个工具到 N 个 agent 框架要写 N×M 份适配。MCP 把它变成 N+M：工具方实现一次 server，框架方实现一次 client。

三类能力：

| 概念 | 是什么 |
| --- | --- |
| **Tools** | 模型可以调用的函数，见 [[05-工具合约五段式模板]] |
| **Resources** | 模型可以读取的数据（文件、数据库记录） |
| **Prompts** | 可复用的提示词模板 |

采用度上，官方 SDK 的下载量已经是每月数亿次的量级，TypeScript 和 Python 两个 SDK 各自累计超过十亿次下载。

### 2026-07-28 那次改版

> [!warning] 协议核心从有状态改成了无状态
> 这是 MCP 发布两年来最大的一次修订。原本它是**双向有状态**的协议，现在核心变成了**请求/响应式的无状态**协议。
>
> 官方的说法是这两年攒下来的「惨痛教训」——有状态协议在可靠性和横向扩展上很吃亏：连接断了状态就没了、负载均衡后请求可能打到没有状态的实例、服务重启就得重连。
>
> **如果你手上有基于旧规范的实现或文档，它对协议核心的描述已经过时了。**

同一版还有几个重要变化：

- **受治理的扩展机制**——把非核心能力挪到扩展里，核心保持精简
- **授权加固**——安全模型收紧
- **正式的废弃策略**——以后的破坏性变更有明确流程
- **Tasks 移出实验性核心**，进入独立扩展
- **动态客户端注册被正式废弃**，改用新的身份机制
- **旧的 HTTP+SSE 传输被正式废弃**，给了一年的过渡期

**看到「MCP 用 SSE 传输」这类说法，先确认它是什么时候写的。**

### 安全上要当心什么

MCP 把外部能力接进来的同时，也把外部内容接进来了。三个面：

**一、工具描述本身是注入面。** 动态加载的 server 提供的工具描述会进模型上下文。恶意的 server 可以在描述里塞指令，见 [[01-间接提示注入与 20 条攻击载荷]]。

**二、工具返回值是注入面。** 这是间接注入最典型的通道之一。

**三、权限边界要自己划。** 协议本身不替你做最小权限——接了一个 server 不等于该给它全部权限，见 [[02-纵深防御]]。

务实的做法：

- **只接可信来源的 server**，第三方 server 当不可信内容处理
- **每个 server 单独授权**，不共享凭证
- **工具描述过一遍审查**，尤其是自动发现的
- **写操作仍然要人确认**

### 什么时候值得用

| 场景 | 建议 |
| --- | --- |
| 自己写的几个工具、单一框架 | **直接写函数**，MCP 是多余的抽象 |
| 需要复用别人写好的 server | 值得 |
| 多个 agent 框架共用同一批工具 | 值得 |
| 要把自己的能力开放给别人的 agent | 值得——这是它最强的场景 |

**别为了用 MCP 而用 MCP。** 三个自己写的工具接进一个自己写的 agent，直接调函数更简单、更好调试、也没有协议开销。

### 工具数量的问题一样存在

接了 MCP 之后工具数量容易失控——一个 server 可能暴露几十个工具。工具越多选择准确率越低，见 [[08-工具数量与工具检索]]。

所以要**按需加载**：这个任务需要哪些 server 就接哪些，而不是把所有 server 都挂上。

## 动手做

- [ ] 先判断你的场景值不值得用 MCP，而不是默认要用
- [ ] 读 2026-07-28 版规范，特别看无状态那部分和你的假设差在哪
- [ ] 接一个第三方 server，检查它暴露了多少工具、描述里有没有可疑内容
- [ ] 验证每个 server 是单独授权的，凭证不共享
- [ ] 把一条注入载荷放进某个 MCP 工具的返回值，看会不会被执行
- [ ] 统计接入 MCP 前后的工具总数与选择准确率变化

## 算学会了

- [ ] 知道 MCP 解决的是 N×M 问题，也知道什么时候它是多余的
- [ ] 清楚 2026-07-28 之后协议核心是无状态的
- [ ] 把第三方 server 的工具描述和返回值当不可信内容
- [ ] 每个 server 单独授权，按需加载而非全接
- [ ] 接入后会重测工具选择准确率

## 坑

**照着旧规范写。** 协议核心已经从有状态改成无状态，旧文档的描述是错的。

**信任第三方 server 的工具描述。** 那是一条注入通道。

**所有 server 都挂上。** 工具数量爆炸，选择准确率下降。

**为了用而用。** 自己的几个工具接自己的 agent，直接写函数更好。

**以为协议帮你做了权限管理。** 最小权限仍然要自己划。
