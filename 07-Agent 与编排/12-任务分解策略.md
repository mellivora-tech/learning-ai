「把大任务拆成小任务」听起来是废话。但拆到什么粒度、由谁来拆、拆错了怎么办——这几个问题决定了 agent 能不能跑完。

## 一句话

拆的粒度判据是**「这一步能不能被客观验证」**；验证不了的步骤拆得再细也没用，因为 agent 不知道自己做没做对。

## 原理

### 三种拆法

| 谁拆 | 怎么做 | 适合 |
| --- | --- | --- |
| **人预先拆** | 写死流程，agent 只执行每一步 | 流程稳定的任务——**优先选这个** |
| **模型动态拆** | 让模型先出计划再执行 | 任务形态多变 |
| **边做边拆** | 不预先规划，走一步看一步 | 探索性任务 |

**能用第一种就别用后两种。** 人预先拆的流程可预测、可测试、可优化，而且成本最低，见 [[09-多 Agent 编排模式]]。

现实中常见的是混合：**大框架人定，某一步内部让模型自己拆**。

### 拆到什么粒度

判据只有一个：**这一步的结果能不能被客观验证？**

| 步骤 | 能验证吗 | 拆得对吗 |
| --- | --- | --- |
| 「分析这份文档」 | 不能 | ✗ 太粗 |
| 「抽出发票号、金额、日期三个字段」 | 能——schema 校验 | ✓ |
| 「写一段查询」 | 能——EXPLAIN 跑一下 | ✓ |
| 「让代码更好」 | 不能 | ✗ |
| 「让测试通过」 | 能——跑测试 | ✓ |

**能验证的步骤才能形成反馈回路**，agent 才有机会自我纠错，见 [[01-Harness engineering]]。验证不了的步骤，拆得再细也只是把一次瞎猜变成几次瞎猜。

这也和终止条件是同一个道理：**完成必须是可观测的状态转换**，见 [[02-终止条件]]。

### 动态拆的两个坑

**一、计划本身可能是错的。** 模型出的计划看起来很合理，执行到第三步才发现前提不成立。所以：

- **计划要能被修正**，而不是定死之后硬着头皮走完
- **每步执行后重新评估剩余计划**
- 但**重新规划的次数要有上限**，否则会陷入「规划-发现不对-重新规划」的循环，见 [[02-终止条件]]

**二、计划会膨胀。** 模型倾向于把任务拆得很细，十几二十步。步数一多，成本和失败概率都上去了。

**限制计划的步数上限**，逼它拆得粗一些。

### 拆完之后：并行还是串行

能并行的一定要并行——延迟直接除以并行度：

```text
串行：抽取 → 校验 → 汇总 → 生成报告        总耗时 = 各步之和
并行：抽取 A ┐
     抽取 B ├→ 汇总 → 生成报告            总耗时 = max(各分支) + 后续
     抽取 C ┘
```

判断标准是**依赖关系**：B 需不需要 A 的结果。不需要就并行。

实测上，**带并行的子 agent 模式比逐个交接的模式省三分之一以上的 token**，因为交接本身要传上下文，见 [[09-多 Agent 编排模式]]。

### 每个子任务要自带三样东西

拆出来的子任务如果只有一句描述，执行的 agent 会缺信息。至少要带：

| 要素 | 为什么 |
| --- | --- |
| **输入** | 明确的、结构化的，而不是「参考上文」 |
| **成功判据** | 怎么算做完了，见 [[02-终止条件]] |
| **预算** | 分到多少步数、多少钱，见 [[01-五类硬预算]] |

**第一项决定了能不能上下文隔离。** 输入写成「参考上文」的话，子任务就必须带着完整历史，隔离的收益就没了，见 [[02-Context engineering：上下文即预算]]。

### 失败怎么办

子任务失败时有三个选项，要预先定义清楚：

- **重试**——适合瞬时故障
- **降级**——用更简单的方式做，见 [[04-降级链]]
- **上报**——交给上层重新规划，或者转人工，见 [[03-升级到人与结构化中间状态]]

**默认不要无脑重试。** 如果是规划错了（这一步根本做不到），重试多少次都不会成功。判断依据是失败类型——同一类错误连续出现，说明该上报而不是重试。

## 动手做

- [ ] 拿一个真实任务，人工拆一版流程，和让模型动态拆对比成本与成功率
- [ ] 检查每个步骤：它的结果能不能被客观验证？不能的话重新拆
- [ ] 画出依赖图，找出能并行的分支，测延迟改善
- [ ] 给每个子任务补上输入、成功判据、预算三样
- [ ] 限制动态规划的步数上限，看会不会逼出更粗但更可靠的计划
- [ ] 构造一个「计划前提不成立」的场景，验证能重新规划且有次数上限

## 算学会了

- [ ] 拆的粒度判据是「能不能被客观验证」
- [ ] 能用人预先拆就不用模型动态拆
- [ ] 每个子任务自带输入、成功判据、预算
- [ ] 会画依赖图找并行机会
- [ ] 子任务失败时按失败类型决定重试、降级还是上报

## 坑

**拆出验证不了的步骤。** 「分析一下」这类步骤没有反馈回路，agent 无法自纠。

**默认让模型动态拆。** 流程稳定的任务人写死更省更稳。

**子任务的输入写成「参考上文」。** 上下文隔离的收益全没了。

**能并行的串行做。** 延迟白白翻几倍。

**失败就无脑重试。** 规划错了的话，重试永远不会成功。
