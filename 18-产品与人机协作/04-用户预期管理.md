同一个 85% 准确率的系统，可以被当成「挺好用」，也可以被当成「完全不能信」——差别只在用户以为它该有多准。

## 一句话

**用户对系统的信任应该和它的实际可靠度匹配**——高估会导致不加检查地采信，低估会导致这个功能没人用。

## 原理

### 两种错配

| 错配 | 后果 |
| --- | --- |
| **用户高估** | 不加检查地采信，出事时后果严重、信任崩塌 |
| **用户低估** | 每次都全量复核，系统白做 |

**高估的破坏力更大**：一次严重的失败会让用户从高估直接跳到完全不用，中间没有过渡。

### 把不确定性做进界面

比「在帮助文档里写一句免责声明」有效得多的做法：

| 做法 | 说明 |
| --- | --- |
| **给出依据** | 有引用的结论天然比没引用的可信，用户自己会判断，见 [[06-幽灵文档测试]] |
| **区分「找到了」和「没找到」** | 「文档里没有相关内容」比编一个答案好得多 |
| **标出低置信** | 「这一项我不太确定，建议核对」 |
| **展示中间过程** | 用户能看到它查了什么、怎么推的，见 [[04-流式与可中断 UX]] |
| **明确能力边界** | 「我能查产品文档，不能查订单状态」 |

**第二条是最重要也最容易做错的**。模型默认倾向于给一个答案，要显式地训练/约束它说「不知道」，见 [[01-结构化输出三档]]。

而说「不知道」的代价往往被高估了——**用户对「诚实地说没找到」的容忍度，远高于对「自信地说错」的容忍度。**

### 别承诺你没测过的东西

产品文案里的每一句能力描述，都应该有 golden set 里的对应样本，见 [[01-Golden set]]：

- 说「支持复杂表格」→ eval 里要有复杂表格
- 说「支持中英文」→ 两种语言都要测
- 说「能处理扫描件」→ 扫描件要在测试集里

**没测过的能力不要写进文案。** 用户会按文案去用，然后在你没覆盖的地方翻车。

### 失败要失败得体面

系统总会失败，关键是失败时用户感受如何，见 [[06-降级 UX]]：

| 失败方式 | 用户感受 |
| --- | --- |
| 编一个错答案 | **最糟**——用户可能不会发现 |
| 转圈半天然后报错 | 差——浪费了时间 |
| **快速说「这个我处理不了，转人工」** | **可接受** |
| 给出部分结果并说明缺什么 | 好 |

**「快速失败」比「慢慢失败」好得多**，见 [[03-超时与背压]]。用户等了两分钟才看到报错，会比等了两秒就看到愤怒得多。

### 首次使用最关键

用户对系统能力的判断，主要在头几次使用时形成，之后很难改变。所以：

- **引导用户从系统擅长的场景开始**——给示例、给模板
- **别把最难的场景放在首页**
- **首次失败要给明确的原因和替代路径**

**这不是「掩盖缺点」**——是让用户在建立正确心智模型之前，不要先形成一个错误的。

### 预期要随实际水平更新

系统改进了，要让用户知道；退化了，也要让用户知道：

- 能力扩展时更新文案和示例
- **模型更新导致行为变化时要说明**，见 [[03-漂移监控三条线]]
- 已知问题公开列出来

**最后一条反直觉但有效**：公开「我们知道这类情况处理不好」比让用户自己撞上去，对信任的伤害小得多。

## 动手做

- [ ] 调研用户当前对系统准确率的估计，和实测值对比
- [ ] 检查系统在「找不到」时是否会编答案
- [ ] 给每个结论加上依据，让用户能自己判断
- [ ] 逐条核对产品文案里的能力描述，确认 eval 里都有对应样本
- [ ] 测失败路径的耗时，把慢失败改成快失败
- [ ] 给首次使用的用户设计从擅长场景开始的引导
- [ ] 公开一份已知限制清单

## 算学会了

- [ ] 知道用户的预期和实际水平差多少
- [ ] 系统会诚实地说「没找到」而不是编答案
- [ ] 文案里的每个能力都有 eval 覆盖
- [ ] 失败是快的，且给出替代路径
- [ ] 有公开的已知限制清单

## 坑

**靠免责声明管理预期。** 没人读，也不影响实际使用行为。

**让系统在找不到时编答案。** 用户对「自信地说错」的容忍度远低于「诚实地说没找到」。

**文案承诺没测过的能力。** 用户会按文案去用，然后在你没覆盖的地方翻车。

**慢失败。** 等两分钟看到报错，比等两秒愤怒得多。

**把最难的场景放在首页。** 首次印象很难改变。
