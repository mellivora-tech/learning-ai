「让人来把关」听起来很稳妥，但如果把关的成本和自己做差不多，那这个系统就白做了。

## 一句话

人机协作的价值取决于**复核比重做便宜多少**——所以设计的核心是让人快速判断对错，而不是让人重新读一遍。

## 原理

![[HITL 三种介入形态.excalidraw.md|700]]

### 先算这笔账

$$
\text{净收益} = \text{人工独立完成耗时} - \text{复核耗时} - \text{修正耗时} \times \text{错误率}
$$

**如果复核耗时接近独立完成的耗时，这个系统没有价值。** 常见的失败形态：模型生成一份报告，人得从头读一遍才知道对不对——那还不如自己写。

所以设计目标不是「让人看一眼」，而是**让人在几秒内知道该不该信**。

### 让复核变便宜的几个手段

| 手段 | 说明 |
| --- | --- |
| **可追溯** | 每个结论能一键跳到来源，见 [[06-幽灵文档测试]] |
| **高亮不确定的部分** | 只让人看该看的地方 |
| **结构化而非散文** | 字段清单比一段话好核对，见 [[01-结构化输出三档]] |
| **交叉校验的结果一起给** | 「模型说 1250，OCR 也读到 1250」，见 [[02-OCR pipeline]] |
| **差异视图** | 修改类任务给 diff，不给全文 |

**前两条收益最大**。可追溯把「读一遍验证」变成「点一下确认」；高亮不确定处把复核范围从全文缩到几个点。

### 三种介入形态

| 形态 | 什么时候 |
| --- | --- |
| **事前确认** | 不可逆操作——付款、发邮件、删数据 |
| **事中接管** | 长任务跑偏时，见 [[03-升级到人与结构化中间状态]] |
| **事后抽检** | 低风险、高频量，抽样复核 |

**按错误代价选**，见 [[02-任务可行性判断]]。不可逆操作必须事前确认，没有例外。

### 确认要给足信息

最糟的确认框是「确定要执行吗？[是][否]」——它把责任转移给了人，但没给人做判断的依据。

好的确认要说清：

- **具体要做什么**（不是「发送邮件」，而是收件人、主题、正文）
- **不可逆在哪里**（「发出去撤不回」）
- **模型为什么这么判断**（依据的是哪条信息）
- **一键修改**，而不是只能同意或拒绝

**最后一条很关键**：只能二选一时，人遇到「大体对但有个小错」只能拒绝，然后整个任务重来。允许修改能救回大量本来会被丢弃的结果。

### 警惕自动化偏见

人对「大部分时候都对」的系统会逐渐放松警惕，最后变成无脑点确认。这时候人机协作只剩形式，风险照旧。

对策：

- **别让确认变成机械动作**——高风险的确认要求输入具体内容而非只点按钮
- **抽检复核者**——往里混入已知错误的样本，看有没有被抓出来
- **监控确认耗时**——中位数掉到一两秒说明没人在真看
- **别对低风险项也要求确认**——确认疲劳会传染到高风险项

**第二条是最有效的**，而且顺便给了你一批标注数据，见 [[05-标注流程]]。

### 人的操作是最好的信号

用户改了什么、拒绝了什么、接受了什么——这些是免费且高质量的训练与评估数据，见 [[06-用户信号如何变成 eval 与训练数据]]。

所以交互设计时就要考虑**怎么把这些动作记下来**：

- 改动前后的完整对比
- 拒绝时的原因（给几个常见选项，比自由文本好统计）
- 关联到那次调用的 trace，见 [[01-Trace 与 Span]]

**这一步在交互设计阶段做很便宜，事后补很贵**——因为事后没有原始上下文了。

## 坑

**只让人「看一眼」。** 如果得从头读，还不如自己写。

**确认框只有是/否。** 人遇到小错只能拒绝，整个结果被浪费。

**对低风险操作也要求确认。** 确认疲劳会传染到高风险项。

**不管自动化偏见。** 系统越准，人越不看，最后只剩形式。

**不记录用户操作。** 白扔了最高质量的一批数据，且事后补不回来。
