显存明明还剩 20 GB，新请求却进不来。这不是算错了，是碎片——而解法是操作系统四十年前就用过的那个。

## 一句话

把 KV cache 从「按最大长度预留一整块连续显存」改成「按固定大小的块按需分配」，浪费从六成以上降到最后一块的零头。

## 原理

### 朴素做法为什么这么亏

KV cache 会随生成不断增长，见 [[02-KV cache 为什么存在]]。而 attention 计算希望它在显存里是连续的。

于是最直接的做法是：请求进来时，按 `max_model_len` 预留一整块连续显存。

问题在于**绝大多数请求根本用不满**：

![[按最大预留与按块分配.excalidraw.md|700]]

vLLM 论文里量化过这种浪费——**实测可以超过六成**。分三类：

- **内部碎片**：预留 8k 只用了 500，剩下 7500 个位置的显存被占着不能给别人
- **外部碎片**：显存总量够，但没有一块足够大的**连续**空间
- **无法共享**：两个请求有相同的前缀，各存一份

### 分页怎么解决

**PagedAttention** 的做法和操作系统的虚拟内存一模一样：

1. 把 KV cache 切成固定大小的**块**（block，比如 16 个 token 一块）
2. 每个请求维护一张**块表**，记录它的第 N 段 token 在哪个物理块里
3. 物理块**不要求连续**，用完哪块还哪块
4. attention kernel 改写成能按块表跳着读

于是：

| | 朴素做法 | 分页 |
| --- | --- | --- |
| 内部碎片 | 预留多少浪费多少 | 只剩最后一块的零头（平均半块） |
| 外部碎片 | 有 | **没有**——块一样大，任意块可互换 |
| 前缀共享 | 做不到 | **能**——两个请求的块表可以指向同一个物理块 |

第三行是额外的收获，也是 [[05-Prefix caching]] 的实现基础。

### 块大小是个取舍

- **块小**：浪费少，但块表变长、索引开销变大
- **块大**：索引快，但最后一块的零头变大

16 是常见的默认值。除非有明确的实测理由，不建议动它。

### 它怎么改变你的容量计算

有了分页之后，[[03-KV cache 管理与显存测算]] 里手算出来的并发上限**是保守下界**：

- 手算假设每个请求都吃满目标长度
- 实际请求长度分布很偏，多数远没用满
- 分页把那些没用满的空间还给了别人

所以实测并发通常比手算高，而且**请求长度分布越不均匀，分页赚得越多**。

反过来说，如果你的请求长度高度一致（比如批量处理固定格式的文档），分页的收益就小得多——因为本来就没什么浪费可省。

### 抢占：显存还是会满

分页让显存用得更省，但没有让它变多。并发继续加，还是会满。

满了之后引擎必须踢掉某些请求腾地方，这就是抢占。踢的方式和代价见 [[06-驱逐与内存压力]]。

分页在这里也有帮助：**块的粒度让抢占可以更细**——不一定要踢掉整个请求，理论上可以只换出一部分块。

### 实践上要注意的

**`gpu_memory_utilization` 决定了引擎能用多少。** 默认 0.9，剩下 10% 留给激活值和 CUDA context。调高能多装 KV cache，但调太高会在峰值时 OOM。

**分页不是免费的。** 块表查找、非连续内存访问都有开销，attention kernel 要专门写。好在这部分已经被引擎实现好了，用就行。

**监控 `gpu_cache_usage_perc`。** 它是判断「还能不能再加并发」的直接依据，压到接近 1.0 说明到顶了。

## 坑

**以为分页凭空变出了显存。** 它消除的是浪费，总量没变。并发继续加还是会满。

**手算完就当结论。** 分页之后实测通常更高，按手算配容量会低估。

**把 `gpu_memory_utilization` 调到 0.98。** 峰值时激活值挤不下，直接 OOM。

**在长度一致的负载上期待分页有大收益。** 本来就没多少浪费可省。

**忘了它只管 KV cache。** 权重和激活值不在分页范围内，那部分还是老样子。
