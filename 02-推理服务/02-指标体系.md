「这个服务快不快」是个没法回答的问题。得先问：你说的是首字快，还是吐字快，还是单位时间处理得多？这三件事经常互相拆台。

## 一句话

延迟和吞吐是一对儿此消彼长的量，而延迟本身还得拆成 TTFT 和 TPOT——只报一个平均延迟，等于把三个互相矛盾的东西糊成一个数。

## 原理

### 六个指标，各回答一个问题

| 指标 | 全称 | 回答什么 |
| --- | --- | --- |
| **TTFT** | Time To First Token | 发出请求到看见第一个字要多久 |
| **TPOT** | Time Per Output Token | 后面每个字之间隔多久 |
| **端到端延迟** | | 整个请求从发出到收完 |
| **吞吐（req/s）** | | 单位时间处理完多少个请求 |
| **吞吐（token/s）** | | 单位时间吐出多少 token |
| **并发数** | | 同时在处理多少个请求 |

端到端延迟不是独立的，它由前两个推出来：

$$
\text{端到端} \approx \text{TTFT} + \text{TPOT} \times (\text{输出长度} - 1)
$$

**这个公式很有用**：输出 500 个 token 时，TPOT 每降 1ms，端到端就省半秒。而 TTFT 降 10ms 几乎看不出来。**优化哪一头，取决于你的输出有多长。**

### TTFT 和 TPOT 由不同的东西决定

| | 受什么影响 | 属于哪个阶段 |
| --- | --- | --- |
| TTFT | 输入长度、排队时间、有没有命中前缀缓存 | prefill，compute-bound |
| TPOT | batch 大小、上下文长度、模型大小、显存带宽 | decode，memory-bound |

两阶段的性质对比见 [[01-Prefill vs Decode]]。这里只强调一个后果：**改善 TTFT 和改善 TPOT 是两套手段，混着用会互相抵消**。

比如加大 batch：TPOT 的吞吐上去了，但新请求要等更久才被调度，TTFT 变差。

### 平均值会骗人，必须看分位

尾延迟是 LLM 服务里最容易失控的东西。原因很具体：

- 一个超长 prompt 的 prefill 会占住 GPU 几百毫秒，**期间所有 decode 中的请求都被卡住**
- 显存满了触发抢占，被踢掉的请求要重来，见 [[06-驱逐与内存压力]]
- 请求长度分布很偏，长尾请求天然慢

所以要报 **P50 / P95 / P99**，而且 TTFT 和 TPOT 各报一套。只报平均值的压测报告基本没有参考价值——**平均 TPOT 30ms、P99 500ms 的系统，用户体验是「经常卡住」，不是「挺流畅」**。

### 吞吐怎么算才有意义

`token/s` 和 `req/s` 是两个不同的口径：

- **token/s** 适合对比硬件和模型配置——它直接对应显存带宽的利用效率
- **req/s** 适合对比业务容量——但它强烈依赖请求的长度分布

**跨系统比较时一定要说明请求分布。** 平均输出 50 token 的系统和平均输出 500 token 的系统，req/s 差十倍是正常的，不说明谁快。

还有一个更实用的口径：**goodput**——单位时间内**满足 SLO** 的请求数。吞吐再高，如果一半请求超时了，那部分产能是废的。它和「每次成功任务成本」是同一种思路，见 [[04-成本归因与每次成功任务成本]]。

### 压测要怎么做才算数

几条容易被忽略的：

**用真实的请求长度分布。** 全用 128 token 的输入压出来的数字，和线上（大量短请求 + 少量超长请求）完全对不上。

**区分开环和闭环。** 闭环压测（等上一个回来再发下一个）会自动限流，测不出系统过载时的行为；开环（按固定速率发）才能压出真实的排队和尾延迟。

**要压到饱和。** 只在低并发下测，看不到吞吐-延迟的拐点在哪，见 [[10-吞吐-延迟帕累托前沿]]。

**记录并发数而不只是 QPS。** 同样的 QPS 下，请求变长会让并发数上升，进而改变一切。

### 这些指标要打进 trace

线上要能按维度下钻——某个租户的 TTFT 塌了，全局平均可能纹丝不动。字段清单见 [[02-必打字段清单]]，监控做法见 [[03-漂移监控三条线]]。

## 动手做

- [ ] 用真实的长度分布做一次开环压测，同时记录 TTFT 和 TPOT 的 P50/P95/P99
- [ ] 固定输出长度，扫输入长度，画 TTFT 曲线
- [ ] 固定输入长度，扫输出长度，画端到端延迟曲线，斜率就是 TPOT
- [ ] 把并发从 1 加到饱和，画吞吐-延迟曲线，找出拐点
- [ ] 在稳定负载中插入一个超长 prompt，观察其他请求的 TTFT 和 TPOT 各抖多少
- [ ] 给定一个 SLO，算出你的 goodput，和裸吞吐对比

## 算学会了

- [ ] 报延迟时一定分开报 TTFT 和 TPOT，各带分位数
- [ ] 能用那个公式估算「TPOT 降 1ms 对端到端省多少」
- [ ] 知道加大 batch 会改善吞吐但恶化 TTFT
- [ ] 跨系统比吞吐时会先问请求长度分布
- [ ] 压测用开环、用真实分布、压到饱和

## 坑

**只报平均延迟。** 把三个互相矛盾的量糊成一个数，任何异常都看不出来。

**只报吞吐不报延迟。** 吞吐可以靠堆 batch 无限刷高，代价是尾延迟爆炸。

**闭环压测。** 自带限流，测不出过载行为，给出的数字过于乐观。

**用固定长度压测。** 和线上分布对不上，结论不能外推。

**比较 req/s 不说请求分布。** 这个数字脱离分布毫无意义。
