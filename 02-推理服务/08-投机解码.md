让一个小模型先猜几个字，大模型一次性验证。猜对了白赚，猜错了丢掉重来——听起来像稳赚，实际上高峰期你该把它关掉。

## 一句话

投机解码用**闲置的算力**换 decode 速度，所以只在算力有富余时有效——batch 一大，算力本来就吃满了，收益归零。

## 原理

### 它为什么能成立

decode 阶段是 memory-bound 的：每生成一个 token 要把全部权重搬一遍，算力大量空转，见 [[01-Prefill vs Decode]] 和 [[02-算力经常用不满：两种瓶颈]]。

关键洞察是：**验证 5 个 token 和验证 1 个 token，搬的权重一样多。** 因为都只需要读一遍权重，而多算几个位置对 GPU 来说几乎免费。

于是：

1. 一个便宜的**草稿模型**快速猜出接下来 $k$ 个 token
2. 大模型**一次前向**同时验证这 $k$ 个位置
3. 从头开始比对：猜对的直接采纳，第一个猜错的位置纠正过来，后面的丢掉

数学上可以做到**输出分布和不用投机时完全一致**——这不是近似加速，是无损的。

### 草稿从哪来

| 做法 | 怎么产生草稿 | 特点 |
| --- | --- | --- |
| 独立小模型 | 跑一个同族的小模型 | 通用，但要额外显存和一次完整前向 |
| **EAGLE 系** | 用目标模型的中间层特征，配一个极轻的头 | 接受率高、开销小，目前工程上的主流 |
| n-gram / 提示词查找 | 直接从上下文里找重复片段 | 几乎零开销，只在有大量重复时有效 |

最后一种在特定场景出奇地好用：让模型改写一段给定文本、或者输出大量引用原文的内容时，重复率极高。

### 收益取决于两个数

**接受率**——草稿平均能被采纳几个。它取决于草稿模型和目标模型有多像，**和硬件无关**——换代 GPU 不会改变接受率。

**batch 大小**——这是那个反直觉的部分。

> [!warning] batch 一大，收益就没了
> EAGLE-3 在低 batch 下能把出字速度做到三到四倍。但**到 batch 64 以上，吞吐收益基本可以忽略**。
> 原因回到那条主线：投机解码花的是算力，赚的是带宽。低 batch 时算力大量空转，多算几个位置不要钱；batch 大到算力本来就吃满时，草稿和验证的额外计算变成了真实开销，反而拖慢整体。
> **所以它是一个「低并发时的延迟优化」，不是「吞吐优化」。**

这直接给出了那个运维判断：**高峰期该关掉它，低谷期开着。** 或者做成按当前 batch 大小动态开关。

### 另一个坑：分布外就退化

投机解码在受控环境里表现很好，换到真实流量就可能打折。EAGLE 团队把这个现象归因为 **attention drift**——草稿模型在遇到不同的 chat template、长上下文输入、或者没见过的 system prompt 时，接受率会明显下降。

EAGLE 3.1（2026 年 5 月，EAGLE、vLLM、TorchSpec 三方合作）通过在每个目标隐状态后加 FC 归一化、并把归一化后的隐状态喂进下一步来缓解这一点。

工程上的含义：**必须用你自己的真实流量测接受率**，别信论文里的数字。你的 system prompt 和上下文长度和它们不一样。

### 什么时候值得上

**值得**：交互式场景、低到中等并发、对首字后的流畅度敏感、有闲置算力。

**不值得**：高并发批处理（算力已经吃满）、显存本来就紧张（草稿模型也要占显存）、请求分布特别杂（接受率上不去）。

**先做别的**：连续批处理、前缀缓存、量化这三样的收益更确定也更普适，做完再考虑投机解码。它属于「前面都做完了还想再快一点」的那一档。

## 坑

**以为它总是有用。** 高并发时它是负优化。不测翻转点就全局开启，高峰期反而更慢。

**信论文里的接受率。** 你的 chat template、system prompt、上下文长度都不一样，实测通常更低。

**忘了草稿模型也占显存。** 在显存本来就紧张的配置上，这部分可能挤掉 KV cache，反而降低并发。

**当成吞吐优化。** 它是低并发下的延迟优化，两者的适用场景相反。

**跳过前面几项直接上它。** 连续批处理和前缀缓存的收益更确定，先做那些。
