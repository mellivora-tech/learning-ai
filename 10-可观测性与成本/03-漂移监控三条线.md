CI 门禁挡的是「已知的错误再次发生」。而线上真正难受的那类问题是：什么都没改，它自己慢慢变差了。

## 一句话

盯三条线——输入分布、输出质量、检索命中率；其中第三条的缓慢下滑通常是索引腐化的第一个信号，而它不会报错。

## 原理

### 为什么会「什么都没改却变差」

代码没动，提示词没改，模型版本也锁着，效果却在退。可能的原因：

- **用户变了**——新功能上线带来了新的提问方式，或者用户学会了新的用法
- **数据变了**——知识库加了新文档、删了旧文档、格式换了
- **模型变了**——闭源 API 背后在持续做后训练，见 [[00-模型是怎么来的]]
- **世界变了**——用户问的事情本身有了新答案

这几类都不会触发 CI，因为 CI 跑的是固定的 golden set。**要靠线上监控发现。**

### 第一条：输入分布

监控进来的东西有没有变。看这些：

| 看什么 | 变了说明 |
| --- | --- |
| 请求长度分布 | 用户开始粘贴长文档了？上下文预算够不够 |
| 语言 / 语种占比 | 新市场？分词膨胀会推高成本，见 [[03-Tokenization]] |
| 意图分类占比 | 有一类新问法涌现 |
| 新词 / 未登录词比例 | 出现了系统没见过的实体 |

技术上可以用 PSI（群体稳定性指数）或 KL 散度这类分布距离指标，但**先做简单的**：把请求按 embedding 聚类，看各簇的占比周变化。有新簇冒出来或者某个簇占比翻倍，就值得看一眼。

输入漂移本身不是问题，它是**预警**——它告诉你 golden set 可能已经不代表真实流量了，见 [[01-Golden set]]。

### 第二条：输出质量

线上没有标准答案，所以只能用代理指标：

**可自动判定的**（便宜，全量跑）：

- JSON 解析成功率、schema 合规率
- `finish_reason` 分布，尤其是 `length` 截断的占比
- 输出长度分布——突然变长或变短都是信号
- 重试次数、修复循环触发率
- 拒答率

**需要 judge 的**（贵，抽样跑）：

- 抽样打分，见 [[04-Judge 校准]]
- groundedness 抽检，见 [[06-检索评估两段式]]

**用户信号**（免费但有噪声）：

- 点踩、重新生成、放弃、复制走了没有

这三类的组合很关键：**自动指标全量跑当哨兵，judge 抽样跑看趋势，用户信号定位问题区域。** 用户信号异常的那批请求，正好是拿去做人工评估的最佳样本，见 [[05-人工评估作为校准工具]]。

### 第三条：检索命中率

这条最容易被忽略，也是最有价值的一条。

监控这几个：

- **平均 top-1 相似度分数**——缓慢下滑意味着查询越来越找不到好匹配
- **低分召回占比**——最高分低于阈值的查询比例
- **零召回率**——什么都没找到的比例
- **重排后位次变化幅度**——重排一直在大改顺序，说明初排质量在退

> [!warning] 索引腐化不会报错
> 这是本篇最该记住的一句。索引出问题时，检索**照常返回结果**，只是返回的东西越来越不相关。没有异常、没有告警、没有堆栈——只有答案慢慢变差。
> 常见成因：新文档没进索引、删除的文档没传播（见 [[05-Freshness 与 tombstone 删除传播]]）、embedding 模型换了但没重建全量索引、chunk 策略改了导致新旧文档不一致。
> **平均相似度分数的缓慢下滑，通常是唯一的早期信号。**

### 告警怎么设

漂移是慢变量，用固定阈值会一直误报或者一直不报。做法：

- **和自己的历史比**，不和绝对值比。比如「7 日均值相对 30 日均值下降超过 X%」
- **按维度拆**。总体平稳但某个租户或某个 feature 在塌，全局指标看不出来——这是 `tenant_id` 和 `feature` 必打的原因，见 [[02-必打字段清单]]
- **分快慢**。JSON 合规率这种该立刻告警，相似度分数下滑该走周报

### 发现之后怎么办

漂移监控的输出应该接回评估闭环：

1. 定位到具体是哪一类输入 / 哪个租户 / 哪个 feature 在退
2. 从那批请求里抽样做人工评估，确认是真退了还是指标误报
3. 确认之后，**把这批样本补进 golden set**，见 [[01-Golden set]]
4. 修复，然后 CI 门禁保证它不再退回去

**监控发现新问题，golden set 保证老问题不复发。** 这两件事合起来才是完整的质量体系。

## 动手做

- [ ] 建三个看板：输入分布、输出质量代理指标、检索分数
- [ ] 检索那块至少要有：平均 top-1 分数、零召回率、低分召回占比
- [ ] 所有指标按 `tenant_id` 和 `feature` 拆开，别只看全局
- [ ] 告警用相对历史的变化率，不用绝对阈值
- [ ] 故意往索引里少灌一批文档，观察哪个指标先动、多久能看出来
- [ ] 走一次完整闭环：从告警定位到样本，人工确认，补进 golden set

## 算学会了

- [ ] 三条线都在看，尤其没漏掉检索命中率
- [ ] 知道索引腐化不会报错，只能靠分数下滑发现
- [ ] 指标按租户和 feature 拆开，全局平稳时也能发现局部塌陷
- [ ] 告警基于历史变化率而非绝对阈值
- [ ] 漂移发现的问题会回流成 golden set 的新样本

## 坑

**只监控错误率和延迟。** 传统后端的那套指标对 LLM 应用远远不够——质量退化不会体现为错误。

**不监控检索。** 索引腐化是最隐蔽的一类退化，而它只在检索指标里露头。

**只看全局指标。** 某个大租户的体验塌了，全局平均值可能纹丝不动。

**用绝对阈值告警。** 慢变量配固定阈值，结果不是天天报就是永远不报。

**监控和评估两张皮。** 监控发现的问题没有回流到 golden set，同一个问题会再出现。
