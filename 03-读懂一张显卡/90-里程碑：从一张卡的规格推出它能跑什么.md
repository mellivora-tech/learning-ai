## 交付物

一份一页纸的推演，加一次把它验证掉的压测。给定一张卡和一个模型，先**纯靠算**给出结论，再实测打脸或者对上：

- 最大并发数（受显存约束）——写出三笔账各占多少
- 单请求 decode 速度上限（受带宽约束）
- Prefill 吃 8k 输入要多久（受算力约束）
- 上下文开到 4 倍时，上面三个数各变成多少
- 实测值与推算值的比值，以及**差距的解释**

最后那一项才是这个里程碑的价值所在。算得准不准是其次，**说得清为什么不准**才说明你真懂这张卡。

## 做法

推算这一半有起步脚本，五个函数留空，填一个过一个：

```bash
python "_练习/03-从一张卡的规格推出它能跑什么.py"
```

不用装任何东西，也不用有卡——这半程全是算术。每关的裁判都是构造出来的极端输入或者能手算验证的性质，不是「和某个参照实现比」：

| 关 | 要填 | 谁当裁判 |
| --- | --- | --- |
| 1 | `weight_bytes` | 换精度时体积必须严格成比例 |
| 2 | `kv_bytes_per_token` | 把 KV 头数换成注意力头数，结果必须正好涨 4 倍 |
| 3 | `max_concurrency` | 上下文翻倍并发减半、换大显存卡并发变多、装不下时返回 0 |
| 4 | `decode_tokens_per_s` | H200 相对 H100 的加速比必须**正好等于带宽比**——算力混进公式就过不了 |
| 5 | `ridge_point` / `bottleneck` | 拐点落在 295 附近；算出 590 就是用了含稀疏的算力 |

五关都过之后脚本会打印整页推算，拿它去和下面的压测对照。

然后是真正花时间的另一半：

1. 挑一张手上能拿到的卡，抄下四个关键数字：显存、带宽、算力、互联，见 [[01-一张卡的四个关键数字]]
2. 挑一个模型，从 `config.json` 抄出层数、KV 头数、head_dim、参数量，见 [[02-开源权重包里有什么]]
3. 算显存：权重 + KV cache（按目标上下文和并发）+ 15–20% 余量，反推最大并发
4. 算带宽：显存带宽 ÷ 每 token 要搬的字节 = decode token/s 上限
5. 算算力：$2N \times T$ FLOP ÷ 卡的算力 = prefill 理论耗时
6. 把上下文乘 4，三个数重算一遍
7. 起服务压测，记实测值
8. 算达成率，解释差距

### 一页纸推算模板

```text
卡：__________      显存 ___ GB    带宽 ___ TB/s
                   BF16 算力 ___ TFLOPS    互联 ___ GB/s

模型：__________    参数 ___ B    层数 ___    KV 头 ___    head_dim ___

① 权重      BF16 = 参数×2 = ___ GB      FP8 = ___ GB      INT4 = ___ GB
② 每 token KV   2 × 层数 × KV头 × head_dim × dtype = ___ KB
③ 可用于 KV cache   显存 − ① − 约 15% 余量 = ___ GB
④ 并发上限（上下文 ___ k）   ③ ÷ (② × 上下文) = ___
⑤ decode 上限（batch=1）    带宽 ÷ ① = ___ token/s
⑥ 瓶颈判断   算术强度 ≈ batch 大小，与本卡拐点比较
             → prefill 落在 ______，decode 落在 ______
```

### 压测命令

```bash
vllm serve <模型> --max-model-len 8192 --gpu-memory-utilization 0.9

# 并发上限：压到 cache 接近满
curl -s localhost:8000/metrics | grep -E 'gpu_cache_usage_perc|num_requests_running'
```

对不上的四个常见原因，按出现频率排：

1. **KV 头数用成了 `num_attention_heads`**——GQA 下差好几倍，这是第一个要查的
2. 忘了 `gpu_memory_utilization` 默认 0.9，剩下 10% 引擎不碰
3. 忘了权重之外还有激活值和 CUDA context
4. 引擎悄悄开了 KV cache 量化，实际 dtype 不是你以为的那个
