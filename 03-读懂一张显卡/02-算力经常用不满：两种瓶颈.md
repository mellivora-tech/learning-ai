花几万美元买的算力，跑推理时经常只用上几个百分点。这不是配置没调好，是任务本身的形状决定的。

## 一句话

每从显存搬一个字节，H100 能做约 295 次浮点运算——喂不到这个比例，算力就在空转；而 decode 阶段的比例天然接近 1。

## 原理

### 算术强度：一个决定一切的比值

![[显存带宽与算力的两种瓶颈.excalidraw.md|700]]

任何计算任务都可以问一个问题：**每从内存搬 1 个字节，要做多少次运算？** 这个比值叫**算术强度**，单位是 FLOP/byte。

硬件也有一个对应的比值。H100 SXM 的 BF16 **稠密**算力约 989 TFLOPS，显存带宽 3.35 TB/s：

$$
\frac{989 \times 10^{12}}{3.35 \times 10^{12}} \approx 295 \text{ FLOP/byte}
$$

> [!warning] 规格表上那个 1979 不能直接用
> [NVIDIA 的 H100 产品页](https://www.nvidia.com/en-us/data-center/h100/)把 BFLOAT16 Tensor Core 写成 1,979 TFLOPS，但那一栏带星号，脚注是 *with sparsity*——开了**结构化稀疏**才有的数，稠密只有一半。
> 结构化稀疏要求权重按 2:4 的模式置零（每四个数里恰好两个为 0），模型得专门训练或剪枝成这个形状。推理常用的稠密权重吃不到这份加速。
> 拿 1979 去算拐点会得到 590，把门槛抬高一倍，于是所有「够不够喂饱」的判断都会偏。FP8 那栏的 3,958 同理，稠密是 1,979。

这个数叫**拐点**。任务的算术强度高于它，算力先到顶，叫 compute-bound；低于它，带宽先到顶，叫 **memory-bound**——这时候计算单元在干等数据，标称算力再高也没用。

> [!info] 一个比方
> 计算单元是个饭量极大的人，显存带宽是那根送饭的传送带。传送带每送来 1 克食物，他能处理 295 克的工作量。
> 传送带一秒送 3.35 公斤，听着不少，但他一秒能吃将近一吨。**所以他大部分时间在等饭，不是在吃饭。**

### 算一下 decode 的算术强度

生成一个 token 时发生了什么：

- **要搬的字节**：全部权重读一遍。$N$ 个参数，BF16 每个 2 字节，共 $2N$ 字节
- **要做的运算**：每个参数参与一次乘、一次加，共 $2N$ FLOP

算术强度 = $2N / 2N = 1$ FLOP/byte。

**1，对比拐点的 295。** 差了近 300 倍。这就是为什么单请求 decode 时 GPU 利用率惨不忍睹——它几乎全部时间都在等权重从显存搬过来。

好在有个办法：**batch**。同时处理 $B$ 个请求时，权重只需搬一遍，却服务了 $B$ 个 token：

- 搬的字节还是 $2N$
- 做的运算变成 $2NB$
- 算术强度 = $B$ FLOP/byte

所以要把 H100 的 BF16 算力喂饱，理论上 batch 得堆到 **295 左右**。实际达不到（KV cache 也要读，而它不能跨请求共享），但方向很清楚：**batch 越大，单位成本越低**。

这就是 [[07-Continuous batching]] 存在的全部理由——不是为了「顺便提高吞吐」，是因为不这么做，你买的算力有 99% 是浪费的。

### 再算一下 prefill

处理输入时，$T$ 个 token 一次性并行算完：

- 搬的字节：还是 $2N$（权重读一遍）
- 做的运算：$2NT$
- 算术强度 = $T$

输入 2048 个 token，强度就是 2048，**高于拐点 295**。所以 prefill 是 compute-bound——算力吃紧，带宽有余。

同一个模型、同一张卡，两个阶段落在拐点的两侧：

| | 算术强度 | 瓶颈 | 加大 batch 有用吗 |
| --- | --- | --- | --- |
| Prefill | ≈ 序列长度，通常几千 | 算力 | 帮助有限，本来就吃满了 |
| Decode | ≈ batch 大小 | 显存带宽 | **非常有用** |

这张表是 [[01-Prefill vs Decode]] 那一整套结论的根，也解释了为什么两个阶段要分开调度、分开计费。

### 由此推出的几件事

**量化为什么能提速。** BF16 换成 FP8，每个参数从 2 字节变 1 字节，decode 要搬的数据直接减半，速度接近翻倍。注意提速主要来自**搬得少**，不是算得快，见 [[09-量化]]。

**为什么 H200 比 H100 推理快。** 同一颗计算芯片，带宽从 3.35 涨到 4.8 TB/s。对 compute-bound 的 prefill 没帮助，对 memory-bound 的 decode 直接受益。

**为什么小模型的 token/s 高得多。** 权重少，每个 token 要搬的字节就少。这也是级联路由的物理基础，见 [[04-模型路由与级联]]。

**为什么长上下文会拖慢生成。** KV cache 随上下文线性增长，而它每步都要读。上下文越长，decode 每步要搬的字节越多。

> [!warning] 别把 GPU 利用率当成健康指标
> `nvidia-smi` 里那个「GPU 利用率」统计的是「有 kernel 在跑的时间占比」，不是「算力用了多少」。一张卡可以显示 100% 利用率，实际算力只发挥了 3%——因为那些 kernel 全都在等显存。
> 要看真实情况得用 Nsight 之类的工具分带宽利用率和算力利用率。这两个数才告诉你卡到底饿在哪一头。

## 动手做

- [ ] 用「算力 ÷ 带宽」算出你手上那张卡的拐点，记下来
- [ ] 单请求 decode 时看 `nvidia-smi`，记录利用率；再把 batch 加到 32、64、128，看吞吐怎么涨、单位成本怎么降
- [ ] 找出吞吐不再随 batch 增长的那个点，那就是你实际撞到别的瓶颈（多半是显存）的位置
- [ ] 同一模型 BF16 与 FP8 各测一次单请求 token/s，验证提速比例接近模型缩小的比例
- [ ] 用 Nsight 分别看带宽利用率和算力利用率，确认 decode 阶段是哪个先到顶

## 坑

**拿算力数字估推理速度。** decode 阶段算力基本用不上，估出来会离谱地乐观。该用带宽估。

**以为 GPU 利用率 100% 就是跑满了。** 那个指标只说明卡在忙，不说明它在算。真正的判据是带宽利用率和算力利用率。

**在 prefill 上死磕 batch。** prefill 本来就 compute-bound，加大 batch 收益有限，反而可能把 TTFT 拖长，见 [[02-指标体系]]。

**忘了 KV cache 也要搬。** 长上下文时它可能比权重还大，每一步 decode 都要读一遍。只按权重算带宽需求会低估。

**直接抄规格表上的 TFLOPS 去算拐点。** 那些数普遍是含结构化稀疏的，稠密只有一半——算出来的拐点会翻倍，于是你以为要 batch 590 才喂得饱，实际 295 就到了。这个误差会一路传染到容量规划。
