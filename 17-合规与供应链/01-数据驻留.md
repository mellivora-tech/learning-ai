「数据不出境」这句话在 LLM 应用里比在传统系统里难做得多——因为数据会流经模型推理、向量库、缓存、日志、可观测性平台，任何一处漏了都不算合规。

## 一句话

先画出**数据流经的每一个组件及其物理位置**，再逐个确认——LLM 应用里最常漏的不是主数据库，而是缓存、日志和可观测性平台。

## 原理

### 数据会流经哪些地方

比传统 CRUD 系统多出来一大截：

| 组件 | 存了什么 | 容易漏吗 |
| --- | --- | --- |
| 应用数据库 | 原始数据 | 不会 |
| **模型推理** | 输入输出经过厂商 | 不会（但要看条款） |
| **向量库** | 文档内容的向量与原文，见 [[03-Hybrid search（dense + BM25 + RRF）]] | **容易漏** |
| **KV / prompt 缓存** | 上下文片段，见 [[04-Prompt caching]] | **很容易漏** |
| **可观测性平台** | **完整的 prompt 和输出**，见 [[02-必打字段清单]] | **最容易漏** |
| 日志 | 报错时可能带原文 | 容易漏 |
| 评测数据集 | 从线上来的真实样本，见 [[06-用户信号如何变成 eval 与训练数据]] | 容易漏 |
| 训练数据 | 微调用的样本 | 容易漏 |

**可观测性平台是最大的漏点**：为了能排查问题，它通常存了完整的 prompt 和输出——也就是全量原始数据，而且很多 SaaS 平台的服务器在境外。

**评测数据集也是**：从线上采来的真实样本，一旦进了代码仓库或某个共享的数据平台，就跟着跑到别的地方去了。

### 三档合规要求

| 档次 | 要求 | 影响 |
| --- | --- | --- |
| 数据不出境 | 所有组件在指定地区 | 可以用当地的云服务 |
| **数据不出组织** | 不能给第三方 | **必须自建推理**，见 [[06-硬件要多少钱]] |
| 数据不出网络 | 完全隔离 | 全栈自建，包括模型权重 |

**第二档是分水岭**：一旦要求「不给第三方」，调用商业 API 就不成立了，成本结构完全改变。这个判断要在项目启动时就做，见 [[02-任务可行性判断]]。

### 自建推理不等于自动合规

自建之后仍然要检查：

- **模型权重从哪儿下的**，许可证允许你这么用吗，见 [[04-模型权重来源]]
- **可观测性还在用境外 SaaS 吗**
- **依赖的向量库、缓存是不是托管服务**
- **备份存在哪儿**

**备份是最后一个常见漏点**——主库在境内，备份自动同步到了另一个区域。

### 最小化是最省事的合规手段

与其证明每一处都合规，不如**一开始就不让敏感数据流进去**：

| 手段 | 说明 |
| --- | --- |
| **脱敏后再送模型** | 身份证号、手机号替换成占位符，返回后再还原 |
| 日志只记 hash 或摘要 | 排查够用就行 |
| **可观测性采样 + 脱敏** | 不需要存全量原文，见 [[02-必打字段清单]] |
| 设置保留期 | 过期自动删 |

**脱敏那条要注意**：脱敏本身要在数据离开你的边界之前做，而且要能还原（否则模型返回的内容对不上）。做法是用占位符映射表，映射表留在本地。

### 多租户下更复杂

不同租户可能有不同的驻留要求，见 [[06-多租户隔离]]：

- 索引要按租户分区，不能混在一个库里
- **缓存要按租户隔离**，否则跨租户命中就是数据泄露，见 [[05-缓存安全与跨租户命中]]
- 模型推理可能要按租户路由到不同地区的实例

**中间那条既是合规问题也是安全问题**，两边都要过。

### 写下来，定期核对

合规不是一次性的：

- 画一份**数据流图**，标出每个组件的物理位置
- 每加一个新组件（新的 SaaS、新的缓存层）就更新
- **定期核对**——尤其是托管服务，厂商可能变更区域

**没有数据流图的话，「我们合规吗」这个问题没人答得上来。**

## 坑

**只检查主数据库。** 向量库、缓存、可观测性平台都存着原始数据。

**忘了可观测性平台。** 它通常存全量 prompt 和输出，且很多是境外 SaaS。

**以为自建推理就合规了。** 可观测性、托管的向量库、备份都可能还在外面。

**备份跨区同步。** 主库合规，备份跑到了别的地区。

**多租户共用缓存。** 既是合规问题也是数据泄露。
