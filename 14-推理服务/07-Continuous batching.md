一批请求里最长的那个没做完，其余的就得干等着——传统批处理的这个毛病，在生成式模型上被放大到了不能忍。

## 一句话

把调度粒度从「一批请求」降到「一次前向」：谁生成完谁立刻离开，空出来的位子马上补新请求，卡就不会为了等最长的那个而空转。

## 原理

### 静态批处理的木桶效应

传统做法是攒够一批一起算，全部算完再收一批。这在分类、翻译这类**每个请求耗时接近**的任务上没问题。

生成式模型不一样：输出长度差异极大。同一批里有的请求生成 20 个 token 就结束，有的要生成 2000 个。

![[静态批与连续批.excalidraw.md|700]]

上半部分那些空框，就是已经生成完、却还占着批次位子干等的请求。**batch size 8 的批次里，可能大部分时间只有一两个还在真干活。**

而 decode 阶段的吞吐几乎正比于有效 batch 大小（算术强度 ≈ batch，见 [[01-Prefill vs Decode]]）——有效 batch 从 8 掉到 2，吞吐就掉到四分之一。

### 连续批处理做了什么

核心改动只有一句：**调度粒度从「整批请求」降到「一次前向」**。

每跑完一次前向（也就是每个请求各生成一个 token），调度器就检查一遍：

1. 谁生成了结束符或者到了长度上限？**立刻返回结果，释放它的 KV cache**
2. 队列里有没有等待的新请求？**立刻填进空出来的位子**
3. 剩下的继续下一轮

于是批次的成员在**每一步都在变**。它也叫迭代级调度，出处是 Orca 那篇论文。

效果是卡上始终维持着接近满的有效 batch。同样的硬件、同样的模型，吞吐提升几倍是常见的——**提升不来自算得更快，来自不再空转**。

### 新请求怎么插进来

这里有个细节：新请求要先做 prefill 才能加入 decode 批次，而 prefill 是 compute-bound 的重活。

所以每次插新请求，都会打断正在进行的 decode，让所有老请求的 TPOT 抖一下。**吞吐和延迟的矛盾就在这里**：插得越勤，卡越满、吞吐越高，但老请求的体验越抖。

vLLM 里主要靠两个参数拿捏：

| 参数 | 管什么 | 调大会怎样 |
| --- | --- | --- |
| `max_num_seqs` | 批次里最多几个请求 | 吞吐升，但受 KV cache 显存约束，见 [[03-KV cache 管理与显存测算]] |
| `max_num_batched_tokens` | 一次前向最多处理多少 token | 允许更多 prefill 混进来，吞吐升，TPOT 抖动变大 |

**这两个参数是在吞吐和延迟之间选点，不存在「最优值」**，只存在「符合你 SLO 的值」。扫参数画出帕累托前沿的做法见 [[10-吞吐-延迟帕累托前沿]]。

### 显存是硬约束

`max_num_seqs` 不能随便调大，因为每多一个请求就多一份 KV cache。算法很直接：

$$
\text{max\_num\_seqs} \le \frac{\text{可用显存}}{\text{每请求 KV cache}}
$$

超了会怎样？请求进来占不到显存，引擎只能**抢占**——把某个正在跑的请求踢出去，等有空间了再恢复。踢出去有两种做法（换出到内存 vs 直接丢掉重算），代价和选择见 [[06-驱逐与内存压力]]。

所以连续批处理、KV cache 显存、抢占策略这三件事是绑在一起的：**batch 想开大 → 显存不够 → 触发抢占 → 反而更慢**。找那个平衡点是推理调优的主要工作。

### 什么时候它帮不上忙

- **输出长度都差不多**：木桶效应本来就不明显，收益有限
- **并发极低**：batch 攒不起来，问题不在调度而在没流量
- **prefill 占主导**：输入很长、输出很短的场景（比如长文档抽取），瓶颈在 prefill，加大 decode batch 意义不大

第三种情况值得单独留意，因为它和直觉相反——**输入远长于输出时，连续批处理的收益会小很多**。

## 坑

**无脑调大 `max_num_seqs`。** 超过显存能撑的数量会触发抢占，P99 会比调之前更差。上限要先算出来，见 [[03-KV cache 管理与显存测算]]。

**只看吞吐不看 P99。** 吞吐和尾延迟是对立的两端。只报吞吐的压测报告基本没用。

**以为它能救 prefill。** 连续批处理主要改善 decode 阶段的资源利用率，prefill 那段该慢还是慢。

**在低并发下评估它。** 流量不够时批次攒不起来，测出来收益很小，误以为不值得开。

**忽略它带来的抖动。** 新请求插入会打断 decode。追求极致稳定 TPOT 的场景要配合 chunked prefill，见 [[01-Prefill vs Decode]]。
