一千个请求共用同一段两千 token 的系统提示，那两千 token 的 K、V 算了一千遍。这笔钱不该花。

## 一句话

前缀相同的请求可以共用 KV cache 块，省掉重复的 prefill；而**前缀必须逐 token 完全相同**，所以动态内容放在哪一位置直接决定命中率。

## 原理

### 怎么共享

在分页机制下，每个请求的 KV cache 是一串块，块表记录哪一段在哪个物理块，见 [[04-PagedAttention 与分页显存]]。

前缀缓存就是让**多个请求的块表前几项指向同一个物理块**：

![[前缀缓存怎么共享.excalidraw.md|700]]

实现上通常按块内容做哈希：算到某一块时，先查这个哈希在不在缓存里，在就直接引用、跳过计算。

省的是 **prefill 的算力**——那段前缀的 K、V 一次都不用重算。对系统提示很长的场景，TTFT 能降一大截，见 [[02-指标体系]]。

### 命中的前提：逐 token 完全相同

这是全部工程注意事项的来源。**差一个 token，从那一块往后全部失效。**

所以 prompt 要按「变化频率」分层组织：

```text
① 系统提示、工具定义、few-shot 例子      ← 永远不变，放最前
② 租户级配置、用户画像                    ← 一个会话内不变
③ 检索到的文档                            ← 每次请求变
④ 用户这一轮的问题                        ← 一定变
```

**从上到下，越靠后变得越勤。** 顺序反了，前缀就断了。

> [!warning] 最常见也最贵的一个错
> 有人在 system prompt 开头加了一行 `当前时间：2026-07-31 14:23:07`。
> 每个请求的第一个块就不一样了，**整个缓存命中率归零**，prefill 成本翻几倍。而这件事在总成本曲线上要过几天才看得出异常，在「按 feature 拆的缓存命中率」那张图上却是断崖。
> 时间戳、随机 ID、请求序号——所有动态内容都必须放在末尾。这条也是 [[04-Prompt caching]] 的核心。

### 自建和调 API 是两回事

| | 自建（vLLM 这类） | 调 API |
| --- | --- | --- |
| 怎么开 | 引擎参数，通常默认开 | 各家规则不同，有的自动、有的要显式标记 |
| 计费 | 省的是你自己的算力 | 缓存命中的 token 通常按折扣价计费 |
| 观测 | `gpu_prefix_cache_hit_rate` 之类的指标 | 返回里的 `cached_read` 字段 |

不管哪种，**缓存命中率都该是常规监控项**，不是出事才查的东西，见 [[02-必打字段清单]]。

### 和 chunked prefill 的一个坑

vLLM V1 默认开启 chunked prefill——把长 prompt 切成小块，和 decode 请求交错处理，见 [[07-Continuous batching]]。

但两者组合有个已知的粗糙处：**长 prompt 被切成多块之后，只有第一块能利用前缀缓存**，后面几块的缓存利用不充分。

实践上的含义：**如果你的 prompt 特别长且前缀高度重复，要实测一下这两个特性同时开的效果**，别假设收益能叠加。

### 安全：不能随便共享

前缀缓存跨请求共享数据，这本身就是一个需要设边界的地方：

- **cache key 必须包含 `tenant_id` 和权限范围**，否则理论上存在跨租户命中
- prefix cache 还带来 **TTFT 时序侧信道**——命中和不命中的首字延迟差别明显，攻击者可以据此推断「某段前缀是否曾被别人请求过」

高敏场景要按租户分池。展开见 [[05-缓存安全与跨租户命中]]。

## 动手做

- [ ] 做两版 prompt：时间戳放开头 vs 放结尾，各压一轮，对比缓存命中率和 TTFT
- [ ] 把 prompt 按四层重新排序（静态 → 半静态 → 检索 → 用户输入），记录命中率变化
- [ ] 观察引擎的前缀缓存命中率指标，把它加进日常看板
- [ ] 同时开启 chunked prefill 和前缀缓存，用超长 prompt 实测，看收益是否叠加
- [ ] review 一份现有的 prompt 模板，找出哪一行把命中率打成了 0

## 算学会了

- [ ] 能一眼看出 prompt 模板里哪一行会破坏前缀缓存
- [ ] 按变化频率组织 prompt 是默认习惯，不是优化项

- [ ] 知道 cache key 要带租户和权限维度

## 坑

**在前缀里放动态内容。** 时间戳、随机 ID、请求计数——一个就够把命中率打成 0。

**以为「差不多相同」就能命中。** 逐 token 完全相同才行，多一个空格都不算。

**只在开发时验证。** 开发时 prompt 是固定的，命中率很好看；线上有租户变量、有 A/B 实验，实际情况完全不同。

**不监控命中率。** 它会悄悄归零，而总成本曲线要过很久才反映出来。

**跨租户共享缓存。** cache key 不带租户维度，就是一个真实的隔离漏洞。
