把权重从 16 位压到 8 位，模型小一半、吐字快一倍。问题从来不是「能不能压」，而是「压完到底掉了什么」——而这个问题用 PPL 是测不出来的。

## 一句话

量化的收益主要来自**少搬数据**而不是算得更快；代价是能力的不均匀损失，只能靠贴近你任务的 eval 测出来。

## 原理

### 为什么它能提速

回到 decode 的瓶颈：每生成一个 token 要把全部权重从显存搬一遍，算术强度约等于 batch，卡在带宽上，见 [[01-Prefill vs Decode]]。

那么把每个参数从 2 字节压到 1 字节，**要搬的数据直接减半**，decode 速度接近翻倍。

$$
\text{decode 上限} = \frac{\text{显存带宽}}{\text{模型字节数}}
$$

分母减半，上限翻倍。注意这个收益**和算力无关**——就算硬件对低精度没有专门加速，光是少搬一半数据就已经赚到了。

第二个收益同样重要：**腾出来的显存全归 KV cache**。Qwen3-8B 从 BF16 换到 FP8，权重从 16.4 GB 降到 8.2 GB，多出来的 8 GB 能多支撑七十多个 8k 上下文的并发，见 [[03-KV cache 管理与显存测算]]。

### 常见格式

| 格式 | 位宽 | 特点 |
| --- | --- | --- |
| BF16 | 16 | 基准，多数模型的原始精度 |
| FP8 | 8 | 硬件原生支持（Hopper 起），实现简单，质量损失小 |
| INT8 | 8 | 需要校准，兼容性最好 |
| AWQ | 4 | 激活感知，保护对激活影响大的那部分权重 |
| GPTQ | 4 | 逐层最小化重建误差 |
| FP4 | 4 | Blackwell 起硬件支持 |

选择的实用顺序：**先试 FP8**——硬件原生、掉点小、实现成熟；不够再往 4 位走。4 位的质量损失明显更大，而且不同方法在不同模型上表现不一，必须实测。

### 三个地方可以量化

这三件事经常被混为一谈，但代价完全不同：

**权重量化。** 最常见，收益最直接（模型变小、搬得少）。质量影响可控。

**激活量化。** 中间结果也用低精度。能进一步提速，但更容易出问题——激活值里常有极端离群值，压狠了会崩。

**KV cache 量化。** 用 FP8 存 K、V，缓存直接砍半，并发翻倍。质量影响通常比权重量化温和，**但长上下文召回是最容易掉的一项**，要单独测。

很多人说「我上了量化」时只做了第一项。三项各有各的收益和风险，报告时要说清楚做了哪几项。

### 怎么评估掉了什么

> [!warning] 别用 PPL
> 困惑度（perplexity）是最常见也最没用的量化质量指标。它测的是模型对一段文本的整体预测分布，对**能力的局部损失极不敏感**——PPL 只涨 0.1，JSON 合规率可能从 99% 掉到 85%。
> PPL 好看不代表能用。它唯一的价值是当冒烟测试：PPL 涨很多说明肯定坏了，但没涨不说明没坏。

该测的是这四类，它们各自会以不同方式塌：

1. **你的任务 eval**——最重要的一条。用真实样本，见 [[01-Golden set]]
2. **结构化输出合规率**——JSON 能不能解析、schema 对不对。这一项对量化异常敏感，见 [[01-结构化输出三档]]
3. **长上下文召回**——把信息埋在 32k 的不同位置，看还找不找得到。KV cache 量化尤其影响这一项
4. **多步推理**——需要连贯推几步的任务。量化后的模型常常「答得像那么回事但中间一步错了」

**目标不是知道「掉了多少」，是定位「掉在哪个能力上」。** 掉在你不用的能力上，那就是白赚；掉在你的核心路径上，再小也不能上。

### 什么时候不该量化

- **本来就不受带宽约束**：prefill 为主的负载（长输入短输出），量化的提速收益有限
- **任务对精度极敏感**：数值计算、精确抽取，先小心测
- **模型本身就小**：小模型的冗余度低，同样的量化方法掉点更多
- **没有 eval**：没有能测出质量变化的手段就上量化，等于蒙眼开车。这是 roadmap 把「度量先行」排在前面的原因

## 动手做

- [ ] 同一个模型跑 BF16、FP8、AWQ-INT4 三版，记录显存占用、TTFT、TPOT
- [ ] 验证 decode 提速比例是否接近模型缩小的比例——对不上说明瓶颈不在带宽
- [ ] 四类质量测试各跑一遍：任务 eval、JSON 合规率、长上下文召回、多步推理，做成一张对照表
- [ ] **不要只报平均分**，找出每个版本具体错在哪类输入上
- [ ] 单独开 KV cache 量化（权重不动），测长上下文召回的变化
- [ ] 用省下的显存把并发调上去，算一下单位成本降了多少——这才是量化的最终收益

## 算学会了

- [ ] 能解释量化提速主要来自减少数据搬运，而不是算得更快
- [ ] 知道 PPL 测不出量化的真实损失，能说出该测哪四类
- [ ] 能区分权重量化、激活量化、KV cache 量化三者的收益与风险
- [ ] 能定位「INT4 具体掉在哪个能力上」，而不是笼统说「掉了点」
- [ ] 会把省下的显存换成并发，算出单位成本的实际改善

## 坑

**拿 PPL 当验收标准。** 这是量化上线最常见的翻车方式——指标好看，线上 JSON 解析失败率翻倍。

**只报平均分。** 「eval 掉了 2 个点」没有信息量。掉在长尾还是掉在主路径，意义完全不同。

**以为量化只影响质量不影响行为。** 量化后的模型可能输出长度分布变了、更容易重复、停止符判断变差——这些不在准确率里。

**在没有 eval 的情况下上量化。** 你不会知道它什么时候坏的，也不会知道坏了多少。

**忘了 KV cache 也能量化。** 很多人只做权重量化就以为到头了，KV cache 那一半的收益完全没拿。
