显存满了，新请求还在进。引擎必须踢掉某个正在跑的请求——踢谁、怎么踢、踢完怎么回来，决定了你的 P99 有多难看。

## 一句话

抢占有换出和重算两条路，而**多数场景下重算更快**——因为 prefill 是并行的，而把几 GB 数据搬到内存再搬回来是串行的。

## 原理

### 为什么会满

KV cache 随「上下文 × 并发」增长，而这两个都是运行时才知道的变量，见 [[03-KV cache 管理与显存测算]]。所以引擎必须**超额接单**：按平均长度调度，赌大多数请求不会跑满。

赌输的时候就得抢占。典型触发场景：

- 几个请求同时进入长输出阶段
- 一批超长 prompt 撞在一起
- `max_num_seqs` 配得太乐观，见 [[07-Continuous batching]]

### 两条路

被踢掉的请求，它已经算好的 KV cache 怎么办？

**换出（swap）**——把 KV cache 从显存搬到主机内存，等有空间了再搬回来。

**重算（recompute）**——直接丢掉，等重新调度时把整个 prompt 重新 prefill 一遍。

直觉上换出更划算——毕竟算好的东西留着了。但实际上：

| | 换出 | 重算 |
| --- | --- | --- |
| 代价 | 通过 PCIe 搬几 GB，来回两趟 | 重跑一次 prefill |
| 并行度 | **串行**，受 PCIe 带宽限制 | **高度并行**，正是 GPU 的强项 |
| 占用 | 换出期间还占着主机内存 | 不占 |
| 实现复杂度 | 要管两份存储和搬运时机 | 简单 |

**vLLM V1 的默认抢占策略就是重算**，官方给的理由是在 V1 架构下重算开销更低。

这条结论值得记住，因为它反直觉：**丢掉算好的结果重新算一遍，比把它搬走再搬回来更快。** 根子在 [[02-算力经常用不满：两种瓶颈]] 那条 —— prefill 是 compute-bound 且高度并行，而 PCIe 搬运是串行的窄管道，两者差着一个数量级。

### 踢谁

常见策略是**后来的先踢**（近似 LIFO）：

- 新来的请求进度少，重算代价小
- 老请求快做完了，踢掉浪费更大
- 而且能避免「饿死」——老请求总能做完

代价是新请求的尾延迟会很难看。有些场景会加优先级，让付费租户或者交互式请求免于被踢。

### 抢占是尾延迟的头号杀手

一次抢占对被踢的那个请求意味着：

1. 已经生成的进度**不会丢**（token 已经返回了），但 KV cache 没了
2. 重新排队，等有空间
3. 重新 prefill 整段历史——**而这时候历史比第一次更长了**（包含已生成的部分）
4. 继续生成

所以它的延迟惩罚是**非线性**的：越晚被踢，重算的代价越大。而且抢占往往成批发生（显存压力是全局的），于是 P99 会整片塌下去。

> [!warning] 抢占率是必看指标
> 平均延迟看不出抢占，因为它只影响少数请求。但那些请求可能延迟翻好几倍。
> **把抢占次数打进指标**，和 P99 放一起看。抢占率不为零，说明你的 `max_num_seqs` 配得太乐观了——这时候调小它，P99 会明显改善，吞吐只掉一点，见 [[10-吞吐-延迟帕累托前沿]]。

### 怎么让它少发生

按代价从低到高：

1. **调小 `max_num_seqs`**——最直接，用一点吞吐换稳定
2. **调小 `max_model_len`**——多数业务用不到宣称的最大上下文
3. **KV cache 量化**——FP8 存 KV，容量翻倍，见 [[09-量化]]
4. **权重量化**——腾出来的显存全给 KV cache
5. **加卡**——最后才考虑，见 [[06-怎么给任务选卡]]

**接受一点抢占是合理的**——完全不抢占意味着你按最坏情况配置容量，多数时候卡在闲着。目标不是零抢占，是把抢占率控制在 P99 能接受的范围内。

## 坑

**以为换出一定比重算好。** 直觉上留着算好的结果更省，实际 PCIe 搬运是串行窄管道，通常更慢。

**不监控抢占。** 它只影响少数请求，平均延迟完全看不出来，但 P99 会塌。

**把 `max_num_seqs` 调到极限。** 吞吐多一点点，抢占频发，P99 崩掉。

**用平均延迟评估抢占的影响。** 一定要看分位数。

**追求零抢占。** 那意味着按最坏情况配容量，平时大量算力闲置。
